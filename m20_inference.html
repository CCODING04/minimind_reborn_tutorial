五连纯函数：sampling.py 逐个复算

inference/sampling.py 全文 70 行、五个函数，模块 docstring 第一行就立了规矩：≤10 行一个、带形状注释、可独立单测。 这不是风格洁癖——五个函数全是纯函数（同样的输入永远给同样的输出，不碰任何外部状态）， 于是每个都能用一行断言锁死行为（本课验收的 7 个采样测试就是证据）。 本课第一个新概念——采样纯函数链契约——指的就是这两件事的合成： 五个函数的顺序固定为 temperature → repetition_penalty → top_k → top_p → 采样， 且每个函数只做一件事、可被单独验证。顺序为什么固定，M03 测验 3 已推导过（先定型、再截断）， 本课补上每个环节的数值手感。

① apply_temperature：除法改形状，≤0 是"贪心"开关

src/minimind_reborn/inference/sampling.py · apply_temperature 全文python
def apply_temperature(logits: torch.Tensor, temperature: float) -> torch.Tensor:
    """logits: (b, vocab)。temperature ≤ 0 语义是"贪心"，此处原样返回，由 sample_token 走 argmax 分支。"""
    if temperature <= 0:
        return logits
    return logits / temperature

logits（模型对词表每个候选的未归一化打分，M02 调温度时摸过）除以 T：T<1 放大间距、 softmax 后分布更尖；T>1 压平间距、分布更平。注意 ≤0 不是"报错"而是显式语义—— 原样返回、让下游走 argmax（必选第一名）。这就是 M03 变式里 temperature=0 连跑两次逐位一致的原因。

② apply_repetition_penalty：正数除、负数乘

src/minimind_reborn/inference/sampling.py · apply_repetition_penalty 全文python
def apply_repetition_penalty(logits, generated_ids, penalty: float):
    """对已出现 token 的 logits 施加惩罚：正数除、负数乘（官方语义）。

    generated_ids: (b, seq) 全部已见序列（prompt+生成）。"""
    if penalty == 1.0:
        return logits
    for i in range(logits.shape[0]):
        seen = torch.unique(generated_ids[i])       # 本条序列出现过的所有 token
        score = logits[i, seen]
        logits[i, seen] = torch.where(score > 0, score / penalty, score * penalty)
    return logits

它是五连里唯一需要随步变化的状态（已见序列每步变长）——所以由 generator 在调 sample_token 之前施加（generator.py:82-83），sample_token 自己不碰它（sampling.py:61-63 注释即此契约）。 "正除负乘"的语义值得停一下：惩罚的目的是压低已见 token 的概率。 正分除以 θ>1 变小，好理解；负分为什么要乘 θ？负分本身已是低概率，除以 θ 会把它 抬回来（−2/2=−1，概率反升）——方向反了。乘 θ 让它更负（−2×2=−4），概率继续往下走： $$ h(s)=\begin{cases} s/\theta, & s>0\\[2pt] s\cdot\theta, & s\le 0 \end{cases} \qquad \theta>1 \Rightarrow \text{已见 token 概率单调下降} $$ 这份分段语义直接来自官方实现（HF transformers 与 CTRL 论文同款），reborn 照抄并配了测试锁定 （test_repetition_penalty_direction，下面验收见）。

③④ apply_top_k / apply_top_p：两种截断，一种落笔（置 −inf）

src/minimind_reborn/inference/sampling.py · 两个截断函数python
def apply_top_k(logits, top_k: int):
    """保留前 k 大，其余置 -inf。top_k=0 表示关闭。"""
    if top_k <= 0 or top_k >= logits.shape[-1]:
        return logits
    threshold = torch.topk(logits, top_k)[0][..., -1, None]  # 第 k 大的值作阈值
    logits[logits < threshold] = -float("inf")
    return logits

def apply_top_p(logits, top_p: float):
    """核采样：按概率降序累积，保留质量 ≤ p 的前缀，其余置 -inf。top_p ≥ 1 关闭。"""
    if top_p >= 1.0:
        return logits
    sorted_logits, sorted_indices = torch.sort(logits, descending=True)
    cumulative = torch.cumsum(torch.softmax(sorted_logits, dim=-1), dim=-1)
    # 右移一位：累积恰好超过 p 的那个 token 也要保留（否则必然丢掉跨过 p 的 token）
    mask = cumulative > top_p
    mask[..., 1:] = mask[..., :-1].clone()
    mask[..., 0] = False
    out = logits.clone()
    out[mask.scatter(1, sorted_indices, mask)] = -float("inf")
    return out

top_k 按个数截（硬上限），top_p 按概率质量截（核采样，nucleus sampling—— 保留累积概率达到 p 的最小集合）。两者落笔方式相同：不要的候选 logits 置 −inf， softmax 后概率正好为 0——不用真删列，词表维度恒定。注意 top_p 那三行右移： 累积跨过 p 的那一个 token 必须留下，否则保留质量永远到不了 p（本页下文实测里 0.5+0.3+0.15=0.95 保留 3 个就是右移的功劳）。

⑤ sample_token：链的出口，贪心与抽签二选一

src/minimind_reborn/inference/sampling.py · sample_token 全文python
def sample_token(logits, gen: GenerateConfig, generator=None):
    """单步采样入口。返回 (b, 1) 的 token id；temperature ≤ 0 显式走贪心分支。

    repetition_penalty 需要"已见序列"这个随步变化的状态，由 generate 内核
    在调用本函数前施加，这里不做。"""
    logits = apply_temperature(logits, gen.temperature)
    logits = apply_top_k(logits, gen.top_k)
    logits = apply_top_p(logits, gen.top_p)
    if gen.temperature <= 0:
        return torch.argmax(logits, dim=-1, keepdim=True)   # 贪心：必选第一名
    probs = torch.softmax(logits, dim=-1)
    return torch.multinomial(probs, num_samples=1, generator=generator)  # 按概率抽签

multinomial（按概率有放回抽签，M03 ⑥站用过）吃 softmax 之后的概率；可选的 generator 参数传入 torch 的随机数发生器——固定 seed 就能复现（测试 test_generation_deterministic_with_seed 锁的正是这条承诺）。注意 sample_token 内部 又调了一次 apply_temperature——每个函数单独看都对，这一行马上会在 猎场里变成主角。

💡 为什么非要纯函数

五个函数不持有模型引用、不读全局变量、不写日志——张量进、张量出。 三个直接收益：① 可单测：test_generator 里 4 个采样用例每个只要三四行构造输入， 不用加载权重；② 可复现：同输入同输出，bug 报告里贴一组数字就能对质； ③ 可重组：RL rollout（M19）想换采样策略，拼的还是这五块积木。 反例是把采样写进生成循环——循环体一长，"每步发生了什么"就只能靠猜。

🔍 bug 猎场：双重温度——纯函数都对，串起来 logits/T²

M03 ⑥站的"停一下"埋过雷：apply_temperature 在 generate 路径上被调两次。 今天立案。先并排看两处代码——

同一温度、两处落笔 · generator.py:80-84 与 sampling.py:64python
# generator.py:80-84（内核主循环里）——第一次

if gen.repetition_penalty != 1.0:
    scaled = apply_repetition_penalty(scaled, input_ids, gen.repetition_penalty)

# sampling.py:64（sample_token 内部）——第二次

修复方案有两边可选：删 generator.py:81 的外层调用（让采样链的"顺序契约"归 sampling.py 独家所有——温度与惩罚都是标量乘除、数学上可交换，挪动不改变结果），或给 sample_token 加 "已预缩放"开关（丑，还破坏它独立单测的契约）。方案一边是对的。 但——本课选择先不修，这是工程判断而非偷懒：

📐 不修的工程判断：改行为 = 改所有已训权重的"表现"

这不是崩溃型 bug，而是行为漂移型：修掉它，所有非贪心采样的输出分布立刻从 softmax(z/T²) 变成 softmax(z/T)——M02 的温度旋钮实验、M16 的生成对比、M19 的全部 rollout（temperature=0.8 → 有效温度从 0.64 跳回 0.8）都会变了样。已训权重的评测基准、 已观察到的采样行为，全部建立在旧分布上。负责任的做法是修复 + 回归评估一起上： 修前修后各跑固定题集（M21 的评测工具正好在场），对比贪心输出（免疫路径，应逐位一致） 与采样输出的分布统计，确认没有意外塌缩再合入。教学仓库按此纪律留给读者作为毕业实验的候选题目 （M22），本课先把检测做实：插桩计数本身就是该进的回归测试—— assert CALLS["n"] == steps，一行锁定"每步恰好一次"。

通用教训与 M02 的签名 bug 同构：契约要有测试锁着，否则每个零件的正确会合谋成整体的错误。 五连函数各有单测、generate 也有 7 个测试，但没有任何一条断言"温度在完整路径上只被应用一次"—— 缝隙又一次长在两块正确之间。

停止三重：generator 的三道闸

生成循环什么时候停？答案是三重停止条件（generator.py:1-7 文件头原文"缺一不可"）， 也是本课第二个新概念——停止条件体系：token 级、循环级、后处理级三道闸各管一层， 少任何一道都会出一种具体事故。循环主体 M03 ④站巡游过，这里只看三颗螺丝：

src/minimind_reborn/inference/generator.py · 三道闸的落笔处python
# 闸 1（token 级）：已结束序列冻结为 eos 占位；finished 只由"新 token"更新
if eos_token_id is not None:
    next_token = torch.where(finished.unsqueeze(-1),
                             torch.full_like(next_token, eos_token_id), next_token)
input_ids = torch.cat([input_ids, next_token], dim=-1)      # (b, T) → (b, T+1)
...
if eos_token_id is not None:
    # 只认"生成位"的 eos——input 里已有的 eos 不会触发（finished 掩码只由新 token 更新）
    finished |= next_token.squeeze(-1).eq(eos_token_id)
    if bool(finished.all()):                                # 闸 2（循环级）：batch 全停才 break
        break
...
# 闸 3（后处理级）在 chat/engine 层：解码后按 eos 截断残留（chat.py:103 / engine.py:198）

闸 1 为什么"prompt 里的 eos 不算数"——这是最反直觉的一条。eos（end of sequence， 对话结束标记 <|im_end|>）在 pretrain 语料里身兼数职：文档之间的分隔符、 凑批时的 pad 位都用 <|endoftext|>（M03 ①站见过常量表）。如果停止条件是 "序列里出现 eos 就停"，那么一个合法携带分隔符的 prompt 会让生成在第 0 步前就宣布结束。 所以 finished 掩码只由新生成的 token 更新（generator.py:96-97），测试里专门有一条： 把 eos 预置进 prompt 再生成，断言 generated_ids.shape[1] > 0——"prompt 内的 eos 不应触发生成停止"。

闸 2 为什么必须"全停"才 break——batch 里两条序列长短不一是常态：短的先抽中 eos， 长的还要继续。若一条停就全停，长句被拦腰斩断；若不冻结已停序列（闸 1 的 torch.where）， 它会继续"生成"垃圾尾巴。三重协作的完整断言在 test_stop_triple_batch_short_and_long： eos 之后全为 eos 占位、finish_reason 逐条如实（stop/length）。

闸 3 为什么解码后还要截一刀——停止占位与残余 token 在 id 层无法删除（batch 形状要 对齐），只能在 decode 前把 eos 之后的部分切掉：ids[: ids.index(eos)] （engine.py:198-202，chat.py:103-109 各有一份）。三道闸各管一层：闸 1 管"谁还在生成"， 闸 2 管"循环何时退出"，闸 3 管"用户看到什么"。

streamer 与 cancel：把循环接到外面

chat 滑窗：训练怎么截，推理就怎么忘

inference/chat.py 的 ChatSession 管"会话记忆"。多轮对话里历史只会越滚越长，最终把 prompt 推过训练窗口—— 模型在没见过的长度上生成，质量塌缩。M12 讲训练侧怎么处理超窗样本（C1：丢最旧整轮、 左截 user 保尾部），推理侧的止血是同一个策略的镜像：

src/minimind_reborn/inference/chat.py · _trim_history 全文python
def _trim_history(self) -> None:
    """历史超预算时成对丢最旧轮次（至少保留当前 user 消息）；仅剩当前消息仍超时左截其内容保尾部。"""
    budget = self.history_budget
    if budget is None:
        return

    def over(msgs):
        return self._prompt_tokens(render_chat(self.tokenizer, msgs)) > budget

    # history 形如 [user, assistant, ..., user(本轮)]，每次丢最旧的 (user, assistant) 对
    while len(self.history) > 1 and over(self.history):
        self.history = self.history[2:]
        self.dropped_turns += 1                    # 滑窗丢弃计数（可观测）
    # 只剩当前 user 消息仍超预算：左截内容保尾部（截字符近似，与训练侧保尾策略同构）
    if len(self.history) == 1 and over(self.history):
        text = self.history[0]["content"]
        while len(text) > 32 and over([{"role": "user", "content": text}]):
            text = text[max(1, len(text) // 5):]   # 每次砍掉前 1/5，直到装得下
        self.history[0]["content"] = text

与 M12 的 C1 逐条对上——"训练怎么截，推理就怎么忘"：

策略训练侧 C1（datasets.py _fit_turns）推理侧滑窗（chat.py _trim_history）
超窗先丢整轮二分丢最旧 (user, assistant) 对，system 恒留while 循环丢最旧 history[2:]，本轮 user 恒留
单条仍超左截 user 内容保尾部（32 字符保底）左截内容保尾部（len(text) > 32 保底）
assistant 回复永不在这里截（监督信号所在）不截（还没生成呢——截的是输入）
可观测性stats 字典（fitted/dangling/…）dropped_turns 计数

同构不是审美，是因果：模型只在"训练时见过的输入形态"上可靠。训练样本从来不会带超窗历史 （C1 已经把它们裁成 ≤ max_length），推理若放任历史超窗，等于把模型推到分布外的长度上作答。 滑窗让推理侧输入的形态分布贴着训练分布——这是 C1 在推理侧的镜像义务。 行为由 test_chat_budget 的 4 个 session 用例锁定：不限预算时全保留、超预算成对丢 （user/assistant 数量恒相等）、送入生成的 prompt 不超预算、单条超长消息左截保尾 （endswith("结尾标记")）。

检验一下

测验 1 · prompt 里已经出现了 eos，为什么不能据此停止生成？

答案：pretrain 语料里 eos（<|endoftext|>）身兼数职——文档分隔符与 pad 位都是它，prompt 合法携带它太正常了。若"序列里出现 eos 就停"，这类 prompt 会在生成第 0 步前就被宣布结束。所以 finished 掩码只由新生成的 token 更新（generator.py:96-97），测试专门断言"prompt 内的 eos 不应触发生成停止"。

答错回看：停止三重 闸 1 段。

测验 2 · 双重温度为什么"危险"？哪些路径踩不到它？该怎么锁？

答案：它不崩溃、不报错，只是把采样分布悄悄换成 softmax(z/T²)——旋钮读数与实际行为脱钩（0.85 实际 0.7225），且影响所有显式走 generate 的路径（engine 两入口、ChatSession、tools/chat.py、serve.py、RL rollout）；踩不到的是贪心路径（≤0 原样返回）与 sample_token 直调的单测——所以零件测试全绿也发现不了。锁法：把插桩计数做成回归断言（每步 apply_temperature 恰好一次），或加一条"generate 与手工单次缩放分布一致"的接线测试。

答错回看：双重温度猎场 的影响面表与不修判断卡。

测验 3 · ChatSession 的滑窗与训练侧 C1 截断同构，这说明了什么设计原则？

答案："训练怎么截，推理就怎么忘"——模型只在训练时见过的输入形态上可靠；C1 已把训练样本裁进窗口（丢最旧整轮、单条左截保尾），推理若放任历史超窗就是把模型推到分布外长度。滑窗逐条复刻 C1（丢最旧 user+assistant 对、本轮恒留、单条左截保尾、dropped_turns 可观测），让推理输入的形态分布贴着训练分布。原则：推理侧的预处理必须是训练侧预处理的镜像，不能自创。

答错回看：chat 滑窗 的对照表。

测验 4 · 重复惩罚对 logit=−2 的已见 token，为什么是乘 2 得 −4，而不是除 2 得 −1？

答案：惩罚的目的是压低已见 token 的概率。−2 除以 2 得 −1，负分变小 → softmax 概率反而上升，方向反了；乘 2 得 −4 更负 → 概率继续下降。"正数除、负数乘"保证两种符号下惩罚方向一致（单调压低），这是官方语义，test_repetition_penalty_direction 用 [2,−2] 一行断言锁死。

答错回看：apply_repetition_penalty 的分段公式。

本课词汇

采样纯函数链契约 sampling chain contract
五个 ≤10 行纯函数按固定顺序串联（temperature → repetition_penalty → top_k → top_p → 采样），每个只做一件事、可独立单测；顺序即契约——先定型、再截断。本课证明：零件各自正确不保证串联正确，契约本身要有测试锁定。
停止条件体系 stop conditions, triple
token 级（eos 掩码只认生成位——prompt 携带的 eos 不算，因 pretrain 语料里它是文档分隔/pad）、循环级（batch 全停才 break，已停序列冻结为 eos 占位）、后处理级（decode 前按 eos 截断残留）。三道闸各防一种事故，缺一不可。
重复惩罚 repetition penalty
对已见 token 的 logits 分段缩放：正数除 θ、负数乘 θ（θ>1），保证两种符号下概率都单调下降。token 级而非短语级；合法重复与复读一起被罚——急救包不是补品。
核采样 top-p / nucleus sampling
按概率降序累积，保留质量达到 p 的最小候选集；实现要点是累积掩码右移一位——跨过 p 的那一个 token 必须留下，否则保留质量永远到不了 p。
滑动窗口 sliding window, history_budget
ChatSession 的会话记忆管理：渲染后 prompt 超预算即成对丢最旧轮次、单条超长左截保尾——与训练侧 C1 截断（M12）逐条同构；dropped_turns 计数可观测。"训练怎么截，推理就怎么忘"。
streamer / cancel 流式回调 / 取消回调
generator 主循环的两个挂点：streamer 每步上交新 token（流式输出的机制），cancel 每步开始前检查、True 即中止（已生成部分保留，finish_reason="cancelled"；commit 20c334d，功能与回归测试同 commit）。
SSE Server-Sent Events
HTTP 长连接上逐帧推送 data: {...}\n\n 的协议；serve.py 流式端点的传输层，OpenAI 风格 API 的 stream=true 即走它。
OpenAI 风格 API OpenAI-compatible API
业界事实标准的服务接口约定（/v1/chat/completions 端点、messages 进 choices 出、delta 流式增量、tool_calls 结构）。实现它 = 生态里所有现成客户端直接可用。
