母版精读：范式到底有多薄

M13 立过一条规矩（trainer.py 模块 docstring 原话）："范式子包只提供 compute_loss(batch, model) -> (loss, log_metrics) 与数据组装。梯度/AMP/裁剪/续训/评估/保存的顺序与不变量固定在此处，任何范式不得绕过。" 当时不验证——现在到了验证的时候。数行数是最诚实的办法： wc -l 亲测，pretrain 母版 37 行、SFT 母版 49 行（含空行与 docstring）。 37 行全文如下，一段一段看：

src/minimind_reborn/training/pretrain/workflow.py · 全文 37 行python
"""预训练 workflow：差异只有数据集与损失——其余全部来自 Trainer 基件。"""

from __future__ import annotations

from minimind_reborn.configuration.schemas import RunConfig
from minimind_reborn.loggers import setup_logging
from minimind_reborn.training.common.setup import build_lm_dataset, build_model, load_tokenizer
from minimind_reborn.training.common.trainer import Trainer


def run(cfg: RunConfig, *, device: str | None = None, local_rank: int = 0) -> Trainer:
    setup_logging(cfg.run_dir)
    tokenizer = load_tokenizer()
    model = build_model(cfg, tokenizer)
    train_ds, eval_ds = build_lm_dataset(cfg, tokenizer, kind="pretrain")

    def compute_loss(batch, m):
        out = m(batch["input_ids"], labels=batch["labels"])
        loss = out.loss + out.aux_loss  # aux 仅 MoE 非零；dense 恒 0，加法等价官方
        return loss, {
            "train/loss": out.loss.item(),
            "train/aux_loss": float(out.aux_loss),
        }

    trainer = Trainer(
        cfg,
        model,
        tokenizer,
        train_ds,
        eval_ds,
        compute_loss=compute_loss,
        save_weight="pretrain",
        device=device,
        local_rank=local_rank,
    )
    trainer.run()
    return trainer

去掉 docstring 与 import，正文只有三件事。① 组装四件（12–15 行）： load_tokenizer() 拿 M10 造的分词器；build_model(cfg, tokenizer) 建 M09 的整机（内部先过词表断言——模型 6400 与 tokenizer 对不上直接 ValueError 拒绝训练）； build_lm_dataset(..., kind="pretrain") 走 M11 的注册表拿 M12 的 PretrainDataset。② compute_loss 闭包（17–23 行，共 7 行）——范式对引擎的全部接口， 其中真正的"损失计算"只有一行：

workflow.py · compute_loss 逐行python
out = m(batch["input_ids"], labels=batch["labels"])   # M09 的移位交叉熵在模型 forward 里就算好了
loss = out.loss + out.aux_loss                       # CE + MoE 辅助损失（M08）；dense 时 aux 恒 0
return loss, {"train/loss": out.loss.item(), ...}     # 引擎接口：(损失张量, 日志字典)

注意损失不是这里"算"的——模型 forward 收到 labels 就顺手算好移位交叉熵（M09）， 闭包只做一次加法（把 MoE 的负载均衡辅助损失加上，dense 模型加 0）。 ③ 交棒（25–37 行）：把四件与闭包塞进 Trainer，声明 save_weight="pretrain" （决定产物名，一会儿讲），然后 trainer.run()——从这一行起，循环、lr、AMP、裁剪、 评估、保存全是 M13/M14 引擎的事，母版再没出现过一行训练逻辑。

同构之美：SFT 母版只改三处

init_from：两棒的交接棒

两棒怎么接？看 64M 的两份配方（tiny 冒烟版结构相同，尺寸更小）：

configs/sft_64m.yaml · 全文yaml
# 64M 全参数 SFT（基于 pretrain 权重）
stage: sft
data:
  dataset: sft_t2t_mini            # 差异①在配方侧的入口：语料换 sft
  max_seq_len: 768
  eval_ratio: 0.005
  num_workers: 8
train:
  epochs: 2
  batch_size: 16
  gradient_accumulation_steps: 1
  learning_rate: 1.0e-5    # SFT 用小 lr 防灾难性遗忘（官方推荐）
  dtype: bf16
  init_from: pretrain      # 严格加载 pretrain 产物  ← 交接棒就这一个键
  save_interval_steps: 500
  log_interval: 50

init_from: pretrain 走的是 M14 讲过的初始化三语义里的"严格起点"： Trainer 构造时（trainer.py:432）把它交给 resolve_weight_path("pretrain", out, 768, False)， 按命名约定 {权重名}_{hidden_size}.pth 解析成 out/pretrain_768.pth， 再 load_inference_weights(..., strict=True)——键集合必须完全相等，否则启动前一秒就炸。 两处小字值得念出声：lr 从 5e-4 降到 1e-5（50 倍）——SFT 是在已训好的权重上"精修"， 大步长会把 pretrain 学到的东西震掉（灾难性遗忘：旧技能被新任务的梯度冲刷掉）； tiny 冒烟配方里 init_from: null——从零训，等下我们会看到从零 SFT 的 loss 长什么样。

🏭 工业对照：两段式是全行业的默认形状

pretrain（海量无标注文本，学语言本身）→ SFT（少量指令-回答对，学"当助手"）这个顺序不是 minimind 的发明：GPT-3 论文把两段分别叫 pretraining 与 fine-tuning，InstructGPT 把后者细化为 SFT + RLHF。分工的经济学在于：pretrain 吃 几十亿到万亿 token、算力以 GPU 月计， 只能少数机构做；SFT 吃 几万到几百万条对话、几小时到几天，人人做得起—— 所以"基座 + 对齐"的市场才会分成两层。你今天用 0.53M 参数走完同一形状的两棒。

[作者实测 · 同上 · 困惑度由 e^loss 换算] 困惑度（perplexity，PPL）：把每个位置"平均在多少个候选词里犹豫"折算成的等效词数： $ \mathrm{PPL} = e^{\mathcal{L}} $，乱猜时 $e^{\log 6400}=6400$； e^7.88 ≈ 2653 即"仍在大海捞针，但针的位置已经摸到一点"。

诚实的第一课：只降了 0.85。从 8.76 到 7.88，这点进步是什么？算一笔"阅读量"： 200 个 micro step × 4 句 × 96 token = 76,800 个 token，按 M10 的例子（5 字≈3 token）粗算 约 11 万汉字——一本薄书。用一本书学一门语言，能学到的只有词频： 哪个字常见（"的""了""是"）、哪些字符组合根本不是汉语。 这 0.85 nat（nat：以自然对数计的损失单位，降 1 nat = 困惑度除以 e ≈ 2.72）恰好就是"从均匀乱猜修正到高频词优先"的信息量。

💡 直觉：loss 的下限是语料本身的不可预测性

训练 loss 不可能降到 0：语料本身有随机性——下一个词有时连人也猜不准（人名、数字、转折）。 这个不可预测性的度量叫熵（entropy，交叉熵的下界，M01 见过交叉熵）。模型能做的是 无限逼近"给定完美上下文时语料的条件熵"，64M 全程降到 1.66（PPL ≈ 5.3）已接近这套迷你语料的地板； 工业大模型在万亿语料上通常落在 1.x～2.x。读曲线时先问自己：地板在哪，再判断模型离地板多远。

⚠️ 坑卡：载入 tiny 权重做验证，build() 报 q_norm size mismatch
  • 训练完想生成验证，顺手写 MiniMindLLM.build("pretrain", hidden_size=64, num_hidden_layers=2)—— 炸：size mismatch for model.layers.0.self_attn.q_norm.weight，checkpoint 是 (16,)、 你建的模型是 (8,)。作者实测今天原样踩中。
  • M02 埋过的坑：build() 只暴露 hidden/层数两个形状参数，头数用 768 系默认 （8 头/4 KV 头）；而 tiny 配方是 4 头/2 KV 头——头数决定 head_dim（64÷8=8 vs 64÷4=16）， q_norm/k_norm 的形状跟着 head_dim 走，于是对不上。
  • 别手填头数，喂结构快照：build(weight, config_path="runs/<recipe>/<时间戳>/config.json") ——每个 run 目录的 config.json（M13 四件套之一）存着训练时的全量模型结构，build 会按快照建模型 （跨源一致性：结构以训练时为准，而不是以你记忆为准）。M02 的裸构造器路线也能走通，快照路线一步到位。

loss 曲线读法：三段式

这条形状不是 minimind 特产——几乎所有语言模型的预训练曲线都长这样，只是刻度不同。 本课第一个新概念：预训练动力学，即 loss 随步数的下降规律。读法三段：

阶段本档区间loss 在降什么
① 垂直下跌8.13 → 6.1（前 500 步）词频：哪些 token 高频。梯度最大、学得最快——unigram 统计（单字频率表）几步就能拟合，tiny 的 200 步全程都在这一段
② 快速变缓6.1 → 2.4（500 → 8000 步）局部结构：固定搭配与相邻依赖（"北京"后面常是"市"）。信息量比词频大一个量级，但仍是局部统计
③ 长平台2.4 → 1.66（8000 步 → 26 万步）长尾：句法、语义、事实——每降 0.1 nat 都要海量数据与参数。这段占了总时长 95%，也是"大模型为什么贵"的曲线形态

val 与 train 的关系在存档里也有一课：pretrain_full 的 val（1.53）反而低于 train（1.66）。 两个原因：日志里的 train loss 是"过去 50 步的窗口均值"，而模型还在下降通道里（评估时模型比窗口内的大部分时刻更强）； 验证集又是语料尾部固定 50 batch，分布略偏简单。方向健康——两边同降、无分叉。 什么时候要警惕？看 SFT 的曲线。

现在你能从训练侧解释这张表了——这正是本课第二个新概念：SFT 行为跃迁。 pretrain 的损失对每个位置记账（M09：labels 就是 input_ids），模型学的是"文字接龙"这一件事， 语料里混着的 chat 文本只教会它"表格词常出现"，于是拿着对话模板它只会把见过的表格词一个个填下去。 SFT 换了两个东西：数据变成（用户问题，助手回答）对；账本被 M12 的 loss mask 改成 只对助手回答区间记账。成千上万个 optimizer step 之后，梯度只强化一件事—— 在 assistant 标记之后，以助手身份把回答说完。行为跃迁不是涌现的魔法，是账本改了、 模型跟着账本学的必然。第三行"万物复苏"与第一行"天气开始变暖"用的是同一套 pretrain 语言知识， 差别只在"以什么身份接下文"。

检验一下

测验 1 · SFT 为什么用 pretrain 权重当起点，而不是从零训？用两组数字回答

答案：从零 SFT 意味着用几万条对话同时学"语言"和"当助手"两件事，前者根本学不动。数字：64M 链式 SFT 起点即 1.94（pretrain 的语言知识第一 step 就在场），从零则是 8.8 起步——差近 7 个 nat；tiny 上同款实验（从零 8.61 → 7.27 vs 链式 8.43 → 7.23）差距缩小到 0.2 nat，因为 tiny 的 pretrain 本身只学到词频。另外 SFT 还配 1e-5 的小 lr（pretrain 的 1/50）：起点是训好的权重，大步长会把旧知识震掉（灾难性遗忘）。

答错回看：init_from：两棒的交接棒 与 sft_full 曲线。

测验 2 · loss 曲线的三段各在学什么？平台期是"训练失败"吗？

答案：三段：①垂直下跌学词频（unigram 统计，几步就拟合完）；②快速变缓学局部结构（搭配、相邻依赖）；③长平台学长尾（句法、语义、事实）——信息越深越难挖，每 0.1 nat 都要海量数据。平台期不是失败，是第三段的常态（pretrain_full 用 95% 的时长走它）；真正的失败信号是曲线不动（lr/数据/实现有 bug）或回升（发散）。另外 loss 有下界——语料本身的条件熵，64M 的 1.66 已接近这套迷你语料的地板。

答错回看：loss 曲线读法 与 直觉卡。

测验 3 · tiny 与 64M 的曲线形状有什么异同？tiny 的 0.85 nat 学到了什么、没学到什么？

答案：同：都是"先快后慢"的凹形——预训练动力学不因规模改变。异：tiny 只走完第一段（7.7 万 token 阅读量，学的全是词频）；64M 走完三段（32 亿 token，压到 1.66）。tiny 学到的是"哪些字高频、短前缀后该停"（生成上表现为只会吐高频字然后 EOS）；没学到的是局部结构以上的东西——通顺的续写属于第二段以后。规模买到的不是新的学习规律，而是走得更远的资格。

答错回看：对照表 与 tiny 实战。

测验 4 · sft_full 的 train 降到 1.32、val 钉在 1.96——这个分叉说明什么？和 pretrain_full（val 1.53 < train 1.66）方向相反又是为什么？

答案：SFT 的分叉 = 过拟合信号：train 一路降而 val 不降，模型在记忆训练集的回答（背答案），不是在学泛化的对话能力——SFT 数据相对模型小，两个 epoch 就到临界。pretrain_full 方向相反（val 略低于 train）且两边同降无分叉，属于健康：train loss 是过去 50 步的窗口均值（模型还在下降通道），val 集又是尾部固定 50 batch 略偏简单。判断健康与否看的不是谁高谁低，而是两者是否同向收敛。

答错回看：sft_full：起点不是 8.8。

两棒走完，你的模型会"以助手身份说话"了——但它没有偏好：同一个问题的两个回答， 在它眼里一样"像标准答案"，因为 SFT 的损失只会模仿，不会比较。M17 装上那把尺子： DPO，让模型在两个回答里学会挑更好的那个。

本课词汇

预训练动力学 pretraining dynamics
loss 随步数下降的三段规律：垂直下跌（学词频/unigram 统计）→ 快速变缓（学局部搭配）→ 长平台（学句法语法的长尾，占 95% 时长）。形状不随规模改变，规模决定能走到第几段。
SFT 行为跃迁 behavior shift
SFT 前后模型行为的质变：基座只会文字接龙（拿对话模板只会堆模板词），SFT 后学会"在 assistant 标记后以助手身份回答"。机制是 M12 的 loss mask 把账本改到只记回答区间——不是涌现，是账本改了、模型跟着账本学。
困惑度 perplexity, PPL
交叉熵损失的指数换算 e^loss：等效"每个位置在多少个候选词里犹豫"。乱猜 = 词表 6400；64M 全程终点 1.66 → PPL ≈ 5.3。曲线读数的直观化单位。
母版 workflow recipe workflow
范式侧的薄组装层：pretrain 37 行 / SFT 49 行，正文只做"组装四件 + compute_loss 闭包 + 交棒 Trainer"。M13 docstring"范式只提供 compute_loss"的实体。
init_from 严格起点
训练侧三语义之一（M14）：按 {名}_{hidden}.pth 约定解析路径、strict=True 载入，结构必须完全一致。sft_64m.yaml 的 init_from: pretrain 就是两棒交接棒；配套小 lr（1e-5）防灾难性遗忘。
过拟合 overfitting
train loss 降而 val loss 不降的分叉状态：模型在记忆训练集（背答案）而非学习泛化能力。sft_full 两 epoch 后 train 1.32 / val 1.96 即此信号；判断标准是两者是否同向收敛（M13 的 val 语义）。
灾难性遗忘 catastrophic forgetting
在已训好的权重上用大 lr 继续训新任务，旧技能被新梯度冲刷掉。SFT 把 lr 降到 pretrain 的 1/50 就是为它；"严格起点 + 小步长"是微调的标准姿势。
熵 entropy
语料本身不可预测性的度量，交叉熵（训练 loss）的下界。模型永远降不到 0——读曲线先问"地板在哪"，再判断模型离地板多远。
