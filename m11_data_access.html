数据访问层：registry 与字节偏移索引

姿势一次性成本常驻内存随机取一行
A 全量预载进 list3.23s（全量 json 解析）+1317MB0.69µs（已在内存，最快）
B 顺序扫描不预载无≈021ms（第 10 万行）~ 379ms（近文件尾）
C 字节偏移索引0.47s（只数偏移不解析）+52MB6.5µs（1000 次平均）

读表三句话：A 不慢，是贵——1.3GB 常驻内存，且它随文件大小线性涨；全量 SFT 语料是 14GB， 预载就是 15GB 上下的常驻，还只是一个进程的份——M15 的 DDP（分布式数据并行，多张卡各开一个进程各自喂数据）每个进程都要背上这样一份。 B 省，但每取一行都是 O(N)（耗时随行数线性增长）——训练一个 epoch 要随机取上百万次，直接判死刑。 C 用 0.47s 的一次性扫描 + 52MB 常驻，把每次取样压到微秒级：内存与文件大小近似解耦。 14GB 的 sft_t2t.jsonl 实测同款索引：5,109,432 行、构建 7.2s、净增 265MB——文件大 11 倍，索引只大 5 倍。

💡 直觉：索引把"随文件增长的成本"从每次取样挪到了启动一次

A 把成本付在内存（线性于文件大小），B 把成本付在每次访问（线性于行位置），C 把成本付在启动时的 一次扫描。训练恰恰是一个"启动一次、随机访问亿次"的负载，所以 C 的成本结构对它完美贴合。 同款思路你其实见过：M06 的 KV cache 把"每步重新算历史"变成"预分配一次、增量写"——都是把重复成本 换成一次性预付。C 的取样（6.5µs）比 A（0.69µs）慢 10 倍，但两者都在微秒级，真正的瓶颈在后面的 tokenize（毫秒级）——省下的 1.3GB 内存是纯赚。

src/minimind_reborn/data/registry.py · resolve_datasetpython
@dataclass(frozen=True)
class DatasetEntry:
    name: str
    file: str
    kind: str  # pretrain | sft | dpo | rlaif | agent
    description: str

def resolve_dataset(name: str, data_root: Path | None = None) -> DatasetEntry:
    """注册表名 → 条目；本地文件缺失时报三要素错误。"""
    if name not in _REGISTRY:
        raise ValueError(                                    # 错误路径一：名字没登记
            f"数据集 '{name}' 未注册。已注册：{sorted(_REGISTRY)}。"
            f"新增数据集请在 {Path(_REGISTRY_FILE)} 中声明（名称/文件名/kind），不要散落硬编码路径"
        )
    entry = _REGISTRY[name]
    path = (data_root or envs.data_root()) / entry.file      # 数据根目录：envs.py 单一来源
    if not path.exists():
        raise FileNotFoundError(                             # 错误路径二：登记了但文件缺
            f"数据集文件不存在：{path}（注册名 '{name}'）。"
            f"请检查 MINIMIND_REBORN_DATA_ROOT 或运行 tools/download_data.py --name {name} 从 modelscope 下载"
        )
    return entry

为什么是声明式 JSON，不是 if-else

同一个需求两种写法，差距在"变更成本"与"错误质量"上：

  • 加数据集不改代码：声明式加一个 JSON 条目就完事；if-else 要改源码、过 review、重新发版。M11 之后你想接自己的语料，只需要注册一个新条目；
  • 报错能开出"已注册名单"：sorted(_REGISTRY) 直接打印——清单是数据，机器读得出来；散在 if-else 里的名字，报错只能写死提示文案；
  • 同一份清单被两处复用：tools/download_data.py 的 --name 参数用 choices=sorted(_REGISTRY) 自动获得合法名单与 tab 补全——下载器与解析器不可能对不上；训练侧的组装点 training/common/setup.py 的 build_lm_dataset 也从 resolve_dataset 拿路径；
  • kind 字段是 M12 的路标：五种取值 pretrain / sft / dpo / rlaif / agent 各对应一个 Dataset 类（派发：按 kind 把数据送到对应的类去构建），下一课逐一解剖——本课只需要知道 kind 声明"数据的形状"。

这与 M04 "配置即实验"是同一个哲学的两半：M04 把超参数从代码搬进 YAML，本课把资源描述从代码搬进 JSON （registry.py 的 docstring 引用的 project-structure §4："数据描述的资源走配置文件"）。代码只保留"怎么拿"的逻辑。

字节偏移索引：O(N) 建一次，O(1) 取任意行

现在拆姿势 C 的主角。字节偏移（byte offset）指某行第一个字节在整个文件里的位置编号（第 0 行的偏移是 0， 第 1 行的偏移 = 第 0 行的字节长度，依此类推）。字节偏移索引 = 把每行的起点偏移存成一个整数数组。 原理一句话：建索引时 O(N) 扫一遍文件，把每行起点记下来；取行时 seek（把文件读写指针直接拨到第 N 个字节的系统调用， 成本与拨多远无关）到该行起点，读到换行符为止——不用扫前面的任何字节： 

磁盘上的 jsonl（字节流）                     内存里的索引 self._offsets
 0        ┌ {"text": "给我生成一首诗…"}\n     行 0
 977      │ {"text": "按照这件衣服…"}\n       行 1      [0, 977, 1988, …]
 1988     │ {"text": …}\n                    行 2       ↑ 只有整数，约 40B/行
 …        └ … 共 1,270,238 行 / 1.24GB                  数据一个字节不进内存

load_line(1) = open → seek(977) → readline → json.loads   ← 跳过前 977 字节，只读这一行

精读：__init__ 数偏移，load_line 跳着读

src/minimind_reborn/data/datasets.py · JsonlIndexedDataset（节选）python
class JsonlIndexedDataset(Dataset):
    """jsonl 基类：构建字节偏移索引，__getitem__ 零拷贝 seek+read。

    内存占用与文件大小无关（只存每行偏移），替代 HF datasets 的内存映射方案。
    """

    def __init__(self, path: str | Path):
        self.path = Path(path)
        self._offsets: list[int] = []
        with self.path.open("rb") as f:       # "rb" 按字节读：偏移才是真实文件位置
            offset = 0
            for line in f:
                if line.strip():              # 空行不占索引位（行号只数非空行）
                    self._offsets.append(offset)
                offset += len(line)           # 原始字节数（含 \n；CRLF 文件连 \r 一起计）
        if not self._offsets:
            raise ValueError(f"数据集为空：{self.path}（检查文件内容或注册表映射）")

    def __len__(self) -> int:
        return len(self._offsets)

    def load_line(self, index: int) -> dict:
        with self.path.open("rb") as f:       # 每次独立 open：跨 DataLoader worker 安全
            f.seek(self._offsets[index])      # 指针拨到该行第 0 个字节
            return json.loads(f.readline())   # 只读这一行到换行符，再解析

六个值得停一拍的细节：

  • 构建时只数长度、不解析 json：0.47s vs 全量解析的 3.23s——json.loads 是这条流水线上最贵的一步，建索引刻意跳过它（解析推迟到真正取样时，且只解析被取的那行）；
  • "rb" 二进制模式是正确性的根：文本模式读 Windows 换行 CRLF 文件时，Python 会把 \r\n 悄悄换成 \n，len() 就不再等于文件真实字节数，偏移全错。二进制模式读什么是什么，len(line) 恒等于该行占用的字节数——换行符差异被"按字节计数"天然免疫。实测一个 CRLF + 空行混排的文件：3 行非空正确还原、空行跳过（len=3）；
  • 空行跳过但不留洞：if line.strip() 保证空行不占行号，索引永远是"非空行号 → 偏移"；
  • 每次 load_line 独立 open：open+seek+readline+close 一套实测 6.5µs，比常驻句柄慢一点，但换来自由——DataLoader 的多个 worker 进程（M13）各自持有文件句柄互不干扰，不用管句柄生命周期；
  • 负索引是 Python 语义，不是 bug 也不是防御：ds.load_line(-1) 走 self._offsets[-1] 静默返回最后一行（实测）。DataLoader 只会用 0..len-1 的合法下标，所以无碍——但手写循环时别指望它报错拦你；
  • subclasses 只需实现 encode：五个 Dataset 类（M12）全部继承它，"怎么读一行"只写这一遍，"读来干什么"各家各写。

账本与取舍：索引为什么不落盘

实测账本：1.24GB / 1,270,238 行 → 索引净增 52MB；14GB / 5,109,432 行 → 净增 265MB。账面上每行一个 Python 整数对象约 28~32 字节加列表槽位 8 字节，1,270,238 × ~36B ≈ 46MB，与实测 52MB 对得上（差值是列表扩容余量）。 顺带交代选型：这套自研索引替代的是 HF datasets 的内存映射方案——datasets.py 模块头的理由是"加载 JSONL 不值一个 2GB 的传递依赖"（依赖准入：能标准库解决的不引重型框架）。一个反直觉的决定藏在对比里：偏移索引每次进程启动都重扫（0.47s / 7.2s），不写任何缓存文件——因为重建太便宜； 而 manifest（下一节）要解析全量 json、重扫 14GB 得十多分钟，所以它落盘成旁车。缓存与否是重建成本的函数，不是信仰。

[作者实测 · 2026-09-30 · 纯 CPU 路径] 52MB / 265MB 均为进程内净增值（ru_maxrss 前后差）；14GB 扫描 7.2s 为页缓存热时的数字，冷盘首读会更久。工具侧同款技巧：tools/len_profile.py 与 tools/data_profile.py（数据画像：量长度分布/重复率/语言构成）做随机采样时同样按字节偏移取行，注释原话"避免头部偏差"。

SegmentView / IndexListView：切分是视图，不是复制

有了索引，train/eval 切分（拿一小部分数据当验证集，训练时不碰它——用来观测过拟合：模型把训练集背下来、在新数据上反而变差的现象）就成了一个纯逻辑问题。 最笨的做法是把行拷成两份新 Dataset——reborn 的做法是两张视图：M06 讲过 view vs copy（read() 返回零拷贝前缀视图，"递指针不搬数据"），同一思想搬到 Dataset 层：

src/minimind_reborn/data/datasets.py · 两个视图类python
class SegmentView(Dataset):
    """数据集的连续段视图（train 段 / eval 段）：复用底层字节索引，不复制数据。"""

    def __init__(self, base: JsonlIndexedDataset, start: int, stop: int):
        self._base = base                # 底层引用：不搬数据，索引仍只有一份
        self._start, self._stop = start, stop

    def __len__(self) -> int:
        return self._stop - self._start

    def __getitem__(self, index: int):
        return self._base.encode(self._start + index)   # 视图内第 i 行 = 底层第 start+i 行

class IndexListView(Dataset):
    """行索引子集视图（哈希分桶的 train/eval 各一）：复用底层字节索引，零数据复制。"""

    def __init__(self, base, indices: list[int], *, filter_zero_loss: bool = False):
        self._base = base                # 同一个底层
        self._indices = list(indices)    # 只存行号数组——重复的也是行号不是数据
        ...

    def __getitem__(self, index: int):
        pos = index % len(self._indices)
        return self._base.encode(self._indices[pos])    # 行号 → 底层 O(1) 取行

两张视图各管一种切法：SegmentView 是连续段（pretrain 用：文件已打散时直接取尾部固定切片当 eval， _tail_split 保证可复现）；IndexListView 是任意行号集合（SFT 用：按内容哈希分桶选行， 下一节讲为什么）。真跑一遍（/tmp/m11_registry.py 的后半）：

manifest 一节：稳定哈希、分桶与旁车指纹

SFT 的切分比 pretrain 讲究：要做回复去重和按内容切分，就得先知道每行的"回复规范化哈希"和"消息数"—— 这需要解析全量 json（14GB 十多分钟），不能每次启动都付。manifest.py 的方案：扫一次，把每行的派生信息存成"旁车文件"（sidecar：与数据文件同名、多一个后缀的伴生缓存） ——sft_t2t_mini.jsonl.manifest.npz（npz：numpy 的压缩存档格式）。三件设计各防一件事：

  • 稳定哈希防跨进程漂移：stable_hash 用 md5（一种摘要哈希：任意长度输入 → 定长指纹，快且确定）， 而不是 Python 内置 hash()——后者被 PYTHONHASHSEED 环境变量加盐，每个进程的值都不一样： 
    $ python3 -c 'print(hash("你好"))'; python3 -c 'print(hash("你好"))'
-1270350379663970142
142117065527604372
    用了它，昨天建的 manifest 今天读进来哈希全对不上。stable_hash('你好') = -2771627962067793282 则跨进程跨机器恒定 （注意 md5 在这里只当"稳定的指纹"用，不做加密——"md5 被破解"指的是碰撞攻击，对分桶/去重无威胁；快和稳定才是要的）。
  • 哈希分桶防 eval 泄漏：切分不掷骰子，而是 stable_hash(整行规范化文本) % 1000 < bucket_take 进 eval （eval_ratio=0.005 → bucket_take=5，即 5‰）。同一行内容的哈希固定，所以永远落同一侧。对比随机切分两宗罪： ① 每次重跑切分结果都变，eval 指标不可比；② 换数据集重训时，训练见过的行可能混进新 eval—— eval 泄漏（验证集混入训练样本），指标虚高，你以为什么都没发生过。
  • mtime+size 指纹防旁车脏读：旁车必须知道"数据文件变没变"。_fingerprint 返回 f"{st.st_mtime_ns}:{st.st_size}"（修改时间戳纳秒值 : 文件字节数），存进 npz；加载时不匹配就全量重建 （写入走 tmp+rename 原子替换：先写临时文件、再一步改名顶替，中途崩溃也留不下半个文件——同款手法 M14 在 checkpoint 里详讲）。真实旁车实测： 指纹 1788969816217196132:1739201170，冒号后半恰是 sft_t2t_mini.jsonl 的字节数。
src/minimind_reborn/data/manifest.py · 两处关键逻辑（节选）python
def stable_hash(text: str) -> int:
    # signed=True：落在 int64 范围内（npz 存 int64 数组）
    return int.from_bytes(hashlib.md5(text.encode("utf-8")).digest()[:8], "little", signed=True)

_BUCKET_MOD = 1000  # 哈希分桶粒度：eval_ratio=0.003 → 命中 [0,3) 进 eval

# 建清单时逐行判定归属（与文件顺序无关，与随机数无关）：
is_eval_flags.append(stable_hash(normalize_text(text)) % _BUCKET_MOD < bucket_take)

def _fingerprint(path: Path) -> str:
    st = path.stat()
    return f"{st.st_mtime_ns}:{st.st_size}"   # 修改时间(纳秒):字节数，便宜且够用

坑卡：改了 eval_ratio 却"不生效"

⚠️ 坑卡：旁车的缓存键里没有 eval_ratio——同文件换口径，静默用旧切分
  • 症状极隐蔽：你把配方里的 eval_ratio 从 0.001 改成 0.005，重跑训练——eval 集大小纹丝不动， 指标"看起来正常"，只是验证集比配置小了 5 倍，过拟合观测的分辨率悄悄打折。不报错、不告警。
  • load_or_build 的缓存命中只看指纹 mtime_ns:size，不含构建参数；而 is_eval 列在建清单时就把"eval_ratio=多少"烘进了数值里。恰好仓库里有两个配方共用同一份数据文件： configs/smoke/smoke_sft.yaml（sft_t2t_mini，eval_ratio 0.001）与 configs/sft_64m.yaml（sft_t2t_mini，eval_ratio 0.005）——谁先把旁车建了，另一个就静默沿用它的切分。 作者机器上的真实旁车就是 smoke 建的（证据见下方实测）。

检验一下

测验 1 · seek+偏移为什么能做到 O(1) 取行？它依赖哪两个前提？

答案：前提① 文件系统支持随机访问——seek 把读写指针拨到任意字节位置，成本与拨多远无关（不需要"经过"前面的数据）；前提② 每行起点的字节偏移在建索引时已经量好（O(N) 扫一遍存成整数数组）。于是取第 i 行 = 寻址 offsets[i] + 读到换行符，代价只与该行自身长度有关，与文件总大小无关——实测 6.5µs/次，顺序扫描同一行 21ms。若任一前提不成立（比如没有索引、或介质只能顺序读），O(1) 立刻塌回 O(N)。

答错回看：字节偏移索引原理图 与 __init__ / load_line 精读。

测验 2 · SegmentView 为什么省内存？它和 M06 的 read() 有什么共同点？

答案：视图只持有两样东西：底层 Dataset 的引用 + 一个起止区间（SegmentView）或行号数组（IndexListView），__getitem__ 是纯转发——数据仍在磁盘、字节索引仍只有一份，切 train/eval 不复制一个字节（实测建两张视图后峰值内存不变）。与 M06 read() 返回零拷贝前缀视图同理："递指针，不搬数据"——区别只在 M06 切的是张量维度、本课切的是行号空间。反例是 copy：若切分靠拷出行数据，14GB 语料切一次就是一次全量读+写。

答错回看：SegmentView / IndexListView。

测验 3 · 哈希分桶切分防的是什么？随机切分错在哪？

答案：防 eval 泄漏与切分漂移。同一行内容的稳定哈希固定，% 1000 落进哪个桶永远不变——所以"同一条数据永远落同一侧"。随机切分两宗罪：① 每次重跑掷一次骰子，eval 集成员变了，两次实验的指标不可比；② 换数据集/重排文件重训时，训练见过的行会混进新的 eval 集——模型"考了自己做过的题"，指标虚高且你无从察觉。哈希分桶把切分变成内容的确定函数，重跑、换机器、改行序都不影响归属。

答错回看：manifest 一节。

测验 4 · stable_hash 为什么用 md5 而不是内置 hash()？"md5 不安全"影响这里吗？

答案：内置 hash() 受 PYTHONHASHSEED 盐值影响，跨进程不稳定（实测两个进程对"你好"给出 -1270350379663970142 与 142117065527604372）——今天建的 manifest 明天读不回同一个桶。md5 是摘要哈希：确定的（跨进程跨机器同值）、快的、指纹定长的，正合"去重键 + 分桶"之需。"md5 被破解"指攻击者能构造碰撞（两串不同内容同指纹）——分桶与去重场景没有对抗者，不构成威胁；若做完整性校验对抗场景才需要换 SHA-256 级别。

答错回看：manifest 一节。

FileNotFoundError（数据集文件不存在） → 数据未就位，回 M01 设 MINIMIND_REBORN_DATA_ROOT 或用 uv run python tools/download_data.py --name pretrain_t2t_mini 下载；行数与 wc -l 不一致 → 文件里有空行（索引跳过空行属正常语义，对照时也应跳过空行计数），或数据根目录指向了不同版本的文件； 索引不快（µs 级拿不到） → 确认是对同一文件的二次访问（首次含页缓存加载），且不是在网络盘/容器卷上跑； pytest 报 ModuleNotFoundError → 在仓库根目录执行且 uv sync --extra dev 已跑（M01）。

货架修好了：注册表让"按名字找文件"零硬编码，字节偏移索引让"随机取一行"从毫秒降到微秒、内存与文件大小解耦， 视图让切分零复制，manifest 让昂贵的全量扫描只付一次。但取回的还只是 {"text": …} 或 {"conversations": …} 的原始行——下一课把它们变成四种训练范式真正吃的样本：五个 Dataset 类同承一个地基， 以及全系统最脆的那根线——loss mask 怎么在渲染产物里逐 token 找到"该学的那段"。

本课词汇

数据注册表 registry
一张"名字 → 数据集描述"的清单，物理形态是 datasets.json（9 条目 × 四字段 name/file/kind/description）。声明式：只描述有什么，不含怎么拿的代码；resolve_dataset 是唯一解析入口。
声明式 declarative
用数据（JSON/YAML）描述"有什么"，而不是用代码写"怎么拿"。与 M04 配置即实验同源：加数据集 = 加条目，不改代码；报错能打印全量名单。
kind 数据集类别
注册表里声明数据形状的字段，五种取值 pretrain / sft / dpo / rlaif / agent，各派发到 M12 的一个 Dataset 类；下载器与训练组装点共用同一份清单。
字节偏移索引 byte-offset index
每行第一个字节在文件中位置编号的整数数组。O(N) 扫一遍文件建一次（只数长度不解析，1.24GB 实测 0.47s），__getitem__ 走 seek+readline 为 O(1)（6.5µs/次）；内存与文件大小近似解耦（52MB vs 265MB @1.2/14GB）。
seek 文件寻址
把文件读写指针直接拨到第 N 个字节的系统调用，成本与拨多远无关——随机访问的物理基础。二进制模式（rb）下偏移恒等于真实字节数，CRLF 换行差异天然免疫。
视图 view
只持底层引用 + 行号区间/数组、__getitem__ 纯转发的薄壳 Dataset（SegmentView / IndexListView），切分与上采样零数据复制——与 M06 零拷贝前缀视图同一思想（见 M06）。
旁车文件 sidecar / manifest
与数据文件同名、多一个 .manifest.npz 后缀的伴生缓存，存每行的派生信息（回复哈希/去重 keep/分桶 is_eval/消息数）。删了只会触发重建，无数据风险；是纯派生物。
指纹 fingerprint
mtime_ns:size（修改时间戳纳秒:文件字节数）拼成的缓存键——改一个字节（mtime 变）、追加内容（size 变）都会失效重建；漏网情形是保时戳同大小替换，是"检查成本 vs 脏读风险"的工程折中。
稳定哈希 stable hash
跨进程/跨机器取值恒定的哈希——md5 前 8 字节读 int64。内置 hash() 受 PYTHONHASHSEED 盐值影响每进程不同，不可用于落盘的清单。
哈希分桶 hash bucket
stable_hash(行内容) % 1000 < bucket_take 的确定性切分：同一行永远落同一侧，防 eval 泄漏（验证集混入训练样本致指标虚高）与重跑切分漂移。
