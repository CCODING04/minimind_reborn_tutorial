工程工具速查：CI、门禁与代码质量那些词

课程正文会顺口提到一些工程开发常用词——CI、pre-merge job、lint、mypy……它们不是 LLM 知识， 而是"代码怎么被工程化地写、验、发"的行业通用语。本页按"是什么 / 为什么需要 / 在 reborn 哪里" 三栏速查，供首次撞见时回来翻。

受众：工程经验不限（与课程 FAQ 一致） 用法：字典式，随查随走 姊妹篇：PyTorch 特殊用法指南

怎么用这一页

三种读法：① 正文撞见生词 → 回本页查那一行；② 通读一遍（约 15 分钟）， 建立"工程化 = 让机器替你验证"的世界观；③ 学完 M22 后回来对照—— 毕业实验里的"改数据→重训→复测"循环，本质就是一套手动 CI。

每个词只给三句话：是什么、为什么工业界离不开它、它在 reborn 或本课程里的对应物。 想深入的主题词都给了官方文档链接。

一、自动化验证：让机器替你说"没改坏"

术语是什么为什么需要在 reborn / 课程哪里
CI
持续集成
Continuous Integration		 代码一提交（push / PR），机器自动跑一遍构建 + 测试，红了立刻报警。 把"我以为没改坏"变成"机器证明没改坏"；越小的改动越容易定位是谁改坏的。 M01 工业卡里 make smoke 的定位就是"手动版 CI"；93 个单测是它的弹药库。
GitHub Actions
workflow		 GitHub 内置的 CI 引擎，用 .github/workflows/*.yml 声明"什么事件触发、跑哪些步骤"。 不用自建服务器，仓库在哪 CI 就在哪；YAML 即文档。 活例子：你正在看的这个课程站——每次 push 由 deploy-pages.yml 自动部署到 GitHub Pages（见本页最后一节）。
pre-merge job
合并门禁 / gate		 PR（拉取请求）合并进主分支之前必须通过的检查项；红了就拦下。 主分支永远可用——任何人的改动没过门禁就进不来。 M01 工业卡："改完代码跑冒烟"在工业界常挂进 CI 的 pre-merge job。
CD
持续部署
Continuous Deployment		 测试全绿后自动发布产物（部署站点、发包、推镜像）。 发布不再依赖"某个人的笔记本和手速"，过程可复现。 课程站的 Pages 自动部署就是最小编纂版 CD。
pytest marker
-m "not slow"		 给测试打标签（如 @pytest.mark.slow），运行时按标签挑子集。 冒烟要快（秒级）、全量要全（过夜），同一套测试两种吃法。 M01 工业卡：reborn 的冒烟等价于 CI 里跑 pytest -m "not slow" + 冒烟链路。
smoke test
冒烟测试		 用最小代价验证"整条链路能通"，而非"每一步都对"。 秒级可重复，所以你敢在每次改动后都跑。 M01 有完整概念卡（词源：电路板第一次通电先看冒不冒烟）；make smoke 全课要跑几十次。
回归测试
regression test		 每个 bug 修完，补一个"专门锁住它"的测试，防止将来复发。 修过的 bug 再犯是最贵的浪费；测试让修复永久生效。 bug 猎场的固定第四幕"回归锁定"；test_lr_schedule.py 就是一次真实回归（双卡余弦分母 bug）。

二、代码质量：机器审代码的三个层次

术语是什么为什么需要在 reborn / 课程哪里
Make / Makefile 把长命令固化成短目标（make smoke、make test）的任务编排器。 可记忆、可发现（敲 make 列出全部目标）、自文档化。 reborn 的 Makefile——M01 第一盏绿灯就是 make smoke。
lint / 风格检查
（reborn 用 ruff）		 不运行代码，机器审查格式与低级错误（未用变量、可疑写法）。 把" reviewers 反复挑格式"的人力解放出来，风格零争议。 reborn 的 ruff 全绿是 CI 口径之一；M20 的 cf46125 提交信息里可见"ruff 清零"。
类型检查
mypy		 不运行代码，静态证明"类型对不上"（把 int 传给了要 str 的地方）。 测试覆盖行为，静态检查覆盖名字存在性——测不到的分支它管。 M19 猎场：多卡分支测试进不去，mypy 静态揪出 PPO all_reduce 透传 bug。
pre-commit / git hooks 提交（commit）动作触发的本地自动检查钩子，常用来跑 lint。 问题在提交前就拦下，而不是等 CI 红了才返工。 reborn 未启用（规模还小）；工业仓库标配，值得知道。
PR / code review
拉取请求 / 代码评审		 改动先开一个 PR，别人看 diff、留意见、通过后合并。 机器门禁（CI）+ 人审（review）双保险；知识在团队里流动。 本课程仓库自身的修改周期就是按 PR/commit 组织的；bug 猎场里的 git show 正是在读评审素材。

三、工程基础：让"在我机器上能跑"变成"哪都能跑"

术语是什么为什么需要在 reborn / 课程哪里
依赖锁定
uv.lock / lockfile		 把"精确到补丁号的依赖版本清单"锁进一个文件，随仓库分发。 三个月后、别人机器上，uv sync 还原出一模一样的环境。 M01 的 uv sync + uv.lock；日志里的"环境指纹"是它的运行时镜像。
git 工作流
clone / commit / push		 分布式版本控制的最小集：取代码、存快照、传远端。 改动可回溯、可归因（谁在哪改了什么）、可并行。 M00 教最小集；M01 第 0 步的 git clone；bug 猎场的 git show <commit>。
版本号 / tag 给"某个确定的状态"起名字（v1.2.0 或权重文件名）。 "复现实验 X"的前提是能指认 X 到底是哪个状态。 reborn 权重命名 {name}_{hidden}.pth 就是朴素版本思想：模型、规模、来源一眼可辨。
可观测性
observability		 把系统内部状态（loss、吞吐、指纹）持续写出来，供事后回答"发生了什么"。 训练是黑盒长跑，没有日志就没有归因——出问题只能重炼。 课程主线内容本身：M13 可追溯四件套（config 快照 + 环境指纹 + train.log + metrics.jsonl）。
🏭 活例子：你正在看的这个课程站，就是一套最小 CI/CD

每次有人 git push 到课程仓库，GitHub 被 push 事件唤醒（GitHub Actions）， 按 .github/workflows/deploy-pages.yml 里声明的步骤构建站点并发布到 GitHub Pages（CD）。 全程无人值守——"人只负责写，机器负责验和发"。等学完 M22， 你会认出这正是课程反复训练的那套循环的自动化形态：改动 → 验证 → 发布。
