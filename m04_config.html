配置即实验：分域 schema 与守门人

从这一课起你开始"造"——而且你已经用过这套系统的产品：M01 跑的每个冒烟配方、M02 写的 GenerateConfig(temperature=…)，都是它的住户。造模型之前先造实验台： reborn 与官方 minimind 差异最大的一层不是某个算法，而是配置系统——分域 dataclass 做唯一事实源， YAML 配方只写差异，CLI 只管临时覆盖，守门人拦下所有非法组合。拼错一个 key？它在训练开始前一秒咬你。

前置：M01（M02/M03 建议完成——正文引用其细节） 时长：约 60 分钟 新概念：分域配置 schema · 守门人校验 对照：configuration/{schemas,loader}.py · configs/ · tests/test_configuration/test_loader.py

学完你能

  • 说出"配方即实验"的三条铁律（只写差异 / CLI 覆盖 / 未知 key 硬错），并解释各防什么事故；
  • 默写 dataclass 默认 → YAML → CLI 三层覆盖顺序，指出唯一守门人 validate_and_derive 在数据流中的位置；
  • 手算 hidden=768 的 head_dim=96 与 intermediate_size=2432，并解释派生参数为什么不进 YAML；
  • 亲手触发三类守门人报错（未知 key / GQA 不整除 / bool 类型不符），读懂报错自带的修复提示，并把 test_loader.py 的 10 个测试当回归锚点。

先被咬一口：拼错的 key 会怎样？

普通做法里，YAML 常用 dict.update(config) 式合并——它不核对你拼错的 key： 写了 max_step: 4（少了 s），合并器默默吞下，训练静默用默认 epochs=2 跑完， 三小时后你才对着"怎么没生效"的 loss 曲线排查。换 reborn 跑同一个错误，它不训练，当场翻脸： 

$ uv run python tools/train.py configs/smoke/smoke_pretrain.yaml --set train.max_step=4
Traceback (most recent call last):
  File ".../src/minimind_reborn/configuration/loader.py", line 113, in _apply_override
ValueError: 未知配置项 'train.max_step'。合法项：['batch_size', 'compile', 'deterministic', 'dtype', 'epochs', 'eval_interval_steps', 'finetune_from', 'grad_clip', 'gradient_accumulation_steps', 'init_from', 'learning_rate', 'log_interval', 'lr_min_ratio', 'max_steps', 'resume', 'save_interval_steps', 'seed', 'warmup_steps', 'weight_decay']

[作者实测 · 2026-09-29 · 2×RTX 4090 · torch 2.14.0+cu130] 报错发生在任何训练日志之前——模型未建、数据未碰；名单第 13 项就是正确拼法 max_steps。

这就是 fail-fast（快速失败）：把"三小时后曲线不对"兑换成"启动前一秒一条报错"。本课回答三问：报错谁抛的（装载器）、凭什么知道全部合法项（schema）、除拼写外还拦什么（守门人）。

两张概念卡：配方即实验 / 分域 schema

💡 概念卡：配方即实验

M01 埋过伏笔，这里展开成完整世界观：一个 YAML 文件 = 一个可复现实验，文件名即实验名。 pretrain_64m.yaml 不只是"配置"，而是"64M 预训练"这个实验的定义——任何人任何时候 拿着它在锁定环境里跑出的实验与你结构等价。三条铁律：① 只写差异——与默认相同的超参不写； ② CLI --set 只做临时覆盖——值得保留的差异应沉淀回配方；③ 未知 key 硬错。

📐 概念卡：分域 dataclass——超参的唯一事实源

reborn 把全部超参收进 configuration/schemas.py， 按变化原因切成 9 个域（一个类只因为一个原因修改——职责表见下节）。为什么用 dataclass 而不是散落的 dict？

  • 类型即文档：dropout: float = 0.0 一行说清名字、类型、默认值；
  • 默认值是唯一事实源：全仓库只此一处写默认值，配方与 CLI 都是"相对此处的差异"，永不漂移；
  • 可枚举即可校验：dataclasses.fields() 列出全部合法字段——上面报错的名单就是它打印的；
  • 哨兵表达"待派生"：head_dim: int | None = None 的 None 是"守门人稍后会填"。

精读 schemas.py：RunConfig 的组合结构

9 个域由顶层 RunConfig 组合，精简骨架（省略各域内部字段）：

src/minimind_reborn/configuration/schemas.pypython
STAGES = ("pretrain", "sft", "dpo", "distill", "lora", "grpo", "ppo", "agent")  # 共 8 个范式，stage 的合法值

@dataclass
class RunConfig:
    """一次实验的完整定义：配方文件（yaml）按域映射到这些字段。"""

    stage: str = "pretrain"
    recipe_name: str = "default"  # 实验名 = 配方文件名（指标曲线 ↔ 输出目录对齐）
    output_dir: str = ""       # 以下三目录均派生（哨兵 ""，守门人必填）：
    checkpoint_dir: str = ""  #   out_root() / checkpoint_root()
    run_dir: str = ""          #   run_root()/recipe_name/时间戳
    model: ModelConfig = field(default_factory=ModelConfig)  # 为什么不是 = ModelConfig()？可变默认值
    data: DataConfig = field(default_factory=DataConfig)    # 会被所有实例共享（Python 经典陷阱），
    train: TrainConfig = field(default_factory=TrainConfig)  # 工厂每次造新对象；其余六域同理
    metrics: MetricsConfig = field(default_factory=MetricsConfig)
    generate: GenerateConfig = field(default_factory=GenerateConfig)
    dpo: DPOConfig = field(default_factory=DPOConfig)
    distill: DistillConfig = field(default_factory=DistillConfig)
    lora: LoRAConfig = field(default_factory=LoRAConfig)
    rl: RLConfig = field(default_factory=RLConfig)

9 个域各管一段：

域管什么（变化原因）代表字段（默认值）
model模型结构（权重形状；resume 以 checkpoint 快照为准）hidden_size=768 · num_hidden_layers=8 · num_key_value_heads=4
data数据集与切分、评估比例dataset="pretrain_t2t_mini" · max_seq_len=340

收益在装载期兑现：YAML 顶层写 model:/train: 自然对齐到域， 一个范式的参数改动不可能弄脏另一个范式——官方脚本间复制粘贴的 dim/n_layers 在这里只剩一份。

活标本：16 行的 64M 配方

守门人算的两笔账：head_dim 与 intermediate_size

ModelConfig 有两个字段默认值是 None（哨兵）——它们不是超参，是派生参数： 由其他超参算出，写进 YAML 反而是隐患。推导发生在守门人里：

src/minimind_reborn/configuration/loader.py · validate_and_derive 节选python
# ---- 模型域派生（哨兵 → 推导值）----
m = cfg.model
m.head_dim = m.head_dim or m.hidden_size // m.num_attention_heads
m.intermediate_size = m.intermediate_size or math.ceil(m.hidden_size * math.pi / 64) * 64
m.moe_intermediate_size = m.moe_intermediate_size or m.intermediate_size
if m.num_attention_heads % m.num_key_value_heads != 0:   # GQA 约束先查
    raise ValueError(
        f"num_attention_heads({m.num_attention_heads}) 必须被 "
        f"num_key_value_heads({m.num_key_value_heads}) 整除（GQA 约束）"
    )
# 紧随其后还有第二条：hidden_size 必须被 num_attention_heads 整除（练习 2 会踩到）

第一笔账直白：head_dim = hidden_size // num_attention_heads，默认 768 // 8 = 96。 第二笔是官方 minimind 的经验公式——FFN 中间维取 hidden 的 π 倍，再向上取整到 64 的倍数（硬件对齐； SwiGLU 是 M08 要讲的门控前馈结构，比经典 FFN 多一个矩阵，参数量相当的量级是 8h/3，π 略高于此——作者推算，非官方声明）： $768 \times \pi \approx 2412.7 \Rightarrow \lceil 2412.7 / 64 \rceil = 38 \Rightarrow 38 \times 64 = $ 2432。真实命令核对： 

$ uv run python -c "import math; print(math.ceil(768*math.pi/64)*64)"
2432

[作者实测 · 2026-09-29] 同法核对三档：64→256、512→1664、768→2432；与 models/config.py 的 MiniMindConfig（同一公式独立实现）一致，512→1664 是 test_derived_fields 的断言值——公式、双实现、测试三方对得上。

派生参数为什么不写进 YAML？因为它是冗余信息：写进去就可能与其他超参自相矛盾 （hidden 改 512 而 intermediate 还是 2432——形状对不上，要拖到模型构建才爆，晚了好几拍）。 哨兵 None + 守门人统一推导，单一事实源连派生值都不例外。 随后两条整除校验——GQA 要求 query 头数是 kv 头数的整数倍（M07 讲头复用时你会知道为什么是硬约束）。 违反会怎样？真跑（64m 配方 8 头，设 3 个 kv 头）： 

$ uv run python tools/train.py configs/pretrain_64m.yaml --set model.num_key_value_heads=3
ValueError: num_attention_heads(8) 必须被 num_key_value_heads(3) 整除（GQA 约束）

[作者实测 · 2026-09-29] 报错里的两个数字就是当前配置的实际值——不查文档就知道该改哪边。

精读 loader.py：三层覆盖与唯一闸口

装载器 configuration/loader.py 只有一个入口 load_config(recipe, overrides)，内部是严格的三层覆盖——后到的胜出：

src/minimind_reborn/configuration/loader.py · load_config 核心三步python
def load_config(recipe: str | Path | None = None, overrides: list[str] | None = None) -> RunConfig:
    """唯一入口：默认值 → yaml → CLI 三层覆盖后过守门人。"""
    cfg = RunConfig()                          # ① 全部默认值就位（唯一事实源）
    if recipe is not None:
        ...
        mapping = yaml.safe_load(recipe_path.read_text(encoding="utf-8")) or {}
        _apply_dict(cfg, mapping, source=str(recipe_path))   # ② 配方差异覆盖默认
        cfg.recipe_name = recipe_path.stem     # 实验名 = 配方文件名（铁律）
    for override in overrides or []:
        _apply_override(cfg, override)           # ③ CLI 逐条覆盖（最后说话）
    return validate_and_derive(cfg)        # 出厂必过守门人（单闸口）

整条数据流——记住两个"一"：一个入口、一个闸口：

  configs/pretrain_64m.yaml              --set train.max_steps=10 --set model.hidden_size=512
  （配方：只写差异，沉淀复用）            （CLI：临时实验，不落盘，后到者胜）
             │                                        │
             ▼                                        ▼
┌──────────────────────── load_config() ─────────────────────────┐
│ ① RunConfig()         dataclass 默认值 = 全部超参唯一事实源      │
│ ② _apply_dict(yaml)   逐域合并；未知 key / 类型不符 → 硬报错    │
│ ③ _apply_override     解析 domain.field=value；同样硬报错       │
└──────────────────────────────┬─────────────────────────────────┘
                               ▼
            validate_and_derive()   ← 唯一守门人（单闸口）
            · stage ∈ STAGES（8 范式枚举）  · GQA / hidden 整除
            · dtype ∈ {fp32,bf16,fp16}     · 区间检查（accum≥1 等）
            · 派生 head_dim / intermediate / moe_intermediate_size
            · 派生 output_dir / checkpoint_dir / run_dir
                               ▼
     RunConfig ──► snapshot() 写入 run_dir/config.json（复现凭据）
              └──► tools/train.py 按 cfg.stage 分发到 8 个 workflow

入口侧，tools/train.py 是 60 行的薄入口， 逻辑就两行：cfg = load_config(args.recipe, args.overrides) 装配配置，再按 cfg.stage 用 importlib 分发到 8 个 workflow（每个 stage 一个薄入口，M16 读 pretrain/SFT 两个母版）。--set 用 action="append" 收集，可重复出现。

优先级谁来验证？test_yaml_then_cli_priority：YAML 写 batch_size: 16，CLI 再 --set train.batch_size=32，断言最终 32——CLI 胜；未被覆盖的 learning_rate 保持 YAML 的 1.0e-5。配置最后经 snapshot()（dataclasses.asdict）随 checkpoint 与 run_dir/config.json 落盘——只拿输出目录就能唯一重建实验，含派生值。

🏭 工业对照：配方思想的成熟形态

reborn 手写的三层覆盖 + dataclass schema，工业界有整族成熟工具：Hydra（配置组 + 命令行组合覆盖）、 jsonargparse（dataclass 直接变 CLI，类型校验免费）、MLflow（平台级记录每次运行的全部参数， 对应 reborn 的 snapshot → config.json）。共同内核与本课所见一致：声明式 schema + 分层覆盖 + 装配期校验 + 运行留档。reborn 用 200 行手写而非引框架，为的是零依赖保住这四件事——也让你能逐行读懂。

🔍 bug 猎场：bool CLI 覆盖失效（cf46125）

配置系统自己也会生病。素材来自 git 史，修复落在 commit cf46125（2026-09-24， 提交信息含"bool CLI 覆盖修复"）。

⚠️ 坑卡：小写 false 曾经过不了 CLI
  • 修复前，--set train.resume=false（CLI 习惯的小写）直接报错： ValueError: 配置项 train.resume 需要 bool，得到 'false'（str）——只有 Python 风格 False 能过。更阴险的平行宇宙：若没有类型断言，字符串 "false" 非空、恒为真值， 覆盖会"静默失效"、训练照常 resume（bool("false") == True，argparse 最经典的陷阱）。
  • CLI 边界上一切值先是字符串。装载器用 ast.literal_eval 还原类型，但它只认 Python 字面量 （大写 True/False）；小写 false 被拒后回落为字符串，撞上类型断言。实验看清： 
    $ uv run python -c "import ast; print(ast.literal_eval('False'), ast.literal_eval('0'))"
False 0
$ uv run python -c "import ast; ast.literal_eval('false')"
ValueError: malformed node or string on line 1: <ast.Name object at 0x76794a38cf90>
  • cf46125 在 literal_eval 之前先识别小写布尔字面量（修复 diff 节选，_apply_override 内）：
    git show cf46125 -- src/minimind_reborn/configuration/loader.py（节选）diff
    -    try:
-        value = ast.literal_eval(raw)
-    except (ValueError, SyntaxError):
-        value = raw  # 字符串字面量：交给类型断言拦下不匹配者
+    low = raw.strip().lower()
+    if low in ("true", "false"):
+        value = low == "true"  # CLI 习惯：小写布尔字面量
+    else:
+        ...  # 其余值仍走 literal_eval + 类型断言
    修复后真跑验证（M01 的 resume-by-default 正好当探针）：--set train.resume=false --set train.max_steps=2 从零训练 2 步、日志无"续训恢复清单"——小写 false 生效；--set train.resume=nope 仍被拦： ValueError: 配置项 train.resume 需要 bool，得到 'nope'（str）。

[作者实测 · 2026-09-29 · 2×RTX 4090] 症状与 diff 来自 git show cf46125（66 files changed, +1051/−375）；修复后两条行为为当日实测。

通用教训：CLI 边界永远是字符串——类型转换是配置系统的必修课。bool 有大小写陷阱；float 有 "0.001" 字符串陷阱（YAML 里要写数字字面量而非带引号字符串）；int 要防 bool 冒充（Python 里 bool 是 int 子类——见 _coerce_type 的 allow_bool=False 防线）。 也正是"未知 key 硬错 + 类型断言"两道闸，把这个坑从"静默错误"降级成"响亮的摩擦"——把错误提前到可解释的位置。

检验一下

测验 1 · 为什么未知 key 要硬报错，而不是打条警告继续跑？

答案：警告淹没在启动日志里，训练继续用默认值——你要到 loss 曲线不对劲才回头排查，代价小时级；硬错把发现时刻提前到启动前一秒，且自带合法项名单，修复秒级。fail-fast：错误越早暴露越便宜，配置期是全链路最便宜的暴露点（模型未建、数据未读、GPU 未占）。

答错回看：先被咬一口 的对比实验 + loader 精读 的闸口位置。

测验 2 · pretrain_64m.yaml 只有 16 行，hidden 768、8 层、学习率调度这些超参在哪？

答案：在 configuration/schemas.py 的 9 个分域 dataclass 默认值里——全部超参的唯一事实源。配方只写"与默认不同"的差异（16 行全是有意识的选择），CLI 只写临时差异：默认值管"一般情况"，配方管"这个实验特殊在哪"，CLI 管"这次临时试什么"。

答错回看：精读 schemas.py + 16 行配方活标本。

测验 3 · YAML 写 batch_size: 16，CLI 又 --set train.batch_size=32，最终生效几？还有哪层能再赢它们？

答案：32——CLI 后到胜 YAML，YAML 胜 dataclass 默认：顺序固定为 dataclass 默认 → YAML 配方 → CLI --set，后到者胜，由 test_yaml_then_cli_priority 锁定。另有两个"局外胜利者"不在覆盖链里：resume 时模型结构以 checkpoint 快照为准，run_dir 时间戳由守门人派生。

答错回看：loader 精读 的三步代码与数据流图。

测验 4 · head_dim=96、intermediate_size=2432 为什么不写进 pretrain_64m.yaml？

答案：它们是派生参数——由 hidden_size 等超参按公式算出，写进 YAML 就是冗余：改 hidden=512 而忘了改 intermediate，两份"事实"自相矛盾，错误要拖到模型构建才爆。schema 用 None 哨兵占位、守门人统一推导——换 hidden_size 时自动跟上（练习 1 亲眼可见）。

答错回看：守门人算的两笔账。

机制：输出目录用扁平命名 {权重名}_{hidden_size}.pth（MoE 再加 _moe 后缀），hidden 进文件名。 这是"配方即实验"的落地：模型宽度是实验身份的一部分——不同宽度的权重互不干扰， 下游 init_from: pretrain 也能按官方命名直接解析。派生参数自动跟上：head_dim 变 128、intermediate 变 1664。

🧪 变式 2 · 构造一个非法头数组合，守门人几时拦、报什么？

冒烟配方默认 hidden=64、heads=4、kv=2。现在把 query 头改成质数 7：

$ uv run python tools/train.py configs/smoke/smoke_pretrain.yaml --set model.num_attention_heads=7

写下预测：这个组合同时踩两条红线（7 不能被 kv=2 整除；hidden=64 也不能被 7 整除）。守门人先报哪条？在训练开始前还是后？

观察结果与解释（先动手再看）

作者实测（同环境）：

ValueError: num_attention_heads(7) 必须被 num_key_value_heads(2) 整除（GQA 约束）

机制：报错发生在 validate_and_derive——装配的最后一环，早于模型构建与数据加载。 先报 GQA 这条，因为守门人源码里 GQA 检查写在 hidden 整除检查之前：校验顺序就是代码顺序。 若把 kv 改成合法值（num_key_value_heads=1）再跑，下一条红线才现形： hidden_size(64) 必须被 num_attention_heads(7) 整除。为什么必须整除？M07 讲 GQA 头复用时揭晓——query 头要均分给 kv 头复用，除不尽就没有分组方案。

本课词汇

dataclass 分域 schema
按变化原因把超参切成 9 个 dataclass（一个类只因为一个原因修改），字段名+类型+默认值三合一，可被 fields() 枚举——校验的机器依据。
守门人 validator
唯一闸口 validate_and_derive：全部配置必经此处做合法性检查与派生推导。
fail-fast 快速失败
非法状态在装配期立刻硬错，而非带病运行后由症状倒查；错误越早暴露越便宜。
派生参数 derived parameter
由其他超参按公式计算的值（head_dim、intermediate_size、输出目录），不进配方、守门人统一推导；占位用 None/""/-1 哨兵。
覆盖顺序 override precedence
dataclass 默认 → YAML 配方 → CLI --set，后到者胜；由 test_yaml_then_cli_priority 锁定。
配置快照 config snapshot
snapshot() 把装配后的完整配置随 checkpoint 与 run_dir/config.json 落盘——只拿输出目录即可复现实验。
