一台引擎，八种范式

reborn 有八种训练范式（pretrain / SFT / DPO / 蒸馏 / LoRA / GRPO / PPO / Agent），但它们不各写一个训练循环。 循环、精度、梯度累积、裁剪、评估、保存——全部长在同一个类里： training/common/trainer.py 的模块 docstring 第一行就立了规矩："范式子包只提供 compute_loss(batch, model) -> (loss, log_metrics) 与数据组装。 梯度/AMP/裁剪/续训/评估/保存的顺序与不变量固定在此处，任何范式不得绕过。"

先看骨架，再逐段精读。epoch（轮）：把训练数据完整过一遍；一个 batch（批）：一次喂给模型的一组样本。 整个 run() 就是"epoch 循环 → 每 epoch 末评估 → 存档"三件事： 

Trainer.run() 生命周期（trainer.py:184）—— 所有八种范式共用这一台引擎
│
├─ try:
│   └─ for epoch in range(start_epoch, epochs)        ← 续训从存档的 epoch 接着数
│       ├─ _train_epoch(epoch)                        ← 微观循环（本课主角）
│       │   ├─ _build_loader：种子打乱 + SkipBatchSampler（续训对齐）
│       │   ├─ CUDAPrefetcher：CUDA 侧流预取（CPU 设备自动旁路）
│       │   └─ for batch in loader:                   ← 一个 micro step
│       │       ├─ get_lr(全局步) → 写回 optimizer 的 lr
│       │       ├─ autocast 里 compute_loss(batch, model)   ★范式唯一注入点
│       │       ├─ (loss/累积步数).backward()          ← 梯度累积：先记账不动手
│       │       ├─ 累积满：unscale_ → clip → step → zero_grad   ← optimizer step
│       │       └─ 每 log_interval 步：metrics.jsonl + train.log
│       ├─ evaluate()：固定 batch 算 val/loss（NaN batch 全过滤）
│       ├─ _save(is_best)：刷新最优另存 _best；常规存档带 checkpoint 六件套【M14】
│       └─ exhausted → break（max_steps 冒烟预算截断）
│
└─ finally: metrics.close() + 收尾总账（best_val_loss / optimizer_steps）
src/minimind_reborn/training/common/trainer.py · run 全文（日志参数裁剪）python
def run(self) -> None:
    logger.info("训练启动 stage=%s recipe=%s | %.2fM 可训练参数 | dtype=%s device=%s ...", ...)
    try:
        for epoch in range(self.start_epoch, cfg.train.epochs):   # 续训：从存档 epoch 接着数
            last_step, exhausted = self._train_epoch(epoch)       # 微观循环，见下节
            val = self.evaluate()                                  # 每 epoch 收官评估
            if val is not None:
                improved = self.best_val_loss is None or val < self.best_val_loss
                if improved:
                    self.best_val_loss = val
                    self._save(epoch, last_step, is_best=True)     # 刷新最优 → 另存 _best
            self._save(epoch, last_step)                           # 常规存档（六件套，M14 详拆）
            if exhausted:                                          # max_steps 截断：冒烟/调试预算
                break
    finally:
        self.metrics.close()                                       # 指标后端收尾（句柄必须关）
        logger.info("训练结束：best_val_loss=%s optimizer_steps=%d", ...)

M01 冒烟日志的最后一行你见过 训练结束：best_val_loss=8.7748… optimizer_steps=3—— 就是这行 finally 日志。best_val_loss（最优验证损失）驱动 _save(is_best=True)： 验证损失是"模型在没见过的数据上的表现"，比训练损失更能代表真实进步，所以最优权重按它另存一份。

micro step 与 optimizer step：训练的两种"步"

本课第一个关键区分。跑一个 batch 的前向+反向，是一个 micro step（微步）； 优化器真正更新一次参数，是一个 optimizer step。两者之间隔着梯度累积 （gradient accumulation）：显存装不下大 batch 时，把一个大 batch 切成 N 份逐份算， 每份只把损失除以 N 记进梯度（backward() 是累加进 .grad 的，不清零就不覆盖）， N 份攒齐才动一次参数——等效于大 batch 训练。 _train_epoch 的核心二十行把整台引擎的机械结构都装进去了：

src/minimind_reborn/training/common/trainer.py · _train_epoch 主循环（裁剪）python
for offset, batch in enumerate(data_iter, start=start_step):
    global_micro = epoch * full_iters + offset               # LR 调度用的全局 micro 步数
    lr = get_lr(global_micro, total_micro, t.learning_rate,
                warmup_steps=t.warmup_steps, min_ratio=t.lr_min_ratio)
    for group in self.optimizer.param_groups:                # 不用 scheduler 对象：
        group["lr"] = lr                                     #   直接把 lr 写回优化器

    batch = _to_device(batch, self.device)                   # (B, T) 整批搬卡（non_blocking）
    is_sync_step = (offset + 1) % t.gradient_accumulation_steps == 0 or is_last
    sync_ctx = nullcontext() if (no_sync is None or is_sync_step) else no_sync()
    with sync_ctx:                                           # DDP 梯度累积省通信【M15 详讲】
        with self.autocast_ctx:                              # bf16/fp16 才生效；fp32 是空上下文
            loss, log_metrics = self.compute_loss(batch, self.model)   # ★范式唯一注入点
        scaled = loss / t.gradient_accumulation_steps        # 累积：每份只记账 1/N
        self.scaler.scale(scaled).backward()

    if is_sync_step:                                         # 累积满（或最后一步）→ 优化步
        self.scaler.unscale_(self.optimizer)                 # 先还原真实梯度，裁剪阈值才有意义
        last_grad_norm = torch.nn.utils.clip_grad_norm_(params, t.grad_clip)
        self.scaler.step(self.optimizer)                     # bf16：直通 step；fp16：查 inf/nan 才放行
        self.scaler.update()
        self.optimizer.zero_grad(set_to_none=True)           # 引用置 None：省内存，不留僵尸梯度
        self.optimizer_steps += 1

三个"为什么"值得逐个过：① loss 为什么要除以累积步数？backward 累加不平均， 不除的话累积 N 份的梯度是单份的 N 倍，等效 batch 大了梯度也大了，lr 语义就变了。 ② unscale_ 为什么在裁剪之前？fp16 下 scaler 把梯度整体放大了 65536 倍（下节详讲）， 此时的"梯度范数"是虚胖的——先还原真实大小，clip_grad_norm_（梯度范数裁剪： 当所有参数梯度的总模长超过阈值 grad_clip=1.0 时等比例缩小，防某一步的坏梯度把参数打飞） 的阈值语义才成立。③ zero_grad(set_to_none=True)？把 .grad 引用直接置空 而不是写零张量——省一块显存，也让下一步 backward 必须重新分配（不留上一步的僵尸梯度）。

账目上：M01 冒烟跑了 max_steps=6 个 micro step、累积 2，所以 optimizer_steps=3——6 ÷ 2 = 3，参数真的只动过 3 次。 metrics.jsonl 里所有曲线的 x 轴都用 optimizer step（这把尺子统一是 2026-09-24 修的缺陷，猎场见）。

同构：范式只提供 compute_loss

预训练范式对这台引擎的全部"定制"，是一个 37 行的 workflow 文件（M16 说的"37 行母版"就是它）： 组装三件套 + 一个 compute_loss 闭包：

src/minimind_reborn/training/pretrain/workflow.py · run 全文（组装段）python
def run(cfg, *, device=None, local_rank=0) -> Trainer:
    setup_logging(cfg.run_dir)
    tokenizer = load_tokenizer()                     # 四件组装：tokenizer
    model = build_model(cfg, tokenizer)              #   模型（先过词表断言）
    train_ds, eval_ds = build_lm_dataset(cfg, tokenizer, kind="pretrain")   #   数据集
    def compute_loss(batch, m):                      #   ★损失 = 与引擎的全部接口
        out = m(batch["input_ids"], labels=batch["labels"])
        loss = out.loss + out.aux_loss               # aux 仅 MoE 非零（M08）；dense 恒 0
        return loss, {"train/loss": out.loss.item(), "train/aux_loss": float(out.aux_loss)}
    trainer = Trainer(cfg, model, tokenizer, train_ds, eval_ds,
                      compute_loss=compute_loss, save_weight="pretrain", ...)
    trainer.run()                                    # 之后的一切都是基座的事
    return trainer

DPO 的 compute_loss 吃 {x, y, mask} 三个张量、RL 的吃 messages 列表—— 但循环骨架、lr、AMP、裁剪、保存一字不改。引擎对 batch 的内容只有一个假设： "取第一个张量字段的 batch 维当 token 数"（trainer.py:278）。 这就是 M16 要展开的"37 行母版"同构之美，本课先把引擎本体看透。

组装段里的三个助手来自 training/common/setup.py： load_tokenizer 从 assets/tokenizer/ 加载（M10 造的那份）； assert_vocab_match 是 M02 见过的双源断言训练版——模型词表 6400 与 tokenizer 对不上直接 ValueError 拒绝训练；build_lm_dataset 走 M11 的 registry 按名字找到语料文件。 SkipBatchSampler（trainer.py:39）解决续训对齐：断点存在 epoch 中间时，重跑的数据顺序必须和 断点前完全一致（同 seed 打乱），只是跳过前 k 个 batch 不产出——被跳过的样本连加载都不发生。 它和 checkpoint 六件套是一对，M14 一起拆。

🏭 工业对照：HF Trainer、accelerate 与"母版循环"

把训练循环收敛成一个基类 + 回调，是工业界共同的选择：HuggingFace 的 Trainer 用几十个回调点（on_step_end、on_epoch_end…）换可插拔，代价是控制流散在回调里、 debug 要追注册表。reborn 反其道：接口收到只剩一个 compute_loss， 循环骨架永远可读——教学项目要的是"一眼看穿"，不是"万能插槽"。 预取器 CUDAPrefetcher（prefetch.py， YOLOX 同款模式）也是这个路数：用一条独立 CUDA 流（stream：GPU 上的并行任务队列）提前把下一批数据 拷到卡上，数据传输与当前步的计算重叠——CPU 设备自动旁路，不引入"GPU 之外无预取语义"的假象。

学习率调度：一个 15 行的纯函数

M01 说 lr（学习率）是"每步参数更新的步长"。它不该是常数：训练开局模型还很乱， 大步长会把参数打飞；训练后期接近收敛，需要小步长精修。 学习率调度（LR schedule）就是"步长随进度变化的方案"。reborn 不用 PyTorch 的 lr_scheduler 对象，而是 lr.py 里一个 15 行纯函数 （纯函数：只吃参数返回结果、不碰任何外部状态的函数）：

src/minimind_reborn/training/common/lr.py · get_lr 全文python
def get_lr(step, total_steps, base_lr, *, warmup_steps=0, min_ratio=0.1) -> float:
    """warmup 线性爬升 → 余弦衰减到 base_lr·min_ratio（官方 get_lr 的地板语义保留）。"""
    if total_steps <= 0:
        return base_lr
    if warmup_steps > 0 and step < warmup_steps:
        return base_lr * (step + 1) / warmup_steps          # 阶段一：线性爬坡
    progress = min((step - warmup_steps) / max(total_steps - warmup_steps, 1), 1.0)
    return base_lr * (min_ratio + (1 - min_ratio) * 0.5 * (1 + math.cos(math.pi * progress)))
    #      ↑ 阶段二：余弦从 base_lr 光滑滑到 base_lr×0.1（地板），越界钳在 progress=1

两段拼起来，公式是：

$$ \mathrm{lr}(s) = \mathrm{base}\cdot\begin{cases}\dfrac{s+1}{W} & s < W \quad\text{（warmup：线性爬升）}\\[8pt] \rho + (1-\rho)\cdot\dfrac{1+\cos\!\big(\pi\,p\big)}{2} & s \ge W \end{cases}\qquad p=\min\!\Big(\tfrac{s-W}{T-W},\,1\Big),\;\; \rho=\text{min\_ratio}=0.1 $$

warmup（预热）：前 W 步让 lr 从 0 线性爬到 base——因为 AdamW 开局时对每个参数的 "梯度波动幅度"估计还是零（下节展开），头几步的更新量天然失衡，先小步走几步等统计量稳定。 余弦衰减（cosine decay）：之后按余弦曲线光滑滑落，最终停在 base×0.1 的地板 ——不是降到 0：训练末段仍要留一点步长，否则最后几步等于白跑。 真跑 11 个采样点（base=5e-4、总步 60、warmup 10，与 64M 配方同底）：

为什么是纯函数：可单测、可复现、无状态可漂移

lr_scheduler 对象把"当前走到第几步"藏在对象内部状态里——每调一次 step() 它变一点， 出了问题你得审对象的一生。纯函数没有这层：lr 是 (step, total, base, …) 的函数， 想知道任意一步的 lr，算就是了；想断言"训练结束恰好在地板上"，直接调函数末步。 test_common.py 前两个用例锁的正是语义： test_lr_official_cosine_floor_semantics 断言与官方公式 lr*(0.1+0.45*(1+cos(pi*t))) 逐位一致（误差 < 1e-12），test_lr_warmup_and_clamp 锁 warmup 首步/末步与越界钳制。

纯函数还有个隐藏收益：分母口径错了，测试能抓。 test_lr_schedule.py 记录了一个真实缺陷（2026-09-29 perf_analysis 案 B）：双卡 DDP（DistributedDataParallel，数据并行多卡训练， M15 详讲）下每卡每 epoch 只迭代全量的 1/world，而余弦分母此前按全量算—— 2 个 epoch 跑完 lr 只退到 75% 进度处（≈lr×0.23），到不了地板。 修复是 per_rank_full_iters()（trainer.py:82）按本 rank 口径折算分母； test_old_bug_signature_locked 把旧口径的错值 ≈2.32e-6 钉成"回归签名"—— 这个数字再出现，就是 bug 回来了。单卡 world=1 时两种口径恰好一致，所以 mini 时代从未暴露： 又一个"单卡测不出、多卡才现形"的案例。

AMP 混合精度：bf16 与 fp16 的分野

AMP（Automatic Mixed Precision，自动混合精度）：矩阵乘这类大数值吞吐的算子跑低精度 （省一半显存与带宽、快一倍），敏感的归约仍留在 fp32——PyTorch 的 autocast 上下文自动逐算子分派， 你只需选 16 位类型。M05 见过 bf16 的位宽（8 位指数 + 7 位尾数），这里把它和 fp16 摆在一起看关键差异：

指数位尾数位最小正规数训练要 GradScaler？
bf168（同 fp32）7≈1.2e-38不要——动态范围与 fp32 同宽
fp16510≈6.1e-5要——小梯度会下溢为 0

fp16 尾数更精（10 位），但指数只有 5 位：绝对值小于 ~6.1e-5 的数在 fp16 里直接变成 0。 深网络反向传播到浅层时梯度经常就是这个量级——消失的梯度不会报错，参数只是静默不学。 bf16 砍尾数保指数，动态范围和 fp32 一样宽，天生不需要补救。两分钟实机验证：

reborn 把这三个决定收进 amp.py 的 43 行里， 训练循环只使用、不判断：

def resolve_dtype(name: str) -> torch.dtype:
    """配置字符串 → torch dtype；设备不支持 bf16 时回退 fp16 并留痕。"""
    if name == "fp32":
        return torch.float32
    if name == "bf16":
        if torch.cuda.is_available() and not torch.cuda.is_bf16_supported():
            logger.warning("当前 GPU 不支持 bf16，AMP 回退 fp16（降级留痕）")   # 老卡（如 V100）路线
            return torch.float16
        return torch.bfloat16
    if name == "fp16":
        return torch.float16
    raise ValueError(f"未知精度 {name!r}（守门人应已拦截，说明绕过了 loader）")

def autocast_context(dtype: torch.dtype, device: str):
    """autocast 上下文：CPU 或 fp32 时 nullcontext（空操作），否则 cuda autocast。"""
    if device.startswith("cuda") and dtype in (torch.bfloat16, torch.float16):
        return torch.autocast(device_type="cuda", dtype=dtype)
    return nullcontext()

def build_scaler(dtype: torch.dtype) -> torch.amp.GradScaler:
    """scaler 恒创建，enabled 只认 fp16——scaler 的 step/update 调用次数与 optimizer 对齐。"""
    return torch.amp.GradScaler(enabled=(dtype == torch.float16))

resolve_dtype 的回退链你在 M02/M03 见过推理版（CPU 上 bf16→fp32）；训练版的回退方向不同： GPU 不支持 bf16（Ampere 之前的老卡）就退 fp16 + GradScaler，降级必须打一行警告留痕。 注意最后那行注释——scaler 无论什么精度都创建，只是 enabled=False 时它变成透传 （scale(loss) 原样返回、step() 直通优化器）。于是训练循环里 scaler.scale(...).backward() 一套代码三种精度通吃，一个 if dtype == 都不用写。

⚠️ 坑卡：scaler 与精度错配——要么静默丢梯度，要么白付开销
  • 两种长相。A：fp16 训练不开 scaler——loss 不 NaN、日志正常，但浅层梯度下溢成 0， 模型"在跑却不在学"，几小时后从 loss 曲线不动才发现；B：bf16 训练挂了 enabled=True 的 scaler——一切照常，你白付每步两次额外检查/缩放，还可能因 假 inf 跳步。两种都不报错。
  • 根子是把"16 位"当成一种精度。fp16 指数 5 位、最小正规数 ~6.1e-5，深网梯度常态性低于它 （上面的实测：2e-8 → 0.0）；bf16 指数 8 位与 fp32 同宽，根本没有这个坑，挂 scaler 属于 给不需要急救的病人上呼吸机。amp.py 模块 docstring 把这两条列为 anti-patterns §训练 的前两行。
  • reborn 的解法是恒创建 + enabled 开关（build_scaler 一行），错配在构造期就消灭。 顺带的实测发现：tiny 模型上 fp16 反而最慢（7.29 ms/步 vs bf16 3.46）—— 每步 ~3ms 里 scaler 的簿记（unscale、inf 探测、状态更新）成了重税； 到 64M 模型步子变大，簿记摊薄，fp16 才回到与 bf16 相当。

优化器：decay 分组与 0.95

引擎里最后一个基件是 AdamW：Adam 优化器 + 解耦权重衰减。 Adam 为每个参数维护两个滑动平均：一阶矩 m（梯度的动量，方向）与二阶矩 v (梯度的平方均值，尺度)；更新量 ∝ m/√v——尺度自适应，各个参数"步长自动配速"。 optim.py 全文 25 行， 两处值得停：

src/minimind_reborn/training/common/optim.py · configure_optimizers 全文python
def configure_optimizers(model, lr, weight_decay, params=None) -> torch.optim.Optimizer:
    """AdamW + 权重 decay 分组：≥2 维张量 decay，bias 与 1 维参数（norm）不 decay。"""
    trainable = [p for p in (params if params is not None else model.parameters()) if p.requires_grad]
    decay = [p for p in trainable if p.dim() >= 2]     # 矩阵（embedding、各投影）
    no_decay = [p for p in trainable if p.dim() < 2]   # 向量：bias 与 norm 的 scale
    groups = [
        {"params": decay, "weight_decay": weight_decay},
        {"params": no_decay, "weight_decay": 0.0},
    ]
    fused_available = "fused" in inspect.signature(torch.optim.AdamW).parameters
    extra = {"fused": True} if (fused_available and torch.cuda.is_available()) else {}
    return torch.optim.AdamW(groups, lr=lr, betas=(0.9, 0.95), **extra)

weight decay（权重衰减）：每步把参数往 0 拉一小把的正则项，防止权重无限膨胀。 但"往 0 拉"对两类参数是伤害：RMSNorm 的 scale 与 bias 是一维向量，它们本身编码的就是 "这一层输出的尺度/偏移"——衰减它们等于持续把表示的幅度往 0 压，模型得用别的参数拼命补偿。 所以 LLM 惯例按维度一刀切：dim ≥ 2 的矩阵衰减、一维向量不衰减。 tiny 模型上真分组看账：decay 组 532,480 个参数、no_decay 组只有 384 个—— 恰是 8 个 norm 向量（q_norm/k_norm 16 维 + 两个 layernorm 64 维，×2 层）加出口 norm 64 维； 整个模型连一个 bias 都没有（M09 说过的去偏置哲学），全靠 dim 规则兜住。 test_optimizer_decay_groups 用 Linear+LayerNorm 双层模型锁死分组不变量。

[作者实测 · 2026-10-01] 分组数字来自对 tiny 冒烟模型跑 configure_optimizers 后 按 param_groups 的 weight_decay 分别求和：532,480 / 384，与逐参数形状清单一致。

betas=(0.9, 0.95)：β₁ 是动量系数（0.9 = 记住近 10 步梯度方向，惯例不变）； β₂ 是二阶矩的衰减率——PyTorch 默认 0.999（窗口 ≈ 1000 步），LLM 训练惯例改 0.95（窗口 $1/(1-0.95)=20$ 步）：语言模型早期梯度分布变化剧烈，更短的窗口让尺度估计 跟得上突变、对 loss 尖峰更稳健，GPT-3 起几乎全员如此。fused 那两行是工程口味： 不比较版本号，而是签名探测——当前 torch 的 AdamW 支持 fused（CUDA 融合内核，一次launch 完成整组更新）才开启；能力探测比版本判断更能抵御环境漂移。

MFU：为什么 tiny 只有 0.1%

M01 欠的最后一个词。MFU（Model FLOPs Utilization，模型算力利用率）：模型理论需要的计算量， 占 GPU 峰值算力的比例。训练一个 N 参数的模型，每个 token 前向约 2N 次浮点运算、反向约 4N， 合计 6N——所以：

$$ \text{MFU} \;=\; \frac{6\,N\cdot \text{tok/s}}{\text{world} \times \text{peak}} \;=\; \frac{6 \times 532{,}864 \times 48{,}624}{1 \times 165 \times 10^{12}} \;\approx\; 0.09\% $$

代入冒烟实测：分子 6×0.53M×48,624 tok/s ≈ 0.155 TFLOPS，分母是 4090 的 bf16 峰值 165 TFLOPS （TFLOPS：每秒万亿次浮点运算；trainer.py:164-167 的口径注释——换卡型要同步改这个数）—— 0.09%，日志四舍五入成 0.1%。 模型每步只做 ~3ms 的算术， 而每步的固定开销（Python 循环、几十次 kernel 启动、优化器更新、数据拼装）一个不少—— GPU 大部分时间在等指令。对照真实 64M 训练存档： [存档 runs/pretrain_full/20260925_005504 · 2×RTX 4090 DDP · bf16] 日志 tok/s=253714 mfu=29.5%，验算 $6\times63.91\text{M}\times253714 / (2\times165\times10^{12}) = 29.5\%$—— 注意分母的 world=2：tok/s 统计的是两卡合计吞吐。0.1% → 29.5% 就是"模型变大、每步算术变重、 固定开销被摊薄"的完整故事；连 Google 的 PaLM（540B）公开报告的 MFU 也只有 46%—— 这个指标的天花板远低于直觉。

ETA 与"度量口径"

ETA（预计剩余时间）：剩余步数 × 每步平均耗时。它被提炼成又一个纯函数 （trainer.py:71，9 行）：$\text{ETA}=\dfrac{t_{\text{elapsed}}}{\text{steps}_{\text{done}}}\times\dfrac{\text{steps}_{\text{left}}}{60}$（分钟）。 test_eta_formula 锁了三组数：5000 步用了 600 秒 → 剩 3000 步应需 6.0 分钟； 0 步已完成 → 0.0（不外推，防除零）。这个函数为什么值得"纯函数化+测试"？因为它刚出过一次 真实事故——分子用错了时钟，ETA 恒 0。这就是本课猎场。

同属"口径"纪律的还有一个负结果实验：--set data.num_workers=0（数据加载不另开进程， 主进程边算边取）与默认 workers=2 各跑 40 步，稳定窗口 tok/s 分别为 25,178–26,615 与 22,348–27,045——差异在噪声内。tiny pretrain 的取样+拼批太轻，本就不是 CPU 瓶颈； 真正翻车的是 SFT 重编码场景（单条样本秒级，loader_kwargs docstring 记录的 2026-09-29 案 A 因此把预取缓冲加深到 4×workers 并常驻 worker）。教训同款：先量口径，再下结论—— "多 worker 更快"在 tiny 上是伪命题，在你的负载上量过才知道。 [作者实测 · 2026-10-01 · 冒烟配方 max_steps=40 log_interval=10，各跑一次]

                               offset + 1 - start_step,     # 分母：与分子同一口径的已完成步数
                               iters - offset - 1)          # 剩余步数

def estimate_eta_minutes(elapsed_total_s, steps_done, steps_left) -> float:
    """ETA 纯函数：epoch 开局至今总耗时 / 已完成步数 × 剩余步数（分钟）。"""
    if steps_done <= 0 or steps_left <= 0:
        return 0.0        # 无已完成步不外推（防除零）；无剩余步自然为 0
    return elapsed_total_s / steps_done * steps_left / 60

回归锁定：同一个 commit 新增 test_observability.py， test_eta_formula 三组断言把公式钉死；test_metrics_steps_monotonic_and_unified 锁同一 commit 修的另一处口径 （train/val 曲线统一用 optimizer step，x 轴不再错位——M01 日志里 optimizer_steps=3 那把尺子就是它定的）。 通用教训：度量口径——分子分母必须来自同一把尺子。"窗口耗时 ÷ 累计步数"各自单独看都合法 （窗口测吞吐、累计算进度），拼在一起就是结构性的错；而且它错得很体面：早期数值碰巧接近真值 （窗口恰好覆盖全部已走步时两者相等），越到后期越离谱。凡是"越跑越准/越跑越离谱"的指标， 先查口径，再查公式。

检验一下

测验 1 · warmup 为什么存在？reborn 默认 warmup_steps 是多少、什么场景必须打开？

答案：AdamW 开局对每个参数的梯度尺度（二阶矩 v）估计还是零，头几步的更新量天然失衡，大步长容易把参数打飞；warmup 让 lr 从 0 线性爬到 base，等统计量稳定再全速走。reborn 默认 warmup_steps=0（对齐官方"从零训"配方），但 pretrain_longctx.yaml 里设了 200——加载现成权重续训时，参数已是训好的状态，开局就踩全速 lr 会把权重震坏，必须热身。

答错回看：学习率调度 的公式与采样表、优化器 的 AdamW 两矩。

测验 2 · MFU 公式的分子和分母分别是什么？tiny 冒烟 0.1% 和 64M 实跑 29.5% 的差距从哪来？

答案：分子 = 6·N·tok/s（N 是可训练参数量，每个 token 前向 2N + 反向 4N 次浮点运算）；分母 = world × 每卡峰值算力（4090 bf16 按 165 TFLOPS 记，多卡要乘卡数）。tiny 的差距来自两头：分子上 0.53M 参数每步只做 ~3ms 算术，而每步的固定开销（Python 循环、kernel 启动、优化器更新）一个不少，GPU 大部分时间在等指令；64M 每步算术变重，开销被摊薄，29.5% 就是"固定开销摊薄后"的正常水位——工业大模型也不过三到五成。

答错回看：MFU 小节 的两笔验算。

测验 3 · betas=(0.9, 0.95) 里的 0.95 改的是什么？为什么 LLM 训练不用 PyTorch 默认的 0.999？

答案：0.95 是 β₂——AdamW 二阶矩（梯度平方的滑动平均）的衰减率，窗口长度 ≈ 1/(1-β₂)：默认 0.999 对应约 1000 步，0.95 收窄到约 20 步。语言模型训练早期梯度分布变化剧烈、loss 尖峰常见，长窗口的尺度估计更新太慢，短窗口能让步长配速跟得上突变、对尖峰更稳健——GPT-3 起的 LLM 惯例。β₁（动量）保持 0.9 不变。

答错回看：优化器 小节的 betas 段。

测验 4 · 冒烟跑了 6 个 micro step、累积步数 2，optimizer_steps 为什么是 3？grad_norm 为什么必须在 unscale_ 之后测？

答案：梯度累积把每 2 个 micro step 的梯度记账（loss 除以 2 后 backward 累加）合并成 1 次参数更新：6 ÷ 2 = 3 次 optimizer step——模型参数只动过 3 次。unscale_ 之前，fp16 路径下梯度被 GradScaler 整体放大了 65536 倍，"梯度范数"是虚胖的；先还原真实大小，clip_grad_norm_ 的阈值（grad_clip=1.0）语义才成立——这也是"scale→backward→unscale_→clip→step"固定顺序的原因。

答错回看：micro step 与 optimizer step 的三个"为什么"。

🧪 变式 · 把 warmup_steps 从 2 改成 10：前几步的 lr 曲线怎么变？

配置 train.warmup_steps 是每个配方都能动的旋钮（M04 的 --set 直达）。 固定 total=60、base=5e-4，只动 warmup。先笔算再跑：

写下预测：warmup=2 时 step 0 的 lr 是多少？改成 10 后，step 0 变成多少、 什么时候追平 base？warmup 拉长 5 倍，前 6 步里每步的 lr 是变陡了还是变缓了？

/tmp/m13_warmup.py · 对照打印两种 warmup 的前 6 步python
from minimind_reborn.training.common.lr import get_lr

print(f"{'step':>4} {'warmup=2':>11} {'warmup=10':>11}")
for step in range(6):
    a = get_lr(step, 60, 5e-4, warmup_steps=2)     # (step, total, base, …)
    b = get_lr(step, 60, 5e-4, warmup_steps=10)
    print(f"{step:>4} {a:>11.3e} {b:>11.3e}")
观察结果与解释（先动手再看）

作者实测（2026-10-01，同环境）：

step    warmup=2   warmup=10
   0   2.500e-04   5.000e-05
   1   5.000e-04   1.000e-04
   2   5.000e-04   1.500e-04
   3   4.997e-04   2.000e-04
   4   4.987e-04   2.500e-04
   5   4.970e-04   3.000e-04

机制：warmup 段公式是 base×(step+1)/W——step 0 的 lr = base/W： W=2 时一步就到 base 的一半、第二步登顶；W=10 时每步只爬 base/10， 前 6 步整体矮了一大截，要到 step 9 才追平 base，之后才交棒给余弦段。 warmup 拉长 = 起跑更保守；同时注意 W=2 那列 step 2 已是 5.000e-04（登顶后交给余弦， progress=0 处余弦值恰为 base），step 3 起缓慢下滑——两条曲线在"W 处交接"这一性质不变。 回看测验 1 的场景：续训加载现成权重时，你要的正是右侧那列"慢慢踩油门"。

失败了怎么办？（按症状分流）

pytest 有 failed → 读用例名分流：test_lr_* 失败回 LR 小节（先查是否动过 lr.py）， test_ddp_* / test_old_bug_signature_locked 失败回 纯函数小节 的分母口径， test_eta_formula 失败回 猎场； 训练启动即 KeyError / 未知精度 → --set train.dtype 拼错（守门人应更早拦截， 见 resolve_dtype 末行的报错文案）；找不到数据集 → 回 M11 的 registry/datasets.json 检查语料是否就位； runs 目录只有 train.log → config.json/env.json 由 rank0 独占写入（trainer.py:143）， 单卡必然有；若用 torchrun 多卡，确认没把 world_size>1 的 rank1 目录当成了唯一目录； 续训意外接上了旧进度（第一步就从中间开始）→ checkpoints/ 里有旧档而你忘了 --set train.resume=false，日志第一行会写"续训恢复清单"。

引擎转起来了，每 epoch 末它都在默默调 _save——权重之外还存了优化器状态、进度、 RNG（随机数发生器）状态……那个"六件套"里每一件都对应一种"断了又续"的灾难， M14 逐件拆开，并用 kill -9 实验验证它真的接得住。

本课词汇

训练循环生命周期 train loop lifecycle
run → _train_epoch → evaluate → _save 的固定骨架；梯度/AMP/裁剪/续训/评估/保存的顺序与不变量固定在 Trainer，范式只提供 compute_loss 与数据组装，不得绕过。
micro step / optimizer step
前者 = 一个 batch 的前向+反向（梯度记账），后者 = 优化器真正更新一次参数。隔着梯度累积（loss ÷ 累积步数后 backward 累加）；metrics 曲线的 x 轴统一用 optimizer step。
学习率调度 LR schedule
步长随进度的方案：warmup 线性爬升（开局 Adam 统计量未稳，先小步走）→ 余弦衰减到 base×min_ratio=0.1 的地板（末段仍留步长）。reborn 写成 15 行纯函数 get_lr，无对象状态、可单测、续训无漂移。
AMP 混合精度 automatic mixed precision
autocast 逐算子分派：大吞吐算子跑 16 位、敏感归约留 fp32。bf16 指数位与 fp32 同宽（8 位），天生不需要 loss scale；fp16 指数 5 位、最小正规数 ~6.1e-5，小梯度下溢为 0，必须配 GradScaler。
GradScaler 梯度缩放器
把 loss 乘 scale（初始 65536）使梯度落进 fp16 可表示区间，更新前 unscale 还原；发现 inf/nan 则跳过该步并调小 scale。reborn 恒创建、enabled 只认 fp16——训练循环一套代码三种精度通吃。
decay / no-decay 分组
AdamW 构造时按维度切参数组：dim≥2 的矩阵衰减（weight_decay>0），一维向量（bias、norm 的 scale）不衰减——衰减它们等于持续压缩表示的尺度。LoRA 场景可传入自己的参数集。
MFU model FLOPs utilization
模型算力利用率 = 6·N·tok/s ÷（world × 每卡峰值）。每个 token 前向 2N + 反向 4N 次浮点运算。tiny 冒烟 0.1%（固定开销主导），64M 双卡实跑 29.5%；工业大模型普遍三到五成。
ETA estimated time of arrival
剩余时间 = 开局至今总耗时 ÷ 已完成步数 × 剩余步数（estimate_eta_minutes 纯函数）。教训（度量口径）：分子分母必须同一把尺子——窗口耗时冒充总耗时曾让 838 行日志里 270 行 ETA 恒 0。
可追溯四件套 run artifacts
runs/<recipe>/<时间戳>/ 下的 config.json（配置全量快照）、env.json（git commit/软硬件指纹/seed）、train.log（人读时间线）、metrics.jsonl（(step,key,value) 逐行指标流，本地兜底永不断网失忆）。
