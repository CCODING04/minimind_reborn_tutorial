DDP 与 no_sync：把训练扩到两张卡

M14 补上 checkpoint 六件套之后，单卡的训练闭环已经完整：能训、能评、能存、断了能续。 本课把这台引擎原样扩到多卡——代码几乎一行不改，只换一个启动命令； 再拆一个看不见的陷阱：一个让每三份双卡算力就有一份白白蒸发的通信 bug。

前置：M14（M13 的训练循环、M09 的 rank0 门控本课回收） 时长：约 70 分钟 新概念：数据并行（DDP）· 梯度同步（no_sync） 对照：utils/dist.py · training/common/trainer.py · docs/pretrain_readiness.md

  • 解释 DistributedSampler 为什么必须切数据、set_epoch 为什么每个 epoch 都要调，用真实日志指出每 rank 迭代数如何随 world 减半；
  • 复述 utils/dist.py 的不变量"业务代码不写 if distributed"，指出 rank0 门控 IO 在 reborn 的至少三个落点、各自防什么事故；
  • 手算累积 8 步时 no_sync 有/无的全量同步次数（8 次 → 1 次），用双卡 A/B 实测解释为什么吞吐 +31~33% 而不是 8×；
  • 跑通 torchrun 双卡冒烟并逐行读懂 world=2 日志；没有双卡时走存档分析路线。

数据并行：复制模型，切分数据

M08 讲 MoE 时给过 DDP 一句话定义（"反向后同步梯度的多卡训练方式"），M13 讲 MFU 时又借了它的 world—— 今天把它讲透。DDP（DistributedDataParallel，分布式数据并行）是 PyTorch 的多卡训练包装器： 每张 GPU 上跑一个独立的 Python 进程（不是一张卡多个线程），每个进程持有一份完整模型副本， 吃不同的数据分片，各自前向、各自反向，然后在梯度上对齐。 它复制的是模型、切分的是数据——所以叫"数据"并行（与之相对的"模型并行"把一层模型拆到多卡上，见本节工业对照）。

💡 直觉：四个学生、四套卷子、同一本教材

一个班四个学生（4 个进程）用同一版教材（初始参数完全相同的模型副本）， 每人做一套不同的卷子（各自的数据分片）。做完各自总结出自己的错题修正量（本地梯度 g₀…g₃）， 然后全班对答案：每个人每道题的修正量取平均（all-reduce），四个人拿到同一份平均修正量， 各自誊回自己的教材（optimizer step）。因为起点相同、修正相同，四本教材永远逐位一致—— 参数从不需要"抄"给对方，需要同步的只有每一步的梯度。 

DDP 一个 micro step（4 卡）—— trainer.py 每个进程各自执行同一段代码

          一个 epoch 的全部样本
   ┌───────────┬───────────┬───────────┬───────────┐
   │  shard 0  │  shard 1  │  shard 2  │  shard 3  │     ← DistributedSampler 预先切好
   ▼           ▼           ▼           ▼
 ┌───────┐  ┌───────┐   ┌───────┐   ┌───────┐
 │ rank0 │  │ rank1 │   │ rank2 │   │ rank3 │     rank = 进程编号（0 起）
 │ fwd   │  │ fwd   │   │ fwd   │   │ fwd   │     每份模型参数逐位相同
 │ bwd   │  │ bwd   │   │ bwd   │   │ bwd   │     吃的却是不同的 1/4 数据
 │  g0   │  │  g1   │   │  g2   │   │  g3   │     本地梯度（各不相同）
 └───┬───┘  └───┬───┘   └───┬───┘   └───┬───┘
     └──────────┴─────┬─────┴───────────┘
                     ▼
      all-reduce：g = (g₀+g₁+g₂+g₃) / 4          ← 逐元素平均，每个参数一份
                     │
     每个 rank 用同一份 g 各自 optimizer.step()
                     ▼
     四份模型更新后依然逐位一致（下一轮起点又相同）

三个词先钉死。rank：进程编号，从 0 数起，world_size 个进程就是 rank 0…world−1； world size：进程总数（2 卡就是 2）——M13 的 MFU 公式分母里那个 world 就是它； all-reduce：一种集合通信（collective，所有 rank 一起参与、结束时各自拿到同一结果的通信原语）， 这里做的是"把各 rank 的梯度张量逐元素求平均"。注意 all-reduce 平均的是梯度—— 不是 loss（loss 只是日志），不是参数（参数从不搬运），更不交换激活值。

还有一个容易想歪的问题：每 rank 各自跑 optimizer.step()，参数为什么不会跑散？ 因为起点逐位相同 + 梯度经 all-reduce 后逐位相同 + 同一份优化器代码做确定性计算 ——三"同"叠加，四个进程的参数在每一步之后依然逐位相同。DDP 的全部魔法就在"让梯度相同"这一件事上。

先切数据：DistributedSampler 与每 rank 迭代数减半

DDP 自己不切数据——它假设你喂给每个进程的已经是不同的分片。要是两个 rank 吃完全相同的 batch， all-reduce 会忠实地把两份一样的梯度平均成同一份，等效 batch 一点没变大，卡白买、通信白付。 切分是 DistributedSampler（PyTorch 的分布式采样器）的活：它把样本下标按 rank 轮转均分 （rank 0 拿第 0, 4, 8…号，rank 1 拿 1, 5, 9…号），样本数不整除时补 padding 凑齐——保证各 rank 分片等长 （这一点 §变式练习会用到）。reborn 把它接进 M13 读过的 _build_loader：

src/minimind_reborn/training/common/trainer.py · _build_loader 的分布式分支（节选）python
sampler: DistributedSampler | None
if dist.is_initialized():                          # 唯一的分布式分支，长在基座里（范式子包看不见）
    sampler = DistributedSampler(self.train_ds, shuffle=True)
    sampler.set_epoch(epoch)                       # 不调：每个 epoch 的打乱顺序完全一样
    inner: DistributedSampler | list[int] = sampler
else:
    g = torch.Generator()
    g.manual_seed(cfg.train.seed + epoch)          # 单卡：采样器显式携带种子（training §1，M12 的确定性）
    inner = torch.randperm(len(self.train_ds), generator=g).tolist()
batch_sampler = SkipBatchSampler(
    inner, cfg.train.batch_size, self.start_step if epoch == self.start_epoch else 0
)                                                  # SkipBatchSampler：续训跳批对齐（M14）

set_epoch 为什么每个 epoch 都要调？DistributedSampler 的打乱种子由"基种子 + epoch"派生， 不调 set_epoch 它就一直用 epoch=0 的顺序——训练照跑，但每个 epoch 都在重复同一遍数据顺序， 打乱的效果静默失效。单卡分支同样用 seed + epoch 保证两条路语义对齐（M12 讲过的确定性纪律）。 效果直接写在日志的进度分母里——同一份冒烟配方，单卡与双卡各跑一次：

包一层 DDP：三处讲究

src/minimind_reborn/training/common/trainer.py · 构造函数尾部（顺序即要点）python
self.optimizer = configure_optimizers(   # ① 优化器建在裸模型上，之后才包 DDP
    self.raw_model, t.learning_rate, t.weight_decay, ...)
...
self._load_initial_weights()            # ② 权重语义三选一（resume > finetune > init_from，M14）
if dist.is_initialized():
    # 非持久 buffer（RoPE 表）各 rank 由同一 config 确定性算出，广播纯属浪费
    self.model: torch.nn.Module = DistributedDataParallel(
        self.raw_model, device_ids=[local_rank], broadcast_buffers=False
    )                                    # ③ 最后才包装：单卡时连包装都不发生
else:
    self.model = self.raw_model

三处讲究，每处都连着前课：① 优化器建在裸模型上、之后再包 DDP——DDP 不复制参数， 只是在反向传播的路径上挂钩子，把 all-reduce 后的平均梯度写回同一块 .grad； 所以优化器拿到的永远是同步后的梯度，保存时 M09 见过的 unwrap_model 剥掉壳、键名不带 module. 前缀。② broadcast_buffers=False——DDP 默认每次前向前广播模型里的 buffer（M05 讲过的"跟着模型走、不参与训练"的张量），但 reborn 的 RoPE 表是同一 config 确定性算出的，各 rank 本来就一样，广播纯属浪费带宽。③ device_ids=[local_rank]—— 每个进程绑定自己那张卡（local_rank：本机内的卡号；多机时 rank 是全局编号、local_rank 是本机卡号， 单机两者相同）。

🏭 工业对照：DDP 只是并行的最底层

DDP 是"每卡一份完整模型"——64M 模型 256MB 权重，两张 24GB 的 4090 各养一份毫无压力， 所以 reborn 全程 DDP 就够。模型大到单卡装不下时，工业界换挡：DeepSpeed ZeRO / PyTorch FSDP 把优化器状态、梯度、参数切片到各卡（用通信换显存），再往上还有 流水线并行（按层切）与张量并行（把单个矩阵乘切开）。它们的共同底座仍然是本课的概念： 切分的是什么、每步同步什么。先懂 DDP，再懂其他。

容错 dist 封装：业务代码不写 if distributed

多卡代码最怕的不是写不出来，而是散：业务逻辑里到处 if rank == 0:、 if dist.is_initialized():，读代码的人永远不知道还有哪个分支没看到。 utils/dist.py 全文 85 行，模块 docstring 第一句就立了不变量："业务代码不写 if distributed: 分支—— get_rank()/get_world_size() 在 dist 不可用/未初始化时返回 0/1，单机与多机代码同构； 一切 IO 由 is_main_process() 门控。"先看入口：

src/minimind_reborn/utils/dist.py · init_distributed 与容错三件套（节选，压缩处有注）python
def init_distributed(timeout_minutes: int = 30) -> int:
    """按环境变量探测 DDP（torchrun 注入 RANK/WORLD_SIZE），单卡自动回退。"""
    if os.environ.get("RANK", "-1") == "-1":
        return 0                    # 不是 torchrun 拉起来的 → 单进程，rank 0
    if not dist.is_available() or not torch.cuda.is_available():
        raise RuntimeError("检测到 RANK 环境变量（torchrun 启动）但 CUDA 不可用："
                           "分布式后端 NCCL 需要 GPU")
    dist.init_process_group(backend="nccl", timeout=datetime.timedelta(minutes=timeout_minutes))
    local_rank = int(os.environ["LOCAL_RANK"])
    torch.cuda.set_device(local_rank)   # 本进程绑定本卡，防两个进程挤同一张卡
    return local_rank

def get_rank() -> int:
    if dist.is_available() and dist.is_initialized():
        return dist.get_rank()
    return 0                        # 未初始化 = 单卡 = rank 0 —— 单/多卡同构的关键（编注）

def get_world_size() -> int: ...   # 同款容错：未初始化返回 1

def is_main_process() -> bool:
    return get_rank() == 0

两个词。torchrun：PyTorch 自带的多进程启动器——你在命令行敲一次，它拉起 N 个训练进程， 并给每个进程注入三个环境变量 RANK（全局编号）、WORLD_SIZE（进程总数）、 LOCAL_RANK（本机卡号）。NCCL：NVIDIA 的 GPU 通信后端（把 all-reduce 落到 NVLink/PCIe 的那层）；M08 玩具实验用的 gloo 是它的 CPU 兄弟。所以 init_distributed 的探测逻辑读起来是：没有 RANK 环境变量就不是 torchrun 启动， 直接返回 0 当单卡跑；有 RANK 却没有 GPU，立刻报错——docstring 里写了理由： "静默回退 CPU 只会把错误推迟到更难查的地方"（fail-fast，M04 守门人同款哲学）。 于是 README 的 quick start 才敢写"单卡去掉 torchrun 前缀即可"：同一份代码，两种世界。

rank0 门控 IO：单点写入，读侧广播

M09 讲权重保存时说过"rank0 门控——调用方负责"，欠的账今天还。多进程下所有 rank 跑同一份代码， 意味着写文件的代码每个进程都会执行一遍：两个进程同时打开同一个 metrics.jsonl 追加， 行会交错；同时 torch.save 同一个 .pth，互相覆盖甚至写坏。门控（gating，加一个 "只有 rank 0 才执行"的判断）是唯一的解。reborn 的落点：

落点判断防的事故
Trainer._save（trainer.py:366）if not is_main_process(): return两个 rank 同时 torch.save 同一权重/checkpoint 文件
四件套 config.json / env.json（trainer.py:143）构造期 rank0 独占同一 runs 目录写两份快照
metrics 后端（backends.py:134）非 rank0 → NullBackend()metrics.jsonl 两路追加、step 序列交错失真（真实踩坑后加的门）
train.log 文件 sink（loggers.py:51）文件只挂 rank0；控制台可开全 rank日志文件双份交错

写侧门控了，读侧要对齐：run_dir 的目录名由时间戳派生，两个进程各自取"当前时间"会得到两个目录—— rank0 存了日志、rank1 往另一个空目录里跑。所以 tools/train.py 里有一行 cfg.run_dir = dist.broadcast_object(cfg.run_dir)：广播（broadcast，rank 0 的值发给所有人）， 全队只用 rank 0 的时间戳。同文件里的聚合助手 all_reduce_mean 则是反向的"读对齐"：

src/minimind_reborn/utils/dist.py · all_reduce_mean + broadcast_objectpython
def all_reduce_mean(value: float, device: str = "cpu") -> float:
    """跨 rank 求平均（评估指标聚合）。非分布式时原样返回。"""
    if not (dist.is_available() and dist.is_initialized()):
        return value                     # 单卡：恒等函数，业务代码完全无感
    t = torch.tensor([value], device=device)
    dist.all_reduce(t, op=dist.ReduceOp.AVG)   # 各 rank 进各的 val loss，出同一份平均值
    return float(t.item())

def broadcast_object(obj, src: int = 0):
    """rank0 的对象广播到全部 rank（如时间戳派生的 run_dir）。"""
    if not is_initialized():
        return obj
    container = [obj]
    dist.broadcast_object_list(container, src=src)
    return container[0]

M13 的 evaluate() 末尾那一行 mean = dist.all_reduce_mean(mean, device=self.device) 由此闭环：每个 rank 在自己的验证分片上算出 val/loss，all-reduce 平均后所有 rank 拿到同一个数—— best_val_loss 的判断、_best 权重的存否，全队不会分歧。文件末尾的 cleanup() 先 barrier（栅栏：所有 rank 到齐这一行才放行）再销毁进程组， 保证没有进程提前退出留下悬空连接。

🛑 红线：分布式判断只许写在基座里

范式子包（pretrain/sft/dpo/…）与业务代码里不许出现 if torch.distributed.is_initialized()、 if rank == 0 这类分支——这是 dist.py docstring 立的不变量。反例是真实发生过的： metrics 双写踩坑（上表第三行）就是判断散落、漏掉一个写入点导致的。 要判断，用 dist.is_main_process()；要聚合，用 dist.all_reduce_mean()； 要多卡语义，让 Trainer 基座去做。grep 一下你的范式代码，出现 torch.distributed 直接 import 就是坏味道。

⚠️ 坑卡：不加门控的多进程写文件——最安静的竞态
  • 两种长相。A：metrics.jsonl 里 step 序列交错跳动（1,1,2,2,3…），画出的曲线毛刺； B：最危险的是权重文件——两个 rank 同时 torch.save 到同一路径，先写的被后写的覆盖； 若一个写到一半另一个改名（atomic_save 的 tmp→改名），还会留下内容与名字不符的文件。 全程无报错，训练"正常结束"。
  • 竞态（race condition）：N 个进程执行同一份代码，写文件的代码也就被执行 N 次。 atomic_save 防的是"写到一半进程被杀"（M14 的 kill -9 实验），防不了"两个写者"—— 它只保证单个写者的原子性。多进程下"文件只许有一个写者"必须显式声明。
  • reborn 的双层防线：写侧 is_main_process() 门控全部 IO（上表四行）， 非 rank0 的 metrics 后端直接换成 NullBackend（想写也没有笔）；读侧 broadcast_object 对齐 run_dir 等派生值。门控的判断集中在基座，业务代码零感知。

no_sync：梯度累积下的通信陷阱（本课核心）

M13 讲过梯度累积：显存装不下大 batch 时，把大 batch 切成 N 份逐份算，每份 loss 除以 N 记进梯度 （micro step），N 份攒齐才动一次参数（optimizer step）。单卡世界这毫无问题。 多卡世界撞上 DDP 的第二条铁律：DDP 默认在每个 backward() 之后立刻做一次全量 all-reduce ——它不知道你在累积梯度，它只认"backward 结束了就该同步"。于是 64M 配方 （累积 8 步）每个 optimizer step 要做 8 次全量同步，而数学上只需要最后 1 次： 

累积 8 步的通信账（64M 配方，两张 4090 之间只有 PCIe，无 NVLink）

修复前（DDP 默认）：                修复后（no_sync）：
micro 1  bwd → all-reduce ← 256MB   micro 1  bwd（no_sync：只本地累加）
micro 2  bwd → all-reduce ← 256MB   micro 2  bwd（no_sync）
  …        …            …             …        …
micro 8  bwd → all-reduce ← 256MB   micro 8  bwd → all-reduce ← 256MB（唯一一次）
optimizer.step()                   optimizer.step()
通信量：8 × 256MB                   通信量：1 × 256MB（↓ 87.5%）
计算量：一字不变                    梯度数值：一字不变（见下）

256MB 怎么来的：63.91M 个参数的梯度，fp32 主副本 4 字节 ≈ 255.6MB/次全量同步 （按 bf16 桶折算约一半；trainer.py 注释按 2 字节记作"136MB/步"）。两卡之间唯一的搬运通道是 PCIe（PHB 直连——PHB 指 PCIe Host Bridge，两卡经 CPU 的 PCIe 桥点对点互通； NVLink 是 NVIDIA 数据中心卡的专用高速互连，消费级 4090 没有）—— 8 次排队 vs 1 次，浪费的 7 次全是不必要的等待。

📐 为什么 no_sync 不改变数学（可跳过，不影响主线）

DDP 的 all-reduce 是对梯度做"跨 rank 平均"，梯度累积是"跨 micro step 求和"——平均与求和都是线性运算， 交换次序结果不变。设 16 条样本等分成卡 A、卡 B 各 8 条、每卡累积 2 个 micro step（gr,i 是第 r 卡第 i 个 micro batch 的平均梯度，每 batch 4 条）： $$ \underbrace{\tfrac{1}{2}\Big(\tfrac{g_{A_1}+g_{A_2}}{2}+\tfrac{g_{B_1}+g_{B_2}}{2}\Big)}_{\text{no\_sync：卡内先累加，最后跨卡平均一次}} \;=\;\underbrace{\sum_{i=1}^{2}\tfrac{1}{2}\Big(\tfrac{g_{A_i}}{2}+\tfrac{g_{B_i}}{2}\Big)}_{\text{每步同步：逐步跨卡平均再累加}} \;=\;\tfrac{1}{16}\sum_{k=1}^{16} g_k $$ 两条路线殊途同归——都是"16 条样本的平均梯度"，变的只是通信发生的时机与次数，不是数值。 浮点上会有 1e-7 量级的差（归约次序不同），训练意义上可忽略；变式练习里我们会把这个等式真算一遍。

修复后的代码只有四行（M13 你已见过它工作，现在看懂它）：

src/minimind_reborn/training/common/trainer.py · no_sync 梯度累积（fd9fdc8 引入）python
is_sync_step = (offset + 1) % t.gradient_accumulation_steps == 0 or is_last
# DDP 梯度累积：仅最后一个 micro step 同步梯度（training §3），其余步 no_sync
# 省掉 (accum-1)/accum 的 allreduce——64M×2B×8 步在 PCIe PHB 上实测拖累 scaling 至 67.6%
no_sync = getattr(self.model, "no_sync", None)   # 能力探测：仅 DDP 包装有此方法
sync_ctx = nullcontext() if (no_sync is None or is_sync_step) else no_sync()

with sync_ctx:                    # 注意：sync_ctx 已是上下文实例，不能再加调用括号
    with self.autocast_ctx:
        loss, log_metrics = self.compute_loss(batch, self.model)
    scaled = loss / t.gradient_accumulation_steps
    self.scaler.scale(scaled).backward()          # no_sync 里：只本地累加，不通信

三个细节。① 最后一步为什么必须放上下文外面？no_sync() 是 DDP 提供的 上下文管理器（with 块）：块内 backward 不同步。同步点就是第 N 步的 backward 本身—— 前 N−1 步包进 no_sync，第 N 步留在上下文外，这次 backward 触发全量 all-reduce， 把攒了 N 步的完整梯度一次性平均。若 N 步全包进去，梯度永远不同步：各卡各自更新各自的， 参数悄悄发散——不报错、loss 照样降，只是两台机器训出了两个不同的模型。 ② is_last 兜底：epoch 尾部凑不满 N 步的残批也强制同步一次，残批的梯度不许漏网。 ③ getattr(model, "no_sync", None) 是能力探测：单卡时模型没有 DDP 包装、 没有这个方法，探测到 None 就用 nullcontext()（空上下文）——单卡代码路径零分支。 这和 M13 的 build_scaler（恒创建 + enabled 开关）、fused 签名探测是同一个口味： 不问"我是谁"，只问"我有没有这个能力"。

实测：no_sync 有/无的 A/B 对照

说"通信量降 87.5%"不等于"快 8 倍"——通信只是每步开销的一部分。真跑才算数。 64M 模型、官方 64m 配方（seq 340 / batch 32 / 累积 8 / bf16），各跑 48 个 micro step、 每 8 步一个吞吐窗，取第 2~6 窗（丢弃首窗预热）的中位数。"关"的那一组不改仓库一行代码， 用一个 8 行的启动器猴子补丁（monkey patch：运行时替换对象方法）精确复现修复前行为：

⚠️ 坑卡：DDP 的两条铁律，违反哪条都不一定报错
  • 铁律一（M08 已验）：每个 requires_grad 参数每步都要参与前向——违反的下场是响的： RuntimeError（M08 玩具实验复现过），MoE 未路由专家靠"挂图"y[0,0]+=0·Σp 免费续命。 铁律二（本课）：每个 backward 默认触发全量同步——违反规范（该 no_sync 不 no_sync）的下场是 哑的：一切照跑，只有吞吐知道。
  • 两条铁律同源：DDP 的 reducer 在 backward 结束点做事，它不理解你的训练语义（累积、稀疏路由、 冻结参数），只认机械规则。规则一有守卫（报错），规则二没有——因为"多余但正确"的通信 在框架看来不算错误。
  • 规则一靠结构（挂图/或付 find_unused_parameters=True 的每步遍历税）；规则二靠度量： 双卡上线前跑一次单卡基线，算 scaling。<80% 就去找通信账。reborn 的 readiness 清单 把"单双卡对照"列为全量训练前置项，正是这次把 bug 揪出来的流程保证。

通用教训：①"程序能跑"≠"没有浪费"——最贵的浪费是不报错的浪费，它把 32% 的算力 蒸发在你眼皮底下；②度量先行——没有单卡基线，67.6% 这个数字根本不会被发现， 你只会觉得"双卡好像没快多少，可能本来就这样"；③多卡把一切口径放大：M13 的 LR 分母 （per_rank_full_iters）、M14 的跨卡数续训（checkpoint 存 world_size、加载时换算 step）、 本课的通信时机——单卡测不出、多卡才现形，是这条生产线的母题。

检验一下

测验 1 · all-reduce 平均的到底是什么？为什么平均完参数不会跑散？

答案：每个参数的梯度张量逐元素跨 rank 平均（g = (g₀+…+g_{w−1})/w）——不是 loss（loss 只是各 rank 的本地日志）、不是参数（参数从不搬运）、也不是激活。参数不跑散靠三"同"：起点逐位相同（同一份初始权重）+ all-reduce 后梯度逐位相同 + 同一份优化器代码做确定性更新——每步之后各 rank 的参数依然逐位相同，DDP 的全部工作就是守住"梯度相同"这一件事。

答错回看：数据并行 的四卡图与"三个词"段。

测验 2 · 累积 8 步时，为什么前 7 步包进 no_sync、最后 1 步必须留在上下文外？全包进去会怎样？

答案：DDP 的同步点是 backward() 本身：no_sync 块内的 backward 只本地累加、不通信；留在块外的第 8 步 backward 触发全量 all-reduce，把攒齐 8 步的完整梯度一次性平均（数学上与每步平均等价——线性运算可交换）。若 8 步全包进去，梯度永远不同步：每个 rank 用自己的本地梯度各自更新，参数从第一步起就悄悄发散——不报错、loss 照样降，只是多张卡训出了多个不同的模型，结果文件还只从 rank0 存一份，你以为训练"正常完成"。

答错回看：no_sync 的四行代码与三个细节之①。

测验 3 · rank0 门控 IO 防的是什么事故？metrics 后端的 NullBackend 和 train.py 里的 broadcast_object 各解决哪一侧？

答案：防多进程竞态写同一文件：两个 rank 同时追加 metrics.jsonl 会交错（step 序列失真——reborn 真实踩坑后加的门），同时 torch.save 同一权重会互相覆盖甚至写坏；atomic_save 防的是"写到一半被杀"（M14），防不了"两个写者"。NullBackend 是写侧：非 rank0 的指标后端直接换成空操作，从"不许写"升级到"没笔可写"。broadcast_object 是读侧：run_dir 由时间戳派生，各 rank 各取时间会得到不同目录，广播让全队用 rank0 的值——写侧门控 + 读侧对齐，合起来才是完整的单点写入。

答错回看：rank0 门控 IO 的落点表与坑卡。

测验 4 · 如果两个 rank 不用 DistributedSampler、各吃完全相同的数据，DDP 还能"正常"跑吗？损失什么？

答案：能"正常"跑——不报错、loss 正常。但两卡算出相同的梯度，all-reduce 平均后还是它，等效 batch 一点没变大：你付了双卡的算力和通信，得到的是与单卡相同的数据效率（纯浪费时间维度上的浪费）。DDP 不负责切数据，它假设 sampler 已切好——这就是 _build_loader 里 DistributedSampler 分支存在的全部理由，也是"数据并行"四个字里"数据"的分量。

答错回看：先切数据 小节第一段。

变式练习

🧪 变式 · 等效 batch 真算：2 卡 × batch 4 × 累积 2，等价于单卡 batch 16 吗？

M13 讲过单卡的等效 batch = batch_size × 累积步数；DDP 把 world 也乘了进来 （pretrain_64m.yaml 注释：等效 batch = 32 × world × 8）。现在把两条路线摆在一起算梯度。

写下预测：路线一（2 卡、每卡 batch 4、累积 2 步）一个 optimizer step 吃了多少条样本？ 路线二（单卡、batch 16、累积 1 步）——两条路线的梯度数值完全相同吗？只差随机性， 还是连"分片不等长"这种结构性差异都可能有？

/tmp/m15_equiv_batch.py · DDP"两层平均"vs 单卡"一层平均"（CPU 可跑）python
import torch

torch.manual_seed(42)
W = torch.randn(8, 3)            # 假装这是模型的全部参数
X = torch.randn(16, 3)           # 16 条样本
y = torch.randn(16, 8)

def mean_grad(xs, ys):           # 一批样本的最小二乘平均梯度
    w = W.detach().clone().requires_grad_(True)
    loss = ((xs @ w.T - ys) ** 2).mean()
    loss.backward()
    return w.grad

g_big = mean_grad(X, y)                                  # 路线二：单卡 batch16 累积1
g_a = mean_grad(X[:8], y[:8])                            # 卡 A：8 条平均（batch4×累积2）
g_b = mean_grad(X[8:], y[8:])                            # 卡 B：8 条平均
g_ddp = (g_a + g_b) / 2                                  # 路线一：all-reduce AVG
print("两层平均 vs 一层平均最大差：", (g_ddp - g_big).abs().max().item())

g_a2 = mean_grad(X[:10], y[:10])                         # 反例：不等分片 10+6
g_b2 = mean_grad(X[10:], y[10:])
print("不等分片时最大差：", (((g_a2 + g_b2) / 2) - g_big).abs().max().item())
观察结果与解释（先动手再看）

作者实测（2026-10-01，CPU）：

答案与机制：路线一一个 optimizer step 吃 2×4×2 = 16 条样本，等效 batch 16。 等分片时两路线梯度之差 6e-08——纯浮点噪声，数学上严格相等：(1/2)·((1/8)Σ_A + (1/8)Σ_B) = (1/16)Σ_全体的直接推论（§no_sync 推导卡的实例版）。 "等效"的精确含义：每个 optimizer step 的梯度数值等同（等分片前提），因此 lr、 grad_clip、优化器行为的语义完全一致。不等价的部分：①样本抽取路径不同—— 路线二全量打乱取 16 条，路线一是 sampler 切分后各卡各取 8 条，同一步吃到的具体样本不同， 训练轨迹不同但统计等价；②不等分片时两层平均 ≠ 全局平均（反例 0.117 的结构性偏差）， DistributedSampler 的 padding 正是为保证等分片而存在；③路线一多付通信、路线二多付显存—— 工程上选哪个，是吞吐/显存的权衡，不是数学的取舍。

本课词汇

数据并行 / DDP DistributedDataParallel
多卡训练的最底层形态：每卡一个进程、一份完整模型副本、不同的数据分片；各自前向反向，梯度 all-reduce 平均后各自更新，参数逐位保持一致。复制的是模型、切分的是数据；模型大到装不下才需要 ZeRO/FSDP 等切模型的技术。
rank / world size / local_rank
rank = 进程全局编号（0 起）；world size = 进程总数（MFU 分母里的 world）；local_rank = 本机内卡号（多机时才与 rank 不同）。torchrun 启动时经 RANK/WORLD_SIZE/LOCAL_RANK 三个环境变量注入，dist.py 靠探测 RANK 区分单卡/多卡。
all-reduce 集合通信
所有 rank 一起参与、结束时各自拿到同一结果的通信原语；DDP 用它对梯度逐元素求平均。同族还有 broadcast（rank0 的值发给所有人，如 run_dir 对齐）与 barrier（全员到齐才放行，cleanup 里用）。
torchrun 多进程启动器
PyTorch 自带的分布式启动器：一次命令拉起 N 个训练进程并注入 rank 环境变量。reborn 的 README 写"单卡去掉 torchrun 前缀即可"——init_distributed 探测不到 RANK 就回退单卡，同一份代码两种世界。
NCCL / gloo
NCCL：NVIDIA 的 GPU 通信后端（all-reduce 落到 NVLink/PCIe 的那层），torchrun+DDP 的默认选择，没有 GPU 时 init_distributed 显式报错不静默回退；gloo：CPU 可用的兄弟后端，M08 玩具实验用的就是它。
DistributedSampler
把样本下标按 rank 轮转均分（不整除时 padding 补齐，保证各 rank 等长分片）的采样器；每个 epoch 要调 set_epoch 换打乱种子。DDP 不切数据——不切则两卡吃同样 batch，等效 batch 不变、卡白买。
no_sync 梯度累积免同步
DDP 的上下文管理器：块内 backward 只本地累加、不 all-reduce。累积 N 步时前 N−1 步包入、末步留外，全量同步从 N 次降到 1 次（数学不变：平均与求和是线性运算可交换）。缺失时双卡 scaling 67.6%→修复后 88.5%（fd9fdc8）。
rank0 门控 单点写入
一切文件 IO 只许 rank 0 执行的纪律（_save/四件套/metrics 后端/日志文件四个落点；非 rank0 的 metrics 后端换成 NullBackend），防多进程竞态写同一文件；读侧用 broadcast_object 对齐 run_dir 等派生值。atomic_save 防"写到一半被杀"，防不了"两个写者"。
scaling 效率 多卡加速比
双卡 tok/s ÷（2 × 单卡 tok/s）。100% 是理论完美线性加速；2×4090（PCIe PHB、无 NVLink、混合卡）修复后实测 88.5%，剩余损耗来自互连带宽与快慢卡互相等待。判读前提：先有单卡基线（度量先行）。
