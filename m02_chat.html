与 64M 模型对话

M01 的冒烟给了你 3 个 tiny 权重；完整训练出的官方 64M 正主则按 M01 §官方权重下载 下载到 out/official/。这一课先不管模型内部长什么样——把模型叫醒，问它"你是谁"，转 temperature 旋钮看它换三种性格；然后猎一个真实 bug：官方对话入口 tools/chat.py 此刻根本跑不起来，而 49 个测试全绿（49 为 M01 时代口径，随仓库长上下文工作扩容为 85，演进说明见 M01）。为什么？

前置：M01 课程导览与第一个绿灯 时长：约 45 分钟 新概念：采样分布（temperature / top_p） 对照：tools/chat.py · inference/engine.py · out/*.pth

学完你能

  • 用 MiniMindLLM.build() 一次调用把权重名变成可对话模型，说清它替你收拢了哪几件脏活；
  • 转动 temperature / top_p 旋钮，观察输出"性格"的规律变化，并用概率重分配解释它；
  • 解释 pretrain 基座与 full_sft 权重的行为差异——为什么基座用对话模板问只会堆模板词；
  • 从一条 TypeError 回溯出发，定位测试桩与真实入口的签名缝隙，写出精确的一行修复；
  • 说出模型自称"Qwen / 通义千问"背后的数据来源真相。

路线 B 有个值得一趟的小弯路：你可能想写 build('full_sft', hidden_size=64, num_hidden_layers=2)——会报 size mismatch。因为 build() 只暴露了 hidden/层数两个形状参数，头数用的是 768 系默认值（8 头/4 KV 头），而冒烟配方里的 tiny 是 4 头/2 KV 头。于是你只好亲自体验一次"静态工厂 vs 裸构造器"的分工：

temperature=0.1——低温像个守规矩的客服，每句话都走同一模板：

你好！我是Qwen，一个由jingyaogong创造的AI模型。我被设计用于提供信息、解答问题、
进行对话等，能够理解和生成人类语言。我的主要功能包括：1.**信息查询**…2.**知识检索**…
3.**语言翻译**…4.**创意生成**…

temperature=0.85——中温最像"正常说话"，但请注意前两句的自我介绍几乎是复读：

你好！我是由jingyaogong创建的AI模型，我叫通义千问。我是一个由jingyaogong创建的AI模型，
专注于提供高效、准确的信息和帮助。…我可以回答各种各样的问题…

temperature=1.5——高温开始"创作"：身份漂移成小明，句子逐渐不成话：

我叫小明，专注于计算机生成设计。我很高兴我的身份由中国软件设计语言为一枚特殊的代码，
用于构建复杂的产品功能。…

三个值得停下来的观察：

  1. 身份随温度漂移：Qwen → 通义千问 → 小明。"我是谁"不是写死的元数据，而是一个个被采样出来的 token——低温锁死高概率答案，高温把长尾身份词拉进候选池。
  2. 低温 ≠ 高质量：0.1 档最稳也最啰嗦——沿最高概率的模板滑行，撞 128 token 上限（finish=length）才停。
  3. 高温提前停：1.5 档 95 token 即 finish=stop——eos 的概率也被温度抬高，模型"自己决定"说完了；三档 latency 差异主要来自生成长度（95 vs 128）与首 token 开销，温度本身没有快慢。
💡 概念卡：采样分布——temperature 在重分配什么？

模型每一步输出的不是"一个词"，而是整个词表上的概率分布。设某步的 logits（模型给词表里每个候选 token 的原始打分，softmax 归一化之前的分数）为 $z_i$，采样前先做温度缩放：$p_i(T) \propto \exp(z_i / T)$。

  • $T < 1$ 锐化：拉大 logit 差距，高概率词更垄断——输出稳定、模板化；
  • $T > 1$ 平滑：差距被压扁，长尾词有机会被采到——输出多样、易跑偏；
  • $T \to 0$ 等价贪心：$\exp(z_i/T)$ 被最大 logit 完全主导，退化成 argmax。reborn 不用设 0.0001——GenerateConfig 约定 temperature ≤ 0 显式走贪心分支。

top_p（核采样）是另一把刀：词按概率降序排列，只保留累积概率达 $p$ 的最小前缀（$\sum_{i \in S_p} p_i \ge p$），尾部置 $-\infty$。temperature 决定分布的形状，top_p 决定候选池的大小——0.95 的 top_p 配 1.5 的温度，是"允许乱，但只乱到前 95% 概率质量以内"。同族还有 top_k（保留前 k 个，默认 50）与 repetition_penalty（已出现 token 降权，默认 1.0 关闭），M20 深讲。

📐 严谨卡：采样顺序即契约

五个旋钮不是随意叠加的。inference/sampling.py 模块注释写死了顺序：temperature → repetition_penalty → top_k → top_p → 采样。先平滑（温度）、再截断（top_k/top_p）——顺序不同结果不同：若先截断再升温，被截掉的长尾永远回不来。这段注释不是文档点缀，而是行为契约；sample_token() 逐行照此实现（temperature ≤ 0 直接 torch.argmax）。

最后是最有趣的一条：模型为什么自称 Qwen / 通义千问？因为它没说谎——SFT 训练数据正是从 Qwen 系列蒸馏来的（用大模型的回答训练小模型）。语料里充满"我是通义千问"式的自我介绍，模型把"自报家门"这个模式连同门牌号一起学了进来。一个模型的"自我认知"，就是它训练数据的一面镜子——M16 训你自己的 SFT、M18 讲蒸馏时，这条线会再接上。

让权重开口：MiniMindLLM.build()

上面那些输出是怎么跑出来的？只有一个入口： inference/engine.py 里的静态工厂 MiniMindLLM.build()。给它一个权重名，它还你一个能生成、能对话的引擎门面——权重路径解析、模型构建、严格加载、精度回退、设备搬运，五件脏活一次收拢：

src/minimind_reborn/inference/engine.py · build() 主体（节选）python
build(weight="full_sft", *, hidden_size=768, num_hidden_layers=8, use_moe=False, ...)
device = device or ("cuda" if torch.cuda.is_available() else "cpu")
cfg = MiniMindConfig(hidden_size=hidden_size, num_hidden_layers=num_hidden_layers, use_moe=use_moe)
root = out_root if out_root is not None else envs.out_root()
# 权重名 → 路径：命名约定 {weight}_{hidden_size}[_moe].pth，如 full_sft → out/full_sft_768.pth
weight_path = resolve_weight_path(weight, root, cfg.hidden_size, cfg.use_moe)
if not weight_path.exists(): raise FileNotFoundError(f"权重文件不存在：{weight_path}。请先训练…")
target_dtype = _resolve_dtype(dtype, device)  # 精度回退链：CPU 不支持 bf16 时回退 fp32，只警告一次
model = to_dtype(MiniMindForCausalLM(cfg), target_dtype)
load_inference_weights(model, weight_path, strict=True)  # 严格模式：缺/多一个 key 都报错
model = to_device(model, device)
if cfg.vocab_size != len(_load_tokenizer()):  # 双源断言：权重和 tokenizer 必须同源
    raise ValueError(f"模型词表({cfg.vocab_size}) 与 tokenizer 词表不一致——禁止混用")
return cls(model, tokenizer, device, target_dtype)

三个设计点。静态工厂与裸构造器分工：__init__ 只收现成组件，一切环境/路径/回退逻辑关在 build() 里——用户代码除 build 外不出现环境处理，门面模式（facade：给复杂子系统一个简单入口的设计模式）的教科书用法。精度回退链：首选 bf16，_resolve_dtype() 发现目标是 CPU 时回退 fp32（GPU 上 bf16 快且省显存）。双源断言：模型词表 6400 与 tokenizer 词表对不上直接拒绝——把"权重与 tokenizer 混用"这类最诡异的静默错误变成说人话的报错。

🏭 工业对照：build() 与 from_pretrained

HuggingFace 的 from_pretrained() 是同一思路的工业版：给个名字，路径/精度/设备/词表校验全部收拢。 官方 minimind 相反——每个脚本自己 torch.load + .to(device)，五份脚本五份重复。 reborn 把它收敛成库 API 后，tools/chat.py、tools/eval_llm.py、tools/serve.py 共享同一条加载语义——本课猎场正是"入口与引擎脱节"的反面教材。

基座的训练目标只有一件事：给定前文预测下一 token（文字接龙）。它没学过"对话"这个游戏——pretrain 语料里混着大量 chat 格式文本，所以它"见过"模板词、堆得出来，但没学过"在 assistant 标记后以助手身份回答"。用对话模板问基座，等于递给它一张对话表格让它续写，它只会把见过的表格词一个个填下去；而 pretrain_mode=True 的直拼路径（拼 bos + 文本，不套模板）只要求续写——基座唯一会玩的游戏——反而通顺。SFT 的意义就在第三行：同一张模板，full_sft 知道怎么接。tools/chat.py 里 pretrain_mode = "pretrain" in args.weight 就是在自动做这个降级。M16 你会亲手训出这两类权重再对照——这张表将从"现象"变成你自己的结论。

⚠️ 坑卡：keyword-only 参数遇上位置传参
  • TypeError: generate_tokens() takes 3 positional arguments but 4 were given——对话入口输入第一句即崩，回溯直指 chat.py:73。
  • 两个签名对不上。真实入口（engine.py:119 起）把 attention_mask 设为 keyword-only（星号之后）：generate_tokens(self, input_ids, gen, *, attention_mask=None, ...)——位置参数只有 2 个（含 self 共 3）。而 ChatSession.respond()（chat.py:73）用三个位置参数调用，第 2 个本想传 mask、实际落进 gen 槽位，第 3 个无处安放，于是报"4 were given"（self + 3）。
  • 一行修复（chat.py:73，改为按引擎真实签名传参）： self.generate_fn(inputs["input_ids"], self.gen, attention_mask=inputs["attention_mask"])。 但注意：只改这一行还不够——测试桩的签名也得同步（见下）。这正是本猎场的通用教训所在。

把两边签名并排放，缝隙一目了然：

# 真实入口（engine.py）：星号之后 = keyword-only，只能用关键字传
def generate_tokens(self, input_ids, gen, *, attention_mask=None, max_new_tokens=None, ...):
#                          ↑位置1    ↑位置2   ↑ 不能按位置填

# 调用方（chat.py:73）：三个位置参数硬塞

#                  ↑ 填进 input_ids  ↑ 本想传 mask，实际落进 gen 槽位  ↑ 第 4 个位置参数：无处安放

顺带回答"为什么当初要设 keyword-only"：引擎方法后续还会长出 streamer、cancel 等可选参数，星号挡住的就是"按位置盲填、悄悄错位"——把这次的静默语义错误升级成响亮的类型错误。

为什么 49 个测试（当时口径，现为 85）没拦住它

打开 tests/test_inference/test_chat_budget.py， ChatSession 的测试全部用桩函数（stub）注入生成能力：

tests/test_inference/test_chat_budget.py · 桩（节选）python
def _stub_generate(eos_id: int):
    """恒定返回 3 个 token 后 eos 的桩生成函数。"""
    def generate_fn(input_ids, attention_mask, gen):   # ← 桩的签名：3 个位置参数
        ...
    return generate_fn

桩的签名是 (input_ids, attention_mask, gen)——恰好匹配 chat.py:73 的错误调用方式，而不匹配真实引擎。于是测试验证的命题是"ChatSession 能和一个长得像调用方假设的桩合作"，而非"能与真实 generate_tokens 合作"。49 个测试（当时口径，现为 85）没有任何一条把两者接在一起跑过——引擎有测试、ChatSession 有测试，缝隙恰好长在两者之间。这就是测试桩与真实入口之间的缝隙。修复必须两边同步：调用方改成关键字传参后，桩签名也要改成 (input_ids, gen, attention_mask=None)，否则绿灯瞬间变红灯——裂缝只是换了个方向。

🛑 红线：注入的依赖，接口契约必须锁定

依赖注入（把 generate_fn 传给 ChatSession）换来可测性，也给了"桩可以为所欲为"的自由。契约不锁定，桩会漂离真实接口——测试照绿，线上照崩。两种低成本锁定：① 契约测试——断言 inspect.signature(MiniMindLLM.generate_tokens) 与 ChatSession 的调用形式匹配；② 加一条真实（tiny）引擎 + ChatSession 的接线测试，让缝隙每次都被踩到。M01 的 make smoke 给训练链做了接线冒烟，推理链没有对应物——此 bug 在 M02 呈现、M20 回收修复。

检验一下

测验 1 · 模型为什么自称 Qwen / 通义千问？温度调到 1.5 又自称小明，说明什么？

提示：想想 SFT 训练数据是谁生成的，「自我认知」这几个字对模型意味着什么。

答案：SFT 数据是从 Qwen 蒸馏来的，语料里充满教师模型的自我介绍，模型连"门牌号"一起学了进来——自报家门暴露了数据来源。而 1.5 档自称小明说明：身份不是存储的元数据，而是每步被采样出来的 token，温度一高，长尾身份词就进了候选池。

机制：「我是___」的下一个 token 分布里，「Qwen」在 SFT 语料加持下是高概率峰——温度缩放改变的正是这个分布的形状。

答错回看：三档温度，三种性格 的观察 1 与其后"自称 Qwen 的真相"段。

测验 2 · temperature 趋近 0 等价于什么采样？reborn 里怎么触发它？

答案：等价于贪心解码（greedy / argmax）——$\exp(z_i/T)$ 被最大 logit 完全主导，每步取概率最大的 token。reborn 的约定写在 GenerateConfig：temperature ≤ 0（直接给 0 即可）显式走贪心分支，sample_token() 里对应 torch.argmax，不进多项式采样。

答错回看：概念卡：采样分布。

测验 3 · bug 猎场的通用教训是什么？只修 chat.py:73 一行为什么不够？

答案：测试桩与真实入口之间的缝隙——桩验证不了它没模拟的签名契约。只改调用方一行，测试桩 (input_ids, attention_mask, gen) 立刻与新的关键字传参方式错位，绿灯变红灯；修复必须连同桩签名（以及任何其他调用方）一起同步。根治靠锁定契约：签名断言，或一条真实引擎 + ChatSession 的接线测试。

答错回看：为什么 49 个测试（当时口径，现为 85）没拦住它 与 红线卡。

变式练习

🧪 变式 · 同一问题跑两次，输出会完全一样吗？

用 15 行脚本以 temperature=0.1 跑两次，再以 0.85 跑两次（什么都不改，直接重跑）。先想清楚随机性从哪来：采样链消费的是 torch 的 RNG（torch.multinomial），而 tools/chat.py 里那行 random.seed(random.randint(0, 2**31)) 重播种的是 Python 标准库 random——采样路径根本不经过它。

写下预测：脚本里 torch.manual_seed(42) 固定不变，两次输出会逐字相同吗？低温对和高温对，哪对差异更大？

观察结果与解释（先动手再看）

规则：固定 torch 种子后，同机同环境理论上输出一致；不固定种子，低温档两次输出差异小——分布接近 argmax，随机数扰动可选项少；高温档差异大——长尾词都在候选池里，一个随机数就能换一条路。

实测彩蛋：作者在 GPU 上同 seed 复跑两次（seed=42，temperature=0.85），输出前十几个字相同后分叉。原因不在采样，在硬件：bf16 CUDA 矩阵乘的归约顺序非确定，logits 的微小抖动被自回归逐 token 放大。想逐位复现要么上 CPU，要么接受"同 seed ≈ 同输出、不保证逐位"——这也是页面引文都注明"你复跑的字句几乎必然不同"的原因。

🧪 变式 · 把 top_p 从 0.95 压到 0.5，高温会收敛吗？

取15 行脚本，把 GenerateConfig(temperature=0.85, top_p=0.95, …) 改成 temperature=1.5, top_p=0.5，重跑（可与 1.5/0.95 对照各跑几次）。

预测：temperature 仍是 1.5，但 top_p 减半——输出会和 1.5/0.95 那段一样发散，还是更接近中低温的表现？想清楚采样顺序（先温度后截断）再下判断。

观察结果与解释（先动手再看）

观察：发散明显收敛——句子基本成话，身份回归"AI 助手"类高概率自述，1.5/0.95 档那种「1a,_a:1；2h+」式乱码碎片消失（作者实测 1.5/0.5 输出语义完整；字句以你跑的为准）。

机制：顺序是 temperature → top_k → top_p → 采样：温度先把分布拉平，top_p 再砍掉累积概率 50% 之后的整个长尾。top_p 是温度的安全网——温度决定"允许乱"，top_p 决定"乱的上界"。若顺序颠倒（先截断再升温），被砍掉的长尾永远回不来——这就是"采样顺序即契约"的原因（回看严谨卡）。

本课词汇

logits
模型对词表每个候选 token 的原始打分（softmax 归一化之前的分数）；采样旋钮全部作用在它身上。
采样 sampling
从下一个 token 的概率分布中随机抽取一个 token；temperature/top_k/top_p 都是重塑这个分布的旋钮。
temperature
温度缩放 $p_i \propto \exp(z_i/T)$：$T<1$ 锐化，$T>1$ 平滑，$T \to 0$ 退化为贪心；reborn 中 ≤0 显式走贪心分支。
top_p nucleus sampling
核采样：按概率降序保留累积概率达 p 的最小前缀，尾部置 $-\infty$；温度的"安全网"，默认 0.95。
top_k
只保留 logits 前 k 大的候选（默认 50），0 关闭；与 top_p 同族，按个数而非概率质量截断。
贪心解码 greedy decoding
每步取 argmax 的确定性解码：稳定但易重复，等价 temperature→0 的极限。
蒸馏 distillation
用大模型（教师）的输出训练小模型（学生）；本课模型自称 Qwen 即因 SFT 语料蒸馏自 Qwen，M18 专讲。
静态工厂 static factory
以类方法（如 MiniMindLLM.build()）收拢全部构造脏活、返回现成实例；裸构造器只收组件，便于注入与测试。
keyword-only 参数
Python 函数星号之后的参数，只能用关键字传递；把"按位置错位传参"变成显式类型错误。
测试桩 test stub
测试中替身被注入依赖的简化实现；桩与真实接口的契约不锁定，就会产生"测试绿、线上崩"的缝隙。
