关键事实：tokenizer + chat 模板是【训练侧与推理侧共用】的同一套东西——
训练时用它造样本，推理时用它拼 prompt；两边不一致，模型当场"听不懂外语"。

所以这两站值得单独一课：它们不在 models/ 目录（到 M09 为止的主战场）里，而在 assets/tokenizer/ （词表本体，两个 json）与 constants.py / inference/chat.py（常量与渲染入口）。 还是老节奏：先观测，再概念。

观测先行：同一把刀，切五段文本

M03 ①站见过一例：「你好，世界」→ [1968, 294, 1950]，5 个字符变 3 个 token。 现在把刀口放宽——英文、代码、生僻字、emoji 一起上，每段都真跑：

/tmp/m10_observe.py · 多组文本编码对比python
from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained("assets/tokenizer")  # reborn 词表加载点（engine.py 同款）
texts = ["你好，世界", "Hello, world!", "def add(a, b): return a + b", "龘", "你好🤖"]
for t in texts:
    ids = tok(t).input_ids
    pieces = [tok.decode([i]) for i in ids]             # 每个 token 单独还原成文本
    print(f"{t!r:30} {len(t)}字 {len(ids):2d} token  {pieces}")

五个观察，每个都往概念上推一步：

  • 中文最省：「你好，世界」5 字 3 token——常用词整块吞（你好 = 1 个 token，id 1968）。
  • 英文也还行：13 字符 4 token，但 Hello 占一个、空格归并给后一个词。
  • 代码最贵：27 字符 11 token——括号、冒号各自成 token，这份 6400 词表是中文语料训的，没怎么见过代码。
  • 生僻字退化：「龘」不在词表 → 退成 3 个 UTF-8 字节，其中两个字节又被合并成 1 个 token，共 2 个。
  • emoji 同理：🤖 = 4 个字节 → 3 个 token。token ≠ 字 ≠ 词——它是"这把刀学出来的片段"，长度由词表决定。
💡 直觉：tokenizer 决定模型的"阅读速度"与"视野颗粒度"

同样的内容，token 越多，占的上下文窗口越长（64M 模型训练窗只有 380，M05 讲过）——切得碎的语言/领域等于 "看同样一段话要花更多格子"。反过来 token 太长（整句一个 token）则泛化差。词表大小 6400 是教学级选择： 它同时决定 embedding 查找表的行数（6400 × 768 ≈ 4.92M 参数，weight tying 下输入输出共用一份，M09 的参数账本）， 词表不是越大越好，是"和语料匹配"才好。

概念卡 BPE：反复合并最高频的相邻对

💡 概念卡：BPE（byte pair encoding，字节对编码）

训练一个 BPE 词表只有一条规则：从最小字母表出发，数语料里所有相邻 token 对，把出现最多的那对合并成 一个新 token，加进词表；重复，直到词表满。"高频优先"保证有限的词表额度花在最常出现的片段上—— 中文语料里「你」后面几乎总跟着「好」，它们就该合成一个 token；「龘」百年一遇，留在字节层不亏。 编码新文本时，按训练时学到的合并顺序从左到右重放这些合并，得到最终切分。

手玩：8 行语料，跑前 3 轮合并

规则可以直接写成 30 行脚本。给 8 行迷你语料（7 个不同字符），看词表怎么"长出"「你好」：

/tmp/m10_bpe.py · 迷你 BPE（字符级教学版）python
from collections import Counter

corpus = ["你好世界", "你好小模型", "世界你好", "你好你好",
          "小模型你好", "你好世界模型", "模型世界你好", "你好小模型世界"]

seqs = [list(line) for line in corpus]                 # 每行拆成字符序列
vocab = sorted({ch for s in seqs for ch in s})         # 初始词表 = 出现过的字符
print("初始词表（%d）：%s" % (len(vocab), " ".join(vocab)))

for rnd in range(1, 4):                                # 只看前 3 轮
    cnt = Counter()
    for s in seqs:
        for a, b in zip(s, s[1:]):                     # 相邻对：滑窗一格
            cnt[(a, b)] += 1
    print(f"\n第 {rnd} 轮 · 相邻对频次 top3：{cnt.most_common(3)}")
    (a, b), c = cnt.most_common(1)[0]
    new_seqs = []
    for s in seqs:                                     # 把 (a,b) 全部换成长 token a+b
        out, i = [], 0
        while i < len(s):
            if i < len(s) - 1 and s[i] == a and s[i + 1] == b:
                out.append(a + b); i += 2              # 两枚旧 token 换一枚新 token
            else:
                out.append(s[i]); i += 1
        new_seqs.append(out)
    seqs = new_seqs
    vocab.append(a + b)
    print(f"  合并 {a}+{b} → 「{a+b}」→ 词表 {len(vocab)} 个")

print("\n3 轮后词表（%d）：%s" % (len(vocab), " ".join(vocab)))

📐 严谨卡：ByteLevel——为什么从字节起步，永不 OOV

ByteLevel（字节级）指先把文本的每个 UTF-8 字节映射成一个可见字符（256 种，空格变成 Ġ 之类）， 再在这个"字节字符"字母表上学 BPE——tokenizer.json 里 pre_tokenizer 字段的 {"type": "ByteLevel"} 就是这一步（它同时解释了 ' world' 的空格为什么并进词首：空格先变成普通字符，就能参与合并）。 收益是一句话：任何 Unicode 文本都能表示成字节序列，所以没有切不开的文本—— 传统词级 tokenizer 遇到词表外的词只能吐 <unk>（OOV，out-of-vocabulary）， 字节级 BPE 结构上消灭了 OOV：没见过的「龘」「🤖」退化成几个字节 token，照切照还原，只是贵一点（观测表第 4/5 行）。

36 个特殊 token 与三大常量

词表里有 36 个 token 不是合并学出来的，是人工指定、整串占用一个 id 的标记——特殊 token （special tokens）：不参与 BPE 合并、渲染时原样占一个位置。三个最重要的常量写死在 constants.py （全文 18 行，M03 ①站见过注释版）：

src/minimind_reborn/constants.py · 全文python
"""全局常量：特殊 token、模型默认值。

只放"代码自身无法推导"的固定语义；可调参数一律走 configuration。
"""

from __future__ import annotations

# ===== 特殊 token（与官方 minimind tokenizer 完全一致，保证权重与数据互通） =====
PAD_TEXT = "<|endoftext|>"
BOS_TEXT = "<|im_start|>"
EOS_TEXT = "<|im_end|>"

# ===== SFT/DPO loss mask 的区间标记模式 =====
# chat template 渲染后 assistant 回答总是夹在 "<|im_start|>assistant\n" 与 "<|im_end|>\n" 之间，
# loss mask 依赖对这两个 token 序列的模式匹配（data/loss_mask.py），这是全系统最脆的耦合点，
# 由 tests/test_data/test_loss_mask.py 逐 token 断言锁定。
ASSISTANT_PREFIX_TEXT = f"{BOS_TEXT}assistant\n"
RESPONSE_SUFFIX_TEXT = f"{EOS_TEXT}\n"

三个常量各司其职（pad/bos/eos 在 M03 一句话带过，这里正式定义）：pad（padding，填充）凑批时把短序列 填到同长用的占位符；bos（begin of sequence）标记序列开始；eos（end of sequence）标记结束—— 它是 M03 ④站"停止三重"的靶子，生成循环一见到它就停。36 个特殊 token 全景分三类：

类别成员（id 区间）64M 文本模型用到的
对话三常量<|endoftext|>(0) · <|im_start|>(1) · <|im_end|>(2)全部——模板与凑批的地基
工具与思考<tool_call>(21)…</tool_response>(24) · <think>(25) · </think>(26)<think> 对（模板每轮都渲染）
多模态与预留vision/audio/tts 系列（3–20）· <|buffer1..9|>(27–35)零个——纯文本模型用不上

[事实核对] id 与分类逐一来自 tokenizer_config.json 的 added_tokens_decoder（36 条，id 0–35）与 additional_special_tokens 列表；注意 <think>/<tool_call> 一组在配置里 "special": false——它们是"普通 token 待遇的特殊写法标记"，decode 时不会被 skip_special_tokens 跳过。

两个容易踩的混淆，一次说清：① pad ≠ eos。这份词表里 pad 用 <|endoftext|>、eos 用 <|im_end|>，刻意分开——eos 身兼三职（停止靶子、assistant 回答收尾、loss mask 的后缀锚点）， 而 pad 出现在每个凑批的填充位；若让 eos 兼任 pad，填充位与真实结尾在 token 层无法区分：采样一撞填充就提前停、 监督区间也会错位。<|endoftext|> 从不出现在对话协议里，兼任 unk（未知词兜底）也安全。 ② 模板词不是特殊 token。「user」「assistant」就是普通字符串，照样挨 BPE 的刀——见下一节。

🏭 工业对照：词表是"家族遗产"

36 个特殊 token 里近半是 vision/audio/tts——reborn 词表与官方 minimind 一致，而官方又继承自 Qwen 系： 多模态预留 token 在纯文本小模型里原样带着，换来的是与整个家族工具链的互通。工业词表按语料定制 （Qwen 主力词表约 15 万，中文、代码、多语言各自配额）；6400 是教学级取舍：embedding 行数少（参数省）、 但切英文/代码偏碎（观测表第 3 行）。词表一旦定下，权重、数据、模板全体绑定——这正是下一节的主题。

chat 模板即代码：一份写进配置的对话协议

M03 ②站的 render_chat 当时只看了一眼：消息列表进、带特殊标记的文本出。现在回答"模板到底是什么"： chat 模板是把 messages（role/content 列表）渲染成模型训练时见过的固定格式的协议， 物理形态是 tokenizer_config.json 里的一个字符串字段——一段 Jinja2 模板（Jinja2：Python 生态的标准模板引擎，transformers 内置渲染器，{%- if %} 是它的分支语法）。关键分支节选 （原文件是单行字符串，这里排版便于阅读）：

assets/tokenizer/tokenizer_config.json · chat_template 节选（Qwen 风格）text
{# user/system 消息：整段夹进 im_start/im_end 对 #}
{{- '<|im_start|>' + message.role + '\n' + content + '<|im_end|>' + '\n' }}

{# assistant 消息：回答前永远渲染一段 think 结构，结尾 im_end + 换行 #}
{{- '<|im_start|>assistant\n<think>\n' + reasoning + '\n</think>\n\n' + content }}
{{- '<|im_end|>' + '\n' }}

{# add_generation_prompt=True 时：递话头。open_thinking 决定 think 段是"留白"还是"空块" #}
{%- if add_generation_prompt %}
    {{- '<|im_start|>assistant\n' }}
    {%- if open_thinking %} {{- '<think>\n' }}
    {%- else %}          {{- '<think>\n\n</think>\n\n' }}
    {%- endif %}
{%- endif %}

渲染入口只有一层薄壳——inference/chat.py 的 render_chat（chat.py:10），把参数原样透传给 tokenizer（模板进 config、渲染走 transformers， 单一事实源）：

src/minimind_reborn/inference/chat.py · render_chat 全文python
def render_chat(
    tokenizer,
    messages: list[dict[str, Any]],
    *,
    tools: list | None = None,
    open_thinking: bool = False,
    add_generation_prompt: bool = True,
) -> str:
    """消息列表 → chat template 文本。模板进 tokenizer_config.json（单一事实源）。"""
    return tokenizer.apply_chat_template(
        messages,
        tokenize=False,
        add_generation_prompt=add_generation_prompt,
        tools=tools,
        open_thinking=open_thinking,
    )

为什么模型必须见到和训练时一模一样的模板

把协议按 token 拆开看（用观测节同款单 id 解码）：<|im_start|>=1、user=[832, 311] 两个 token、assistant=[1388, 570, 811] 三个 token、\n=234、 <think>=25。也就是说，模板本身就是一串具体的 token 序列。M02 那张对照表里 pretrain 基座"堆模板词"（把 <|im_start|>、user 之类一个个往外蹦）的现象至此得到解释： 基座在预训练语料里"见过"这些 token 组合、能续写它们，但没学过"在 assistant 标记之后以助手身份回答"—— 模板于模型是一门语言：训练时它定义了"什么前文之后该说什么"，推理时换一个字，等于让模型听外语。 这也决定了模板必须进 config 而不是散在代码里：训练侧造样本（M12）与推理侧拼 prompt 走同一个 render_chat → 同一份模板字符串，两边永不漂移；改模板 = 改协议 = 数据重造 + 模型重训。

实验：同一个 API，四种渲染

两个开关各翻一次，行为差异全在输出里（真跑）：

from minimind_reborn.inference.chat import render_chat
from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained("assets/tokenizer")
u = [{"role": "user", "content": "你好"}]

for tag, kwargs in [
    ("A 默认 add_generation_prompt=True（推理侧）", {}),
    ("B add_generation_prompt=False（训练侧）", {"add_generation_prompt": False}),
    ("D open_thinking=True（think 留白，M20 再见）", {"open_thinking": True}),
]:
    text = render_chat(tok, u, **kwargs)
    print(tag)
    print("  ", repr(text), f"→ {len(tok(text).input_ids)} token")

hist = u + [
    {"role": "assistant", "content": "我是 minimind。"},
    {"role": "user", "content": "你会什么？"},
]
print("C 带 history（旧轮次原样铺在前面，结尾仍递话头）")
print("  ", repr(render_chat(tok, hist)))

四行对照读三件事：A vs B——add_generation_prompt（是否在结尾追加 assistant 话头）是 推理与训练的分界：推理侧 True，把"该 assistant 说话了"的语境递给模型；训练侧 False，得到的是完整一轮—— B 再接一段回答就是 M12 SFT 样本的样子，模型要学的正是"给定前文续写这一轮"。C——多轮对话没有魔法， 旧轮次按同一格式原样铺在前面（ChatSession 的 history 列表逐轮 append，M03 ②站伏笔）。 D——open_thinking=True 把空 think 块换成开着的 <think>\n：模型被允许先"想"再答， 生成结束后 split_reasoning（chat.py:28）把 think 段拆出来——推理行为实验 M20 再展开。

模板即代码的锁定：prefix/suffix 测试

constants.py 注释说 loss mask 是"全系统最脆的耦合点"。loss mask（损失掩码：只对 assistant 回答区间算损失、 其余位置填 -100 忽略——M12 详讲）的工作方式是逐 token 扫描：在渲染产物里找 ASSISTANT_PREFIX_TEXT = "<|im_start|>assistant\n" 开头、RESPONSE_SUFFIX_TEXT = "<|im_end|>\n" 收口的区间，区间内才是要学的回答。它成立的前提是：模板永远恰好产出这两个锚点序列——这就是"模板即代码" 的含义：模板不是文档，是一段有测试锁定的行为契约。tests/test_data/test_loss_mask.py 的前两个用例锁的就是地基：

坑卡：把模板写成 f-string 手拼

⚠️ 坑卡："格式看起来一样"的手拼模板，token 层面已经全变
  • 症状极隐蔽：手拼的 prompt 肉眼看和真渲染一模一样，模型也能生成——只是效果莫名变差； 更毒的是训练侧：loss mask 扫不到 prefix 锚点，监督区间静默变空，模型一个 token 都没学， 训练 loss 正常下降（在学别的位置），烧完卡才发现。
  • 模板是逐字符的协议，f-string 手拼两处必错：漏件与空白。真跑对照（脚本见下）——手拼版漏了空 think 块， 与真模板的共同前缀 12 位后分岔：真 18 token，手拼 12 token；另一个版本只在 assistant 后多打一个空格，结尾 token 变成 2615（' \n'）而非 234（'\n'）， prefix 锚点 [1, 1388, 570, 811, 234] 从此在序列里再也对不上。
  • 一条红线：拼 prompt 永远走 render_chat，模板永远住 tokenizer_config.json—— 一处定义、训练推理共用、测试锁定（test_loss_mask.py 7 个用例就是这份协议的回归网）。想改格式？ 改模板字符串本身，然后数据重造、模型重训——不存在"只在推理侧微调一下"这个选项。

检验一下

测验 1 · BPE 为什么从字节级（256 个基础符号）起步，而不是直接用"汉字"或"英文单词"？

答案：覆盖性。任何 Unicode 文本都能表示成字节序列，所以基数恒为 256 的字母表切得开一切文本——生僻字「龘」退成 2 个 token、emoji 退成 3 个，永不 OOV。按"字"起步则英文/emoji 处理不干净且生僻字直接缺位；按"词"起步词表爆炸且未见词无法表示。常用片段交给"高频合并"长回单 token（你好 = 1968）——起点保证切得开，合并保证切得省。

答错回看：概念卡 BPE 与 词表账本 / ByteLevel 严谨卡。

测验 2 · chat 模板为什么住在 tokenizer_config.json 里，而不是写成代码里的 f-string？

答案：单一事实源。训练侧造样本（M12）与推理侧拼 prompt 走同一个 render_chat → 同一份模板字符串，两边永不漂移；模板与 tokenizer 版本一起分发、一起被 test_loss_mask.py 锁定，这是 HF（Hugging Face，transformers 的出品方，M03 ①站的"HF tokenizers"即其分词库）生态的标准做法。散在代码里必然出现两处实现——坑卡实测：手拼版与真模板共同前缀 12 位后分岔（18 vs 12 token），训练推理一不一致，模型等于被换了一门语言。改模板 = 改协议，须数据重造 + 重训。

答错回看：为什么必须一模一样 与 坑卡。

测验 3 · pad 为什么用 <|endoftext|>，而不能让 eos（<|im_end|>）兼任？

答案：eos 身兼三职：生成停止三重的靶子（M03 ④站）、assistant 回答的收尾标记、loss mask 的 suffix 锚点；pad 只干一件事——凑批填充。若 pad=eos，填充位与真实结束在 token 层无法区分：采样撞到填充就提前停、监督区间会错位。让从不出现在对话协议里的 <|endoftext|> 当 pad（顺带兼任 unk），两种语义彻底分开。

答错回看：36 个特殊 token 与三大常量。

测验 4 · add_generation_prompt=False 渲染出来的文本是给谁用的？

答案：训练侧。False 得到"完整一轮"（B 例 7 token，回答以 <|im_end|>\n 收尾），正是 M12 SFT 样本的形态：loss mask 靠它的 prefix/suffix 锚点扫出监督区间，模型学"给定前文续写这一轮"。推理侧恒为 True——追加 assistant 话头把语境递给模型（A 例 18 token）。

答错回看：四种渲染实验 与 prefix/suffix 测试。

本课词汇

BPE byte pair encoding
字节对编码：从最小字母表出发，统计语料中最高频的相邻 token 对并合并为新 token、逐轮扩充词表，直到词表满。高频优先保证额度花在最常见片段上；编码新文本时按学到的合并顺序重放。
token / 词表 vocab
token 是 tokenizer 切出的片段（≠ 字 ≠ 词，见 M03 ①站）；词表是全部 token 的清单，同时决定 embedding 行数。reborn 词表 6400 = 256 字节 + 6108 合并 + 36 特殊。
ByteLevel 字节级
先把文本映射成 256 种字节字符再学 BPE 的做法（pre_tokenizer 的 {"type": "ByteLevel"}）；空格并进词首（' world'）也源于此。任何 Unicode 文本都可表示为字节，结构上消灭 OOV。
OOV out-of-vocabulary
词表外的词。词级 tokenizer 遇到只能吐 <unk>；字节级 BPE 里没有这个概念——生僻字/emoji 退化为几个字节 token，照切照还原（龘 → 2 token，🤖 → 3 token）。
特殊 token special tokens
人工指定、整串占一个 id、不参与 BPE 合并的标记，共 36 个：对话三常量（pad/bos/eos）、工具与思考（<think> 等）、多模态与 buffer 预留（Qwen 家族遗产，文本模型不用）。
chat 模板 chat template
把 messages（role/content 列表）渲染成模型训练时格式的协议，物理形态是 tokenizer_config.json 里的一段 Jinja2 字符串（Qwen 风格 <|im_start|>role\n…<|im_end|>\n）。训练与推理共用同一份——模板即代码。
add_generation_prompt
