checkpoint 六件套与续训

M13 把训练循环点着了，结尾留了一个问题：训练到一半机器挂了怎么办？ M01 你已经"不小心"见过答案——第二次 make smoke 时那段 续训恢复清单日志。本课拆开那份清单背后的 checkpoint 六件套， 再亲手 kill -9 一次训练，验证它真的接得住。

前置：M13（引擎已在转；M09 的权重三语义本课从训练侧再看） 时长：约 70 分钟 新概念：训练状态（checkpoint 语义） 对照：training/common/checkpoint.py · utils/io.py · docs/pretrain_readiness.md

  • 逐件说出六件套各防哪种灾难——为什么"只存权重"续训时是"重新开始装作接着练"；
  • 解释 RNG 四态（torch / cuda / python / numpy）各管哪路随机性，存了换来什么；
  • 说出原子写防的事故（写到一半被杀不产生半个 checkpoint），分清 fp16 推理权重与 fp32 六件套两种文件的职责；

训练状态：六件套逐件清点

M13 结尾说过，Trainer 每 epoch 末（以及每 save_interval_steps 步）都在默默调 _save。它写两个文件：out/pretrain_64.pth（M09 见过的 fp16 推理权重）和 checkpoints/pretrain_64_resume.pth——本课的主角。 checkpoint（检查点/存档）这个词 M01 就出现过，本课给它精确含义： 它存的不是"模型"，是训练状态（training state）——把训练进程在某一刻的 全部可变状态打包，使得另一个进程能在之后恢复出"同一时刻"接着练。 模型权重只是其中一件。 training/common/checkpoint.py 全文 96 行，payload 的组装只有一个字典：

src/minimind_reborn/training/common/checkpoint.py · save_checkpoint 的 payloadpython
raw = unwrap_model(model)          # 剥掉 DDP/compile 壳（M09 同款；分布式的包装不进文件）
payload = {
    "model": raw.state_dict(),    # 件 1：全部参数（fp32 主权重——AMP 只在算子层降精度，
                                  #        参数本体始终 fp32，M13 讲过"主副本"）
    "optimizer": optimizer.state_dict(),   # 件 2：AdamW 每参数的动量 m 与二阶矩 v（M13）
    "scaler": scaler.state_dict() if scaler is not None else None,   # 件 3：fp16 的 scale 水位
    "epoch": epoch,               # 件 4a：进度——本轮序号（存 0 基；日志显示 1 基）
    "step": step,                 # 件 4b：进度——本轮内已走 micro step 数（M13 的两种"步"）
    "world_size": get_world_size(),        # 存档时的进程数（载入时重标定用，见下节）
    "config": config_snapshot,    # 件 5：配置全量快照（M04 的 snapshot，事故取证用）
    "best_val_loss": best_val_loss,        # 件 6：最优验证损失（M13 的 best 语义从这里活着跨进程）
    "rng": _rng_state(),          # 第七件（附加）：四路随机数状态，位精确续训的钥匙
}
return atomic_save(payload, path)          # 原子写（下节）

先坦白一个数数问题："六件套"是口称，仓库里两处官方清单口径不同—— checkpoint.py 的模块 docstring 列了七项（含 RNG）， test_common.py 的用例名注释把 RNG 计入六件而漏列 scaler。本课按上面代码块的实际分组来： 六件套 = ①~⑥，RNG 是雷打不动的第七件（附加），payload 落盘实测 9 个顶层键。 名字不重要，重要的是每一件都有明确职责。 逐件问"为什么"。关键思想是：训练进程的可变状态不止权重一处。 只存权重（件 1）续训，其余全部归零—— AdamW 的动量与二阶矩从零重建 （M13 讲过它们是按步累积的滑动平均，重建等于告诉优化器"你失忆了"）， lr 调度进度、best 指标、数据顺序全部从头再来。这样的续训不是"接着练"， 是"重新开始装作接着练"：loss 不会崩，但会先抖一段——灾难在几万步的真实训练里才显形。 每件缺了会怎样，一张表说清：

件内容缺了续训会发生什么
① modelstate_dict 全部参数（fp32）权重回随机初始化，全部白练——最不可能忘的一件
② optimizer每参数的 m / v、分组超参动量失忆：头几十步更新量失衡（M13 warmup 存在的同一原因），loss 先抖后稳
③ scalerfp16 的 scale 水位与跳步计数scale 从 65536 重新探测；bf16（enabled=False）时此件为空字典，无感
④ 进度 epoch+step走到哪个 epoch 的第几 micro step从 epoch 0 step 0 重跑：lr 调度重走 warmup、数据顺序重头、已练步数重复计费
⑤ config 快照当时的全量配置（M04 snapshot）事故后无法回答"存档时是什么配方"——猎场二的事故本可用它拦下
⑥ best_val_loss历史最优验证损失best 归 None：下一个 val 无论多差都刷新"最优"，_best 权重被烂权重覆盖
附加 rngtorch/cuda/python/numpy 四路随机数状态一切吃全局随机流的操作跳到另一条轨迹：SFT 的随机系统提示注入（python）、dropout>0 的掩码、RL 采样（torch）；batch 打乱顺序本身不吃全局流——M15 见过它由显式 Generator 按 seed+epoch 重放

RNG 四态：把"随机"也存下来

RNG（random number generator，随机数发生器）M01 的环境指纹里见过它（seed: 42）， M13 结尾也预告过。设种子只保证"从零开始时序列一致"；训练进行到第 30 步时， 各路 RNG 已被消耗了 30 步的量——续训进程若不接住这些状态，后续随机数就从"另一个平行宇宙"来。 checkpoint.py 用 8 行收齐四路：

src/minimind_reborn/training/common/checkpoint.py · _rng_state 全文python
def _rng_state() -> dict[str, Any]:
    return {
        "torch": torch.get_rng_state(),            # torch CPU 全局流：dropout>0 的掩码、生成/采样
        "cuda": torch.cuda.get_rng_state_all() if torch.cuda.is_available() else None,
                                                  # 每块 GPU 一份（实测 list[2]：本机两卡都存）
        "python": random.getstate(),               # python random：SFT 数据集的随机注入走这条
        "numpy": np.random.get_state(),            # numpy：部分第三方库的默认随机源
    }

谁在消耗这些流？本仓库里最具体的一例：SFT 数据集按比例随机注入系统提示、 随机丢弃思考段（datasets.py 用 random.random()）——同一个样本在续训前后 可能一个带系统提示一个不带。四路各自独立、互不感知，少存一路，那一路就静默分叉。 注意一个诚实的边界：pretrain 的 batch 打乱顺序不吃全局流——M13 见过 _build_loader 用显式 Generator 按 seed+epoch 重放， 这正是 SkipBatchSampler 能对齐的前提；全局 RNG 管的是"顺序之外的随机性"。 恢复侧 _restore_rng 还有一个防御细节：CUDA 状态恢复失败（比如存档时 2 卡、 恢复时 1 卡）不炸，打警告"继续但不再位精确"。位精确（bit-exact）： 恢复后每一步的随机数与原进程在同一时刻产生的逐位相同——这是"接着练"的最强形式。 载入时你会看到它的日志证据：RNG 状态已恢复（位精确续训）。

原子写：.tmp + os.replace

六件套 6.44 MB（64M 模型 731 MB）的文件，写一半要几十毫秒到几秒。 如果直接写目标路径，写到一半进程被杀——磁盘上留下半个文件： 头部说"我是六件套"，尾部数据是旧的或空的。下次续训加载它， 轻则报错，重则把损坏数据当真。原子写（atomic write，M09 词汇表见过一句话定义） 让"换新文件"这个动作不可分割。reborn 的实现只有 12 行：

src/minimind_reborn/utils/io.py · atomic_save 全文python
def atomic_save(obj: Any, path: str | Path) -> Path:
    """torch.save 的原子版本：先写 .tmp 再 os.replace（同目录保证原子性）。"""
    path = Path(path)
    path.parent.mkdir(parents=True, exist_ok=True)
    tmp = path.with_suffix(path.suffix + ".tmp")   # pretrain_64_resume.pth → ….pth.tmp
    import torch
    torch.save(obj, tmp)                           # 慢操作全部发生在临时文件上
    os.replace(tmp, path)                          # 快操作：一步改名，目标路径"瞬间"换新
    return path

两个"为什么"。为什么 os.replace 是原子的？它对应操作系统内核的 rename 调用， 只改目录项里的一条记录（"这个名字指向哪个文件"），不动数据块——内核保证这一步 要么完成要么没发生，不存在"改了一半的名字"。为什么 .tmp 必须同目录？ rename 的原子性只在同一文件系统内成立；跨文件系统（如 /tmp 与数据盘）会退化成 "复制+删除"两步，原子性破产。所以临时文件用 path.with_suffix(...) 生成， 天生与目标同目录。被杀时最坏情况是留下一个孤儿 .tmp（无害，可清理）， 目标路径要么是完整的旧档、要么是完整的新档。

三语义：resume / init_from / finetune_from

M09 从权重层讲了 strict 与 finetune 两种加载；本课从训练侧看它们如何被三个入口消费。 Trainer 构造的最后一步 _load_initial_weights（trainer.py:422）按固定顺序探测三个配置：

src/minimind_reborn/training/common/trainer.py · _load_initial_weights（裁剪）python
if t.finetune_from:                        # 语义一：微调起点——结构允许不同
    load_finetune_weights(self.raw_model, path)     # 非严格 + 逐 key warning（M09）
    logger.info("微调加载（非严格，缺失 key 已逐条 warning）：%s", path)
if t.init_from:                            # 语义二：严格起点——结构必须完全一致
    load_inference_weights(self.raw_model, path, strict=True)   # M01 冒烟 DPO 段
    logger.info("严格加载起点权重：%s", path)                  #   "严格加载起点权重"就是它
# 铁律 8：续训做成默认行为——checkpoint 在场即恢复

注意 resume 的模型件用的是 strict=True：续训的对象必须与存档逐键同一结构—— 这是它与 finetune 的本质区别（finetune 允许长出新增模块）。 另一个训练侧特有的细节在 load_checkpoint 里：换卡数重标定。

src/minimind_reborn/training/common/checkpoint.py · load_checkpoint 的换算段python
data = torch.load(path, map_location="cpu", weights_only=False)
saved_ws = data.get("world_size", 1)          # 存档时的进程数（world：M15 详讲，本课=卡数）
current_ws = world_size if world_size is not None else get_world_size()
if saved_ws != current_ws:                    # 2 卡存的档换 1 卡续（或反过来）：
    data["step"] = data["step"] * saved_ws // current_ws   #   按吞吐折算等效进度
    logger.info("GPU 数量变化（%d→%d），step 已换算为 %d", saved_ws, current_ws, data["step"])
if "rng" in data:
    _restore_rng(data["rng"])                 # RNG 在读档时就地恢复（不等人调用）
    logger.info("RNG 状态已恢复（位精确续训）")

2 卡各跑一半样本，1 卡要全跑——同样 100 步的"工作总量"差一倍，step 必须换算才不虚报进度。 test_checkpoint_six_pack_roundtrip 把这个语义钉死：存档 step=7、world=1， 以 world=2 读回断言 step == 3（7×1//2）。LR 调度随之自然对齐—— 因为 M13 讲过它是只吃步数的纯函数。

🔍 bug 猎场一：续训记账漂移——len 的两副面孔

上面那份 0.67% 的漂亮报告，是 2026-09-24 kill -9 实验的产出；同一个实验还产出了一个 bug。 报告原文记得很克制："实测发现并修复 1 个续训记账 bug"——断点落在 epoch 中间时， 续训进程把这个 epoch 的总步数算小了：全局步数分母、LR 总步数、尾批 is_last 判定三处全部漂移，尾批的部分累积甚至会被当完整优化步消耗掉。

病根是 iters 的两副面孔。M13 的 SkipBatchSampler 为了"跳过前 k 个 batch"， 它的 __len__ 返回扣减后的本次实际迭代数（total - skip， trainer.py:65）——这是循环终点的正确语义。但旧代码把同一个数又当成了 epoch 全长：续训从 step 30 恢复时 iters=全长−30，于是 global_micro = epoch * iters + offset 的分母每 epoch 短一截、 LR 余弦的 total_micro 跟着缩水、尾批判定 is_last = offset == iters - 1 提前触发——部分累积的梯度在错误的"最后一步"被当成完整优化步消耗掉。 单元测试测不到它（iters 只有在"断点在 epoch 中间"时才有两副面孔）， 全量实测才现形。修复是另立一把只量全长的尺子：

src/minimind_reborn/training/common/trainer.py · 修复后的双轨记账python
# 完整 epoch 步数（不扣 skip）：全局步数记账/LR 调度的分母必须用它。
# iters 是"本次实际迭代数"（续训时 = 完整步数 - start_step），只用于循环结束判定。
full_iters = per_rank_full_iters(len(self.train_ds), t.batch_size, dist.get_world_size())
...
global_micro = epoch * full_iters + offset        # 记账：全长尺
...
is_last = offset == start_step + iters - 1        # 循环终点：实际迭代尺（注意 +start_step）

回归锁定：修复语义后来又叠了一层——per_rank_full_iters（trainer.py:82） 把 DDP（多卡数据并行，M15 详讲）下每卡只分 1/world 样本的口径也折进分母， 这是 M13 猎场外讲的"2026-09-29 perf_analysis 案 B"（双卡余弦到不了地板）； 本课实验里 step 换算（step × saved_ws // current_ws）是它在 checkpoint 侧的镜像。 通用教训：一个量两副面孔，迟早有人拿错——"len(loader)"在同步迭代时是全长、 在跳批续训时是余量，谁消费它谁就要声明自己要的是哪一副；修复的方式不是给 len 加参数， 而是让两个语义各自得名（full_iters / iters），名字即文档。

检验一下

测验 1 · 为什么 RNG 状态也要存？四路各管什么，不存最直接的后果是什么？

答案：四路随机源互相独立：torch（CPU 全局）、cuda（每卡一份）、python random、numpy。本仓库里最具体的消费者是 SFT 数据集的随机系统提示注入（random.random()）；更广地说，dropout>0 的掩码、RL 采样都吃这些流。不存的话，续训进程的 RNG 从头起步：同一步消耗的随机数与原进程不同——同一个 SFT 样本可能一个带系统提示一个不带，"位精确"破产。（batch 打乱顺序倒不吃全局流：它由显式 Generator 按 seed+epoch 重放，SkipBatchSampler 对齐靠的正是它。）存 RNG 换来的是"接着练"的最强形式：恢复后每一步的随机数与原进程逐位相同。

答错回看：RNG 四态 与 六件套表格 的附加 rng 行。

测验 2 · 同一个结构对不上的权重文件，init_from（严格）和 finetune_from 分别发生什么？resume 的模型件用的是哪种？

答案：init_from 走 load_inference_weights(strict=True)：启动前一秒 RuntimeError（"N 个缺失 key / M 个多余 key"），fail-fast；finetune_from 走非严格加载：不炸、缺失 key 保持初始化继续训练，但必须逐 key 打 warning——"静默吞键是最危险的『成功』"（M09 原话）。resume 的模型件是 load_state_dict(strict=True)——严格路线：续训对象必须与存档逐键同构，因为它的承诺是"同一训练的下半场"，长出新模块就属于另一种语义（finetune）。

答错回看：三语义 的对照表。

测验 3 · 原子写防的是什么事故？为什么 os.replace 是原子的、.tmp 为什么要与目标同目录？

答案：防"写盘进行到一半进程被杀"：直接写目标路径会留下半个文件（头部合法、数据残缺），下次续训加载坏档。原子写把慢操作全部发生在 .tmp 上，最后用 os.replace 一步改名——它对应内核的 rename，只改目录项一条记录，要么完成要么没发生。.tmp 必须同目录（同文件系统）：rename 的原子性只在同一文件系统内成立，跨文件系统会退化成"复制+删除"两步。被杀的最坏遗产是一个孤儿 .tmp（本课实验实测一个都没有）。

答错回看：原子写 的两个"为什么"。

测验 4 · 2 卡存的档（step=7）换 1 卡续，step 会换算成多少？为什么必须换算？

答案：7 × 2 // 1 = 14——反方向（1 卡存、2 卡读）才是测试锁的那个方向：7 × 1 // 2 = 3（test_checkpoint_six_pack_roundtrip 断言 step == 3）。必须换算是因为"步数"的口径是每进程的：2 卡各跑一半样本，同样 7 步的工作总量只有单卡的一半；不换算，进度虚报/少报，LR 余弦（只吃步数的纯函数）随之在错误的进度上取值。

答错回看：三语义 的换算段与 test_checkpoint_six_pack_roundtrip。

🧪 变式 · kill 之后把数据集换掉再 resume，会发生什么？

沿用本课实验：B 已被 kill -9，checkpoints/pretrain_64_resume.pth 里躺着 step=30 的六件套。现在不删它，启动一个 换了数据集 的训练（例如 --set data.dataset=sft_t2t_mini，或任何另一份语料），resume 保持默认开。 先合上书推理一遍。

写下预测：会报错吗？恢复清单还打吗——打的进度是多少？SkipBatchSampler 跳过的 30 个 batch 来自哪个数据集的打乱序列？这份训练等效于什么？

观察结果与解释（先预测再看）

不报错，一切"正常"：续训恢复清单：epoch=0 step=30 … 照打， Epoch 1：跳过前 30 个 micro step 续训 照跳。但跳的 30 批是对新数据集 长度与顺序做的打乱——旧账记的是旧语料上的进度，却由新语料来偿还； 训练等效于"旧数据集练了 30 步 + 新数据集从它自己的第 31 批开始"， LR 预算与数据预算两头错位。这正是猎场二（500513b）的机制最小复现： resume 探测只看"同名文件在场"，不核对数据集身份——config 快照件里明明存着答案， 只是没人比对。作者没有为变式真跑这一次（避免污染共享仓库的 checkpoint 现场）， 推理依据全部来自 [存档 docs/pretrain_readiness.md §6 · 2026-09-25] 的实跑事故 与 _load_initial_weights 的探测条件源码；你若有独立环境，值得亲手跑一遍看那份"正常的日志"。

本课词汇

训练状态 training state / checkpoint 语义
训练进程在某一刻的全部可变状态：模型权重 + 优化器矩 + scaler 水位 + 进度（epoch/step）+ 配置快照 + best 指标，再加 RNG 四态与 world_size。checkpoint 存的不是"模型"而是它——缺一件，续训就从那一件开始"重新开始装作接着练"。
六件套 six-pack payload
save_checkpoint 的 payload：model（fp32 主权重）/ optimizer / scaler / 进度（epoch+step 两键）/ config 快照 / best_val_loss；附加 rng 与 world_size，实测顶层 9 键。tiny 6.44 MB（优化器件占 4.3 MB），64M 约 731 MB。
RNG 状态 RNG state
四路随机数发生器的当前状态：torch（CPU 全局）、cuda（每卡一份）、python random、numpy——四路独立，少一路那一路静默分叉。存档与恢复换来"位精确续训"：恢复后每步随机数与原进程逐位相同。
位精确续训 bit-exact resume
恢复进程产生的随机数序列与被中断进程在同一时刻逐位相同——"接着练"的最强形式；CUDA 设备数变化时降级为警告继续（不再位精确）。
原子写 atomic save
先写同目录 .tmp 再 os.replace（内核 rename，只改目录项、要么完成要么没发生）。防"写到一半被杀留下半个 checkpoint"；最坏遗产是孤儿 .tmp（kill -9 实测一个都没有）。
resume-by-default 在场即恢复
续训做成默认行为：checkpoint 文件在场即恢复，无需配置。长跑中断保险（kill -9 实验 0.29%/0.67% 偏差通过）；另一面是猎场二：换数据集后旧档静默劫持续训——启动前 ls checkpoints/ 不可省。
三语义（训练侧）resume / init_from / finetune_from
resume：默认开，六件套全量恢复，模型件 strict=True；init_from：严格权重起点（DPO 从 pretrain 起步），不匹配即炸；finetune_from：非严格 + 逐 key warning（M09 的"不许装哑"）。恢复清单日志让加载错误第一步现形。
world_size 重标定 step rescaling
换卡数续训时按 step × saved_ws // current_ws 折算进度：步数口径是每进程的，2 卡各跑一半样本，7 步的工作总量只抵单卡 3~4 步（测试断言 7→3）。LR 纯函数随之自然对齐。
双轨记账 full_iters / iters
fd9fdc8 修复的纪律：full_iters（epoch 全长，不扣 skip）专供全局步数与 LR 分母；iters（本次实际迭代数 = 全长 − start_step）专供循环终点与 is_last（按 start_step + iters − 1 判定）。一个量两副面孔，让它们各自得名。
